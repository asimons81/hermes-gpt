## 1. Purpose

v0.6 is a **major release** that turns Hermes GPT from "ChatGPT can call Hermes
tools" into a **safe local control plane** where ChatGPT can observe,
coordinate, constrain, review, and operate an entire Hermes + Codex agent
fleet.

Three closely related capabilities ship together as **one integrated release**,
tentatively branded **Mission Control**:

1. Mission Control (observability)
2. Outcome / Work Contracts (verifiable work definition)
3. Swarm Orchestration (multi-agent coordination)

The three capabilities reinforce each other: you can only orchestrate what you
can observe, and you can only verify what you have contracted. Shipping them
separately would create a partial control plane that cannot deliver the core
promise — a trustworthy answer to *"What is my entire Hermes fleet doing right
now, and is the work actually done?"*

This brief captures scope only. Implementation is out of scope until the brief
is approved and the downstream planning artifacts are finalized.

## 2. Capabilities

### 2.1 Mission Control — unified operational view

Give trusted clients (ChatGPT first) a unified operational view of the Hermes
ecosystem.

- Surface profiles, fleet agents, Codex jobs, cron activity, delegated work,
  failures, pending approvals, health, and other meaningful runtime state.
- Goal example: a user asks **"What is my entire Hermes fleet doing right
  now?"** and gets a useful, structured answer.
- Read-only by default. Observation must not require mutation privileges.

### 2.2 Outcome / Work Contracts — verifiable work orders

Move beyond sending agents loose prompts.

- Introduce structured work orders/contracts that define: objective, assigned
  agent/profile, allowed scope, forbidden actions, expected artifacts, tests,
  review requirements, and completion criteria.
- Hermes GPT must be able to determine whether work **actually satisfied the
  contract** rather than trusting a worker's claim that it is finished.
- Build on top of the authority, policy, dry-run, audit, fleet work-order, and
  safety primitives Hermes GPT already has.

### 2.3 Swarm Orchestration — coordinated multi-agent workflows

Allow Hermes GPT to coordinate multi-agent workflows across Hermes profiles,
delegated Hermes agents, isolated Git worktrees, and Codex.

- Example workflow shape: research -> architecture -> parallel
  implementation/tests/docs -> integration review -> Codex review -> acceptance
  validation -> human approval.
- Upstream Hermes now supports isolated worktrees for delegated subagents —
  investigate how that should be incorporated rather than reinvented.
- Goal is **not** "more agents for the sake of agents." It is reliable
  decomposition, bounded parallelism, clear ownership, safe handoffs, and
  verifiable completion.

## 3. Target users

| User | Primary need | How v0.6 serves them |
|---|---|---|
| Tony (operator/owner) | Trust a fleet of agents with real work | Ask "what is my fleet doing?" and get a structured answer; approve bounded work orders; see failures and pending approvals in one place |
| ChatGPT (trusted client) | Act as the control-plane surface | Full observability + ability to draft, coordinate, and validate contracted work within authority boundaries |
| Future trusted clients | Programmatic access to fleet state | A read-only, authenticated operational view API |

Non-target (v0.6): unauthenticated or public exposure of operational data,
multi-tenant/multi-owner fleet management, external SaaS control planes.

## 4. Goals / Non-goals

### Goals

- G1. Mission Control surfaces all listed runtime state (profiles, fleet
  agents, Codex jobs, cron activity, delegated work, failures, pending
  approvals, health) through a single read-only, authenticated surface.
- G2. Work Contracts make "done" verifiable: Hermes GPT can evaluate contract
  satisfaction against artifacts, tests, and completion criteria — not just a
  worker's claim.
- G3. Swarm Orchestration reliably runs a research -> ... -> approval workflow
  with bounded parallelism, clear ownership, safe handoffs, and verifiable
  completion.
- G4. All three capabilities preserve the existing safety philosophy (see
  Constraints).
- G5. Supporting features that naturally belong in v0.6 (approval inbox,
  richer Codex job steering, workflow/event timelines, structured progress
  reporting, checkpointing) are included only with justification; scope must
  not explode.

### Non-goals

- NG1. No weakening of existing Operator / Owner Mode gates to make
  orchestration easier.
- NG2. No fake sandbox claims: orchestration does not pretend to sandbox
  agents that are not sandboxed.
- NG3. No unauthenticated or public-facing operational data exposure.
- NG4. No multi-tenant fleet management or shared-fleet SaaS.
- NG5. No reinvention of upstream Hermes isolated-worktree support — adopt and
  integrate it.
- NG6. No implementation work during the planning phase (this brief, design,
  data inventory, risk review, and plan all precede code).

## 5. Success criteria

- S1. A user can ask "What is my entire Hermes fleet doing right now?" through
  a trusted client and receive a structured, accurate, bounded answer covering
  every listed surface (or an explicit "unavailable" with a reason).
- S2. A contracted work order can be dispatched and independently validated:
  Hermes GPT can reject or return for rework a worker that claims completion
  without satisfying the contract's artifacts/tests/criteria.
- S3. A multi-stage swarm workflow (research -> architecture -> parallel
  implementation -> integration review -> Codex review -> acceptance -> human
  approval) completes end-to-end with ownership and handoffs tracked at each
  step.
- S4. Every mutation path in v0.6 remains dry-run-first and gated; read-only
  surfaces require no mutation privileges; approval is required wherever
  consequence warrants it.
- S5. Downstream planning artifacts are complete and consistent with this
  brief before implementation begins.

---

## 6. Constraints

Preserve Hermes GPT's existing safety philosophy:

- read-only by default where appropriate
- dry-run-first mutation
- explicit authority boundaries
- bounded outputs
- redaction and secret-path protections
- auditable actions
- human approval where consequence warrants it
- no fake sandbox claims
- no weakening existing Operator / Owner Mode gates just to make orchestration
  easier

Technical constraints:

- Hermes GPT is a standalone MCP sidecar; it imports Hermes Agent internals at
  runtime and must not modify Hermes Agent source files.
- Existing env-gated tool surfaces (operator, policy, dry-run, audit, fleet
  work orders, Codex runner) are the foundation — v0.6 layers on top rather
  than replacing them.
- Codex integration keeps its fixed-argv, `shell=False`, bounded-timeout,
  approved-working-directory posture.
- Mission Control data exposure is subject to the data inventory and risk
  review artifacts; every sensitive surface needs a stated risk level and
  mitigation or approval gate before it ships.

1. **Branding**: is "Mission Control" confirmed as the release name, or is it a
   working title?
2. **Trusted-client scope**: ChatGPT first — do any other clients need the
   surface in v0.6, or is the API the only other deliverable?
3. **Success-criteria acceptance**: are S1–S5 the right bar, and is there any
   criterion to add (e.g. performance bounds on "what is my fleet doing").
4. **Supporting-feature appetite**: which of approval inbox, richer Codex job
   steering, workflow/event timelines, structured progress reporting, and
   checkpointing are must-haves for v0.6 vs. stretch?
5. **Contract authority**: who may dispatch contracts — ChatGPT alone, or
   operator-level profiles too, and does dispatch require pre-approved contract
   templates?
6. **Fleet topology**: single-host fleet (this machine + Codex) only, or does
   v0.6 need to account for remote fleet nodes (e.g. other operator machines)?
7. **Approval mechanics**: should pending approvals surface in Mission Control
   and be actionable from it, or view-only?
8. **Timeline pressure**: is there a target date for v0.6, or does the plan
   gate purely on artifact quality?
