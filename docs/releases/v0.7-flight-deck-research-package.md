### 3.0 Release and distribution state

### 3.1 Current MCP compatibility

**Verified facts**

- `hermes-gpt` is a standalone local-first MCP sidecar for Hermes Agent; it
  imports Hermes internals at runtime and does not modify Hermes source
  files.[11]
- The package depends on `mcp[cli]>=1.0,<2`; the checked-out venv runs **MCP
  Python SDK 1.28.1**, whose `SUPPORTED_PROTOCOL_VERSIONS` are `2024-11-05`,
  `2025-03-26`, `2025-06-18`, and `2025-11-25` (LATEST), verified in
  `.venv/lib/python3.11/site-packages/mcp/shared/version.py` and
  `mcp/types.py`.[23][28]
- Transports: stdio (default), streamable HTTP (`--http`, `/mcp`), and
  legacy SSE (`--sse`, `/sse`). FastMCP is constructed with
  `stateless_http=http` and `json_response=http` for the HTTP path.[22]
- Tool metadata advertises security schemes: `oauth2` when OAuth is
  configured, bearer when a static bearer is set, `noauth` otherwise.[22]
- ChatGPT-specific compatibility: allowed origins include
  `https://chatgpt.com`; the OAuth flow targets ChatGPT connector values
  (authorization endpoint, token endpoint, `client_secret_post`/`basic`,
  `offline_access`, OIDC disabled).[12][22]
- A second, curated MCP server exists for Codex as a client
  (`hermes-gpt mcp` / `hermes-gpt codex mcp`) with its own tool names (e.g.
  `hermes_extract_page` vs main-server `hermes_web_extract`).[11][13]
- The MCP spec's 2025-11-25 revision is the protocol's latest; it keeps the
  same feature families (resources, prompts, tools; sampling, roots,
  elicitation) and the same security principles (consent, data privacy, tool
  safety, LLM sampling controls).[8]

**Assessment**

MCP compatibility is in good shape for the 2024-11-05 → 2025-06-18 era and
the SDK already speaks 2025-11-25. The main risks are (a) ChatGPT connector
behavioral drift (streamable HTTP + OAuth semantics), (b) legacy SSE being
deprecated upstream, and (c) the tool surface being large — the schema is
the attack surface and the trust boundary for every client. For v0.7,
"current MCP compatibility" should be pinned to: protocol version
negotiation verified against the SDK, ChatGPT streamable-HTTP path verified
end-to-end with OAuth, and a documented minimum supported MCP protocol
revision.

**Confidence: High** (primary sources: SDK code, server.py, oauth.md).

### 3.2 Long-running task lifecycle management

**Verified facts**

- Recent master commits (2026-08-15) directly target long-running work:
  - `hermes_cron_run` gained a `timeout` parameter (30–7200 s, default 1800
    s) because "real agent cron jobs commonly run longer than two
    minutes".[10]
  - `operator_policy.run_argv` gained a `timeout_cap` (default 600 s, ceiling
    7200 s) so narrowly scoped callers such as the cron runner can raise the
    subprocess budget explicitly.[10]
  - Hermes GPT self-restarts via `systemctl --user restart
    hermes-gpt-server.service` are deferred through `systemd-run
    --on-active=3s` so the MCP response and audit record complete before the
    process dies.[10][22]
- Work Contracts (`hermes_contract_*`) define dispatchable work with
  objective, owner, scope, forbidden actions, artifacts, and review
  requirements; dispatch is workspace-level and dry-run-first.[13]
- Swarm Orchestration (`hermes_swarm_*`) runs DAG workflows on top of
  contracts with default caps (3 concurrent stages/workflow, 4/board, 12
  stages/workflow), one bounded rework retry, and a final human (Owner)
  approval gate.[13][19]
- Codex jobs (`hermes_codex_*`) are asynchronous; restart reconciliation
  marks orphaned PIDs rather than signalling them.[2]
- Kanban (platform) is the durable alternative to `delegate_task`: "Block →
  unblock → re-run; crash → reclaim" resumability vs "None — failed =
  failed", with durable SQLite rows for every handoff.[5]

**Gaps**

- No checkpoint/resume of an in-flight stage across Hermes GPT restarts:
  swarm workflow state is persisted, but advancing a stage after a restart
  is a manual `hermes_swarm_stage_advance` call, not an automatic recovery
  loop.[19]
- `delegate_task` (platform) is a fork/join call with no resumability; long
  reasoning subtasks die with the parent session.[5]

**Confidence: High** (commits, code, docs).

### 3.3 Restart-safe continuity

**Verified facts**

- Hermes GPT persists its own operational state on disk:
  - Swarm workflow instances persist as minimal operational JSON under
    `<hermes_root>/swarm-workflows/` (atomic tmp-write), mirroring the
    `codex-jobs/` pattern.[19]
  - Codex job metadata/transcripts persist with a 30-day age-based cleanup
    window.[14][26]
  - Operator audit trail is append-only JSONL.[13]
- Platform-side durability (the host the sidecar controls):
  - Every conversation is stored in SQLite `state.db` with FTS5; gateway
    chats are designed to be one continuous session "across gateway crashes,
    restarts, and updates"; routing rows are repaired automatically on the
    next turn.[4]
  - Kanban is a durable SQLite board; crash → reclaim is built into the
    dispatcher.[5]
- Documented non-durable surface: OAuth authorization codes, access tokens,
  and refresh tokens are memory-backed only. "Restarting Hermes GPT
  invalidates all issued credentials and requires the connector to authorize
  again. This avoids introducing a persistent plaintext credential store.
  Durable encrypted token storage and explicit revocation administration are
  separate future features."[12]

**Assessment**

State that is written to disk survives restarts; state that is only in
process memory (OAuth credentials, mission cache, in-flight HTTP sessions)
does not. For the "Flight Deck" thesis this is the single most important
continuity decision: **durable encrypted token storage** is a named future
feature and is a natural v0.7 pillar, but it is a security-sensitive design
with tradeoffs (where keys live, revocation, leakage windows) that needs the
architecture + legal lanes before implementation.

**Confidence: High**.

### 3.4 Production review evidence

**Verified facts**

- v0.6.0 shipped a documented limitation: "v0.6.0 does not ship a production
  review-accept writer. If a contract requires review, the necessary evidence
  must already exist through an authorized external reviewer/audit path or
  human approval reference. If it does not exist, validation returns
  `NOT_SATISFIED` rather than inventing acceptance."[14]
- The contract validator accepts two review-evidence forms today: (1) an
  audit record of `hermes_contract_validate` with verdict
  `SATISFIED`/`accept`/`ACCEPT` by a reviewer distinct from the assignee;
  (2) a human approval reference (`authorization.approved_by` +
  `approval_reference`) by someone other than the assignee.[20]
- The release program itself uses gate review artifacts: the v0.6 surface
  manifest was a G2 approval packet approved by Tony; v0.6 planning used
  data-risk and swarm-risk reviews by the legal lane.[18][16]
- The repository's `review-*` directories (`review-bench`, `review-compat`,
  `review-fixtures`, `review-qa`) are empty placeholders in the current
  checkout.
- **New finding: CI on master is red.** The four most recent master commits
  (5a203f9 scope skill writes, 0555592 allow long-running cron jobs, a144639
  defer self-restarts, 2429406 honor extended cron timeouts) all failed CI
  (GitHub Actions, ubuntu, Python 3.10–3.12) on the same 8 tests in
  `test_operator_skills.py` (e.g. `test_skill_create_direct_uses_skill_manager_when_available`).
  The failure reproduces locally with a plain `python -m pytest` and is
  caused by the 5a203f9 change: `_call_skill_manager` now imports
  `hermes_constants.set_hermes_home_override` which is not importable when
  the Hermes Agent source root is not on `sys.path` (CI installs only
  `.[dev]`). With `PYTHONPATH=/home/tony/.hermes/hermes-agent`, the full
  suite passes (1 skip).[9]

**Assessment**

"Production review evidence" is currently a **verified gap**: v0.6 has a
fail-closed validator but no writer. v0.7 must define the review-evidence
contract: who may write a review acceptance, through what tool
(`hermes_review_accept`-style, owner-gated, audited), with what
independence guarantees (reviewer distinct from assignee, no self-review),
and how it feeds `hermes_contract_validate`. In parallel, the red CI must be
fixed before any v0.7 candidate is tagged — a release gate, not a nice-to-have.

**Confidence: High** (code, release notes, CI logs).

### 3.5 Structured event history

**Verified facts**

- Operator audit: append-only JSONL with bounded metadata (tool, level,
  apply mode, dry-run state, changed/success, IDs, length/hash for
  content-bearing ops); raw prompts and secrets are never persisted.[13]
- Kanban `task_events` records every task transition durably (claimed,
  blocked, completed, spawn_failed, protocol_violation, gave_up, etc.).[5]
- Cron `executions.db` tracks per-run status/timestamps/errors (observed
  949 completed / 29 failed / 22 unknown on this host).[17]
- Mission Control surfaces `audit`, `delegations`, `failures`, `approvals`
  as read-only views with redaction.[13][18]
- Swarm workflow records carry stage handoffs (`from`, `to`,
  `artifact_refs`, `contract_verdict`).[19]

**Gap**

- There is no unified, queryable event timeline across swarm/contract/kanban/
  cron/audit. v0.6 explicitly deferred "workflow/event timelines, structured
  progress reporting, and checkpointing" as supporting features requiring
  justification (NG-SW8).[27] A "structured event history" pillar for v0.7
  means defining an event schema and a read surface (likely a new Mission
  Control surface or a dedicated `hermes_events_*` group) that lets a
  trusted client answer "what happened, in what order, to which work" —
  without exposing raw bodies.

**Confidence: High on current state; the v0.7 target shape is a design
decision.**

### 3.6 Explainable least-privilege authority

**Verified facts**

- Operator authority is a strict level ladder `read_only → cron → skills →
  skills_config → workspace → owner`, gated by env, per-call `dry_run`, and
  `confirm` where defined. "Tool visibility is not authority."[13]
- Default posture is read-only; mutations require
  `HERMES_GPT_OPERATOR_APPLY_MODE=direct` + `dry_run=false`; Owner Mode
  requires exact ack and still denies secret paths.[13]
- Mission Control allowlist semantics: unset = all read-only surfaces,
  explicit list = only listed, empty = none.[13][18]
- Fleet dispatch re-checks live peer identity/role against a
  server-controlled authority manifest before structured dispatch; callers
  cannot supply arbitrary peer endpoints or tokens.[13][21]
- Contract validation checks forbidden actions scoped to the contract's task
  identity so unrelated concurrent work cannot contaminate verdicts.[20]
- Every operator action is audited; secrets, raw prompts, and PII-stripped
  free-text never leave the host.[13][18]

**Assessment**

The least-privilege model is mature and explainable: each tool documents its
authority class, each refusal is an expected policy result, and the audit
trail makes decisions traceable. This sits on top of the platform's own
defense-in-depth model (dangerous-command approval, hardline blocklist,
container isolation, MCP credential filtering), which the sidecar does not
weaken.[6] v0.7's job is to keep this model intact
while adding new surfaces (review-accept writer, event history, Flight Deck
UI actions) — each new mutation must land in an existing authority class
with an explicit gate, never a parallel bypass. The current gap: there is no
per-client identity → per-surface mapping beyond the Mission Control
allowlist; a "hardened trusted-client access" pillar (3.7) interacts with
this directly.

**Confidence: High**.

### 3.7 Hardened trusted-client access

**Verified facts**

- **Unreleased OAuth work on master** (CHANGELOG "Unreleased"; commit
  826aa43 "feat: add secure OAuth for remote MCP", merged via PR #13):
  single-confidential-client OAuth authorization-code flow with optional
  PKCE S256, stateless signed authorization codes, bounded memory-backed
  replay/token state, one-hour access tokens, 30-day rotating refresh tokens
  with replay rejection, replay/client/scope/resource validation, explicit
  direct-TLS or loopback trusted-proxy enforcement, and ChatGPT-compatible
  streamable-HTTP normalization.[10][12][22]
- Static bearer alternative remains supported and compatible with OAuth
  access tokens.[12]
- Transport security: `TransportSecuritySettings` (allowed hosts/origins,
  DNS-rebinding protection), trusted-proxy IP allowlist
  (`HERMES_GPT_TRUSTED_PROXY_IPS`, loopback-only entries), CORS restricted
  to `https://chatgpt.com` + issuer origin.[22][25]
- Cloudflare Tunnel deployment is documented with origin Host override and
  `HERMES_GPT_ALLOWED_HOSTS` defense-in-depth.[25]
- The remote profile refuses to start without real authentication
  ("Remote profile requires real authentication. Configure a static bearer
  token or confidential-client OAuth."), unless an explicit unsafe
  no-auth ack is given.[22]

**Assessment**

The OAuth boundary is the most substantial unreleased v0.7 candidate and is
well-specified. Hardening decisions for v0.7: (a) promote OAuth from
"Unreleased" to a shipped, tested, documented feature; (b) decide whether
durable encrypted token storage ships (see 3.3) or whether the
restart-reauthorize behavior is accepted for v0.7; (c) verify the OAuth path
against a live ChatGPT connector before claiming compatibility; (d) keep the
loopback/trusted-proxy posture as the only supported remote deployment.

**Confidence: High** (code + docs).

### 3.8 Architecture seams for cross-machine swarm execution (stretch)

**Verified facts**

- Fleet routing already dispatches bounded work to **remote A2A peers**
  through the local authenticated A2A registry: `hermes_fleet_*` tools,
  authority manifest, live peer verification (`a2a doctor`), work-order
  envelopes, safe completion bundles. On this host the registry has 1 peer
  (Hermes Arch Lead @ 192.168.4.41:8765) and 7 tasks.[17][21]
- Kanban (the platform's durable board) is **deliberately single-host**:
  "Running a shared board across two hosts is not supported — there's no
  coordination primitive for 'worker X on host A, worker Y on host B,' and
  the crash-detection path assumes PIDs are host-local. If you need
  multi-host, run an independent board per host and use `delegate_task`/a
  message queue to bridge them."[5]
- Swarm workflows run on contracts validated from **host-local observed
  state** (kanban task_runs, async delegations, artifacts on disk, audit
  trail). The engine itself is a local JSON store; it has no remote-stage
  primitive.[19][27]
- Hermes Agent itself runs on 6 terminal backends (local, Docker, SSH,
  Daytona, Singularity, Modal), which is a platform-side seam for remote
  execution but not a Hermes GPT swarm seam.[3]

**Assessment**

Cross-machine swarm execution is correctly classified as **stretch**. The
existing A2A fleet dispatch is the honest seam — a swarm stage could be
dispatched to a remote peer as a bounded work order whose completion is
validated from the *remote* peer's observable state — but the current
validator reads local observed state only. A cross-machine seam must solve:
remote observed-state collection (what does "done" mean on host B?),
identity/authority propagation, and crash/lease semantics across hosts.
The v0.7 architecture should **define seams, not implement them**: explicit
interfaces (a dispatch adapter, a remote-evidence provider) that keep
single-host behavior unchanged.

**Confidence: High on current state; design work required for seams.**

## 4. Product thesis validation: "durable, interactive, verifiable autonomy"

| Thesis component | Evidence | Verdict |
|---|---|---|
| **Durable** | Sessions survive crashes/restarts; kanban is a durable SQLite board with crash reclaim; swarm/contract/codex state persists on disk; cron registries + executions persist.[4][5][19][26] | **Mostly true.** Exception: OAuth credentials are memory-only and invalidated on restart; in-flight stage advancement is manual after restart.[12] |
| **Interactive** | Trusted clients (ChatGPT, Codex) drive the control plane through MCP tools; operator levels + confirm gates keep humans in the loop; swarm ends in a human Owner approval gate; platform gateway spans 21+ messaging platforms.[7][13][3] | **True for MCP-first interaction.** The interactive loop is tool-schema-driven; a dedicated UI (Flight Deck) would make interaction richer but is not required for the thesis. |
| **Verifiable** | Work Contracts validate completion from observed state, fail closed, reject false "done"; forbidden-action checks are scoped; review evidence must exist and be independent; audit trail is structured and redacted.[13][20][14] | **True, with one named gap:** there is no production review-accept *writer* yet; verification depends on external review paths or human approval references.[14] |

**Bottom line.** The thesis is technically supported today for a single-host,
trusted-client deployment, with two honest caveats: (1) verification is
stronger than durability for *live* work (a restart can strand in-flight
credentials and requires manual stage advancement); (2) "verifiable"
currently means "the system can check evidence that already exists" — the
write side of review evidence is the missing half. v0.7's Flight Deck
positioning should claim exactly what is true: durable state for
coordination, interactive control through trusted clients, and
evidence-based completion — while the review-accept writer and durable
token storage close the two caveats.

**User-constraint check.** Tony is the sole operator/owner; the deployment
is single-host local-first with a trusted ChatGPT connector; the safety
philosophy (read-only default, dry-run-first, no fake sandbox, human
approval where consequence warrants) is a hard constraint carried from
v0.6.[15][16] Nothing in the thesis conflicts with these constraints as long
as new surfaces (review writer, event history, OAuth token storage) stay
inside the existing authority model.

## 5. Release brief — Hermes GPT v0.7.0 "Flight Deck"

### 5.1 Positioning

v0.6 turned Hermes GPT from "ChatGPT can call Hermes tools" into a **safe
local control plane** (observe, coordinate, verify).[15] v0.7 "Flight Deck"
completes the control-plane story: the operator gets a **hardened,
continuity-safe deck** from which durable, long-running, verifiable work is
watched, steered, reviewed, and trusted — with the current MCP surface kept
current and the authority model kept explainable.

Proposed one-liner (for growth to refine): **"The Flight Deck: watch
long-running agent work survive restarts, prove it's actually done, and
authorize it — from your trusted client."**

### 5.2 Scope

**In scope (core pillars)**

1. **Current MCP compatibility** — pin and verify supported protocol
   revisions against SDK 1.28.x; verify the ChatGPT streamable-HTTP + OAuth
   path end-to-end; document minimum supported MCP revision; keep Codex
   toolset current.
2. **Long-running task lifecycle** — harden cron/Codex/swarm long-running
   behavior (already partially landed on master); add recovery/resume
   semantics for in-flight swarm stages; document lifecycle states.
3. **Restart-safe continuity** — durable encrypted token storage decision
   (see options 5.6); document what survives a restart and what requires
   re-authorization; add a restart-recovery test story.
4. **Production review evidence** — ship a production review-accept writer
   (owner-gated, audited, distinct-reviewer enforced) feeding
   `hermes_contract_validate`; close the v0.6 gap.[14]
5. **Structured event history** — define an event schema and a read surface
   (Mission Control surface or `hermes_events_*`) across swarm/contract/
   kanban/cron/audit; redacted, bounded, queryable.
6. **Explainable least-privilege authority** — preserve the level/gate
   model; every new mutation lands in an existing authority class; no new
   bypasses.
7. **Hardened trusted-client access** — promote the unreleased OAuth
   boundary to shipped/verified/documented; retain bearer + loopback/trusted
   proxy posture; verify against live ChatGPT connector.
8. **Cross-machine swarm seams (STRETCH)** — define seams only (dispatch
   adapter, remote-evidence provider, authority propagation interface); do
   not implement cross-machine execution.

**Out of scope**

- Cross-machine swarm implementation (stretch only).
- Multi-tenant / multi-owner fleet management (carried from v0.6 NG4).[16]
- Any weakening of Operator/Owner gates to make orchestration easier (NG1).[16]
- No fake sandbox claims (NG2).[16]
- No unauthenticated or public-facing operational data exposure (NG3).[16]

### 5.3 Success criteria (draft for Tony's acceptance)

- **S1.** A trusted client can start a long-running swarm workflow, restart
  Hermes GPT mid-flight, and resume/advance the workflow from durable state
  without losing evidence.
- **S2.** A reviewer distinct from the assignee can write a review acceptance
  through a production tool; a contract requiring review validates
  `SATISFIED` only with that evidence; self-review is rejected.
- **S3.** A trusted client can query a structured event history for any
  swarm/contract/cron/kanban/audit activity ("what happened to task X, in
  order") without raw bodies.
- **S4.** The OAuth boundary is released, tested, and documented; remote
  access without real authentication is impossible; restart behavior is
  documented and intentional.
- **S5.** Every new mutation surface is audited, gated, and mapped to an
  existing authority level; no regression in v0.6 safety tests.
- **S6.** CI is green on master before the v0.7.0 candidate is tagged; the
  release doctor reports PASS or understood WARN only.[24]

   theme with the MCP surface as the UI? This changes the architecture card
   materially.
3. **Durable token storage:** ship encrypted token persistence in v0.7
   (restart = no re-authorize), or accept documented restart re-authorization
   for one more release? (Options in 5.6.)
4. **Review-accept authority:** who may write review acceptance — owner only,
   or any distinct reviewer profile at a defined level? Must review accepts
   be human-only, or may an authorized reviewer profile (e.g. legal/QA) write
   them?
5. **Event-history scope:** which event classes must be in the v0.7 read
   surface (swarm/contract/kanban/cron/audit all, or a subset)? Retention
   window for event history?
6. **Cross-machine stretch:** do the seam interfaces need to be demonstrated
   (two-process one-host demo) in v0.7, or is a written interface contract
   enough?
7. **Timeline:** is there a target date for v0.7.0, or does the plan gate
   purely on artifact quality (as v0.6 did)?[16]

### 5.6 Decision options

**D1 — Durable token storage (3.3/5.2/5.5-Q3)**

- **Option A (recommended):** Ship durable encrypted token storage in v0.7.
  Enables restart-safe continuity without re-authorization, closes the
  biggest continuity caveat, and makes "durable" true end-to-end. Requires
  architecture (key management, OS keyring vs encrypted file), legal review
  (leak/revocation windows), and tests.
- **Option B:** Keep memory-backed credentials; document restart
  re-authorization as intentional for v0.7. Cheaper, safer surface, but the
  thesis claim "durable" stays qualified.
- **Option C:** Ship OAuth without persistence and defer the decision to
  v0.8. Lowest risk; continuity gap remains.

**D2 — Flight Deck UI (5.5-Q2)**

- **Option A (recommended):** "Flight Deck" = the control-plane release
  theme; the trusted-client MCP surface (Mission Control + new event/review
  tools) is the UI. Fastest, matches v0.6 posture, no new attack surface.
- **Option B:** A read-only web dashboard backed by existing Mission Control
  surfaces (no new authority). Medium effort; a real visual "deck".
- **Option C:** Full interactive dashboard with action buttons. Highest
  effort/risk; needs a separate design and security review.

**D3 — Review-accept writer authority (5.5-Q4)**

- **Option A (recommended):** Owner-gated write; any distinct profile at
  `workspace`+ level may request, but the accept lands only at owner level
  with audit + distinct-reviewer enforcement. Matches swarm's final human
  approval philosophy.[13]
- **Option B:** Distinct-reviewer profiles at `workspace`+ may write
  acceptance directly (faster, more autonomous, higher abuse risk).
- **Option C:** Human-only via external approval reference (keep v0.6
  behavior, add a UI/connector path for it).

**D4 — Event-history surface (5.5-Q5)**

- **Option A (recommended):** New read-only `hermes_events_*` surface with
  allowlist + retention + redaction, covering swarm/contract/kanban/cron/
  audit.
- **Option B:** Extend Mission Control with an `events` surface (simpler,
  but bloats the already-large overview).
- **Option C:** No new surface; document the existing stores as the event
  history. Cheapest, weakest answer to "what happened in order".
