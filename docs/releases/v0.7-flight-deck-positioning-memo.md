## 2. Positioning statement

v0.6 turned Hermes GPT from "ChatGPT can call Hermes tools" into a **safe local
control plane**: observe, coordinate, constrain, and verify. v0.7 Flight Deck
completes that story. The operator gets a hardened, continuity-safe deck from
which long-running agent work is watched, steered, reviewed, and trusted, with
the MCP surface kept current and the authority model kept explainable.

**Core promise:** durable work, interactive control, verifiable completion.

**One-liner (refined from the research brief §5.1):**

> The Flight Deck: watch long-running agent work survive restarts, prove it's
> actually done, and authorize it from your trusted client.

The spine of the narrative is **receipts, not reports.** A worker's self-report
was never the source of truth; the v0.7 story makes that explicit across the
whole lifecycle: state that persists, evidence that validates, and gates that
explain themselves.

## 3. Target segments

| # | Segment | Primary need | How v0.7 Flight Deck serves them |
|---|---|---|---|
| S1 | **Tony (single-host operator/owner)** — primary | Trust a fleet of agents with real, long-running work without babysitting or losing state | Restart-safe continuity so a swarm or cron job is not stranded by a process restart; review evidence so "done" is checked against observed state; every action gated, audited, and explainable |
| S2 | **Trusted clients (ChatGPT first, Codex second)** | Act as the deck itself: watch, steer, review, and authorize from a conversational surface | Full control-plane surface through current MCP tools; hardened authenticated boundary (OAuth) so the remote client is real; structured event history so "what happened to task X, in order" is answerable |
| S3 | **Technical early adopters of Hermes Agent / local-first agent operators** (external, niche) | A reference pattern for safe agent autonomy on their own machine | A documented, tested example of durable, interactive, verifiable autonomy: contracts, swarms, review evidence, least-privilege authority, all local-first |
| S4 | **Future single-host deployers** (small operators, power users) | Set up a trusted-client control plane without weakening safety | Same stack as S1/S2, packaged so a new operator can stand it up with documented defaults and gates |

**Non-targets (do not position to these):** multi-tenant / multi-owner fleet
management, SaaS control planes, unauthenticated or public operational data
access, enterprise compliance buyers who need vendor-managed guarantees. These
are explicit non-goals in the research package (§5.2) and in v0.6 planning (NG1,
NG3, NG4). Positioning to them would break the product invariants.

**Audience-first implication:** the release narrative leads with S1/S2 (what
Tony can do through ChatGPT that he could not do before), then S3/S4 (why a
local-first operator would care). The message hierarchy below is ordered that
way.

## 6. Differentiation

**vs. a plain MCP tool server.** A tool server exposes tools. Hermes GPT gates
them, audits them, contracts them, and verifies the result. The contrast is a
tool surface versus a control plane. Anyone can let ChatGPT call a function;
Hermes GPT is the layer that decides whether the call was allowed, what it
changed, and whether the work is actually done.

**vs. agent orchestration frameworks (LangGraph, CrewAI, and the like).** Those
are code libraries you build an orchestration layer with. Hermes GPT is a
runtime control plane over a real agent system, with an authority model and an
evidence trail already built in. Frameworks give you primitives; Flight Deck
gives you the operating discipline on top of a working agent runtime.

**vs. SaaS automation platforms (Zapier, n8n cloud, and similar).** Those route
your data through someone else's control plane. Hermes GPT is local-first:
loopback default, read-only default, dry-run-first mutation, and the only
remote path is a real authenticated private boundary. The trust model is
"your machine, your keys, your audit trail," not a vendor's SLA.

**vs. custom GPTs and ChatGPT Actions.** Those are stateless chat tools with no
durable state, no verification, and no audit. Flight Deck's whole point is that
the work is durable, the completion is verified against evidence, and the
history is queryable. A custom GPT can answer; it cannot prove.

The differentiation spine, stated plainly: **others orchestrate, Hermes GPT
verifies.** Chatbots and frameworks can run work; the control plane that proves
it, preserves it, and explains who was allowed to touch it is the gap Flight
Deck fills.

## 7. Claims guardrails

1. **No public publishing from this task.** This memo is internal. Any public
   claim requires the G5 release + outbound approval path and channel
   verification (PyPI vs GitHub state must be checked separately before each
   public statement).
2. **Map every claim to a proof point.** If a statement cannot be tied to a
   SHIPPED row or a passed gate in §5, it does not go in public copy.
3. **Never claim the review-accept writer, event surface, durable token
   storage, or shipped OAuth until their gates pass.** These are the named gaps
   and decisions from the research package (§5.2, D1–D4).
4. **Never claim cross-machine execution.** v0.7 defines seams; it does not
   implement remote swarm stages.
5. **Do not weaken the authority story to sell.** No fake sandbox claims, no
   "full autonomy" framing that implies un-gated action. The safety philosophy
   is the product.
6. **Re-verify before reuse.** TRT editorial and outreach must re-check the
   shipped capability list against the released candidate before drafting
   public copy; this memo is a point-in-time snapshot (2026-08-15).

### 8.4 Honesty note on telemetry

Hermes GPT is local-first and has no product telemetry, and we will not add
telemetry as part of v0.7. That means adoption and behavioral metrics come from
channels (PyPI, GitHub, X, docs), the beta program, and public discussion, not
from in-product events. The measurement plan above is built on what is actually
observable. The north-star proxy is therefore: **qualified operators running a
verified long-running workflow through a trusted client within 30 days of
release**, measured through beta activation and public reports, not through an
instrumented counter we would have to build.
