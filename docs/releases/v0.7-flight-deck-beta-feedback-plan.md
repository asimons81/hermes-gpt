## 1. Purpose

Define the closed beta feedback program for Hermes GPT v0.7.0 "Flight Deck":
who participates, how they are invited, how they give feedback, on what
cadence, and how that feedback becomes development work. This plan is a
planning artifact only. **No invitation, post, email, or message is sent
and no public action is taken from this card.** Every external message
requires Tony's explicit per-message approval.

The beta exists to answer one question before G5: does the Flight Deck
thesis ("durable, interactive, verifiable autonomy") hold for real users on
real machines, not just in the release harness? The success criteria S1–S6
from the research package are the acceptance bar; the beta validates them
in the field.

## 2. Program shape and timing (gate-relative, not calendar-relative)

The beta is gated on release gates, matching the v0.6 discipline that the
plan gates on artifact quality rather than dates (research package §5.5-Q7).

frozen candidate.

## 3. Participant criteria

Tier-1 criteria are the *required* bar for the named cohort. Every Tier-1
participant must meet all of:

1. **Runs Hermes Agent** — the sidecar controls a Hermes installation; a
   participant without Hermes cannot exercise the product. Must have a
   live local Hermes Agent install (any of the 7 terminal backends).
2. **Uses an MCP client** — ChatGPT connector, Codex, Claude Desktop, or
   another MCP host. The interactive surface is MCP-first; testing requires
   at least one real client.
3. **Runs locally** — Linux, macOS, or Windows with Python 3.10+; able to
   run a local server process and read logs.
4. **Can spend 1–2 hours/week for ~3 weeks** and will file structured
   GitHub issues (not just chat).
5. **Has prior signal of engagement with hermes-gpt or Hermes** — filed an
   issue/PR, starred/watched the repo, installed from PyPI, or responded to
   the public beta call.

Tier-2 (community reviewers, 5–10 people) relaxes the GitHub-issue
requirement: technically literate Hermes/MCP community members who exercise
specific pillars (OAuth remote path, review evidence, event history) and
report qualitatively (email or DM). Same local-run requirement.

Tier-3 (ecosystem observers, optional) is deferred to growth's positioning
work after G4; not part of this program's core.

**Non-criteria:** follower count, X status, any commercial relationship.
This is a technical beta, not an audience play.

## 5. Feedback collection channels

1. **GitHub Issues (primary, durable, routed to dev)** — all structured
   feedback lands as issues with label `beta-v0.7`. Template in the
   approval packet (bug / feature / pillar-focus variants). This is the
   mechanism that makes feedback *routable*, per §7.
2. **Email (private channel)** — participants who do not want public issues
   email `tony@tonyreviewsthings.com`; outreach transcribes to a GitHub
   issue on the participant's behalf (with their handle or anonymized).
3. **Weekly check-in** — a short email or DM per participant, weekly, with
   three fixed questions (broken/weird? most useful? dealbreaker?). Keeps
   cadence without a form tool.
4. **No telemetry.** Local-first product; nothing is collected or sent from
   participant machines. State this explicitly in onboarding so no one
   assumes instrumentation.

Optional (gated on Tony): a lightweight intake form (Google Form) for
non-GitHub Tier-2 participants. Not required for launch.

## 6. Cadence

- Day 0: invite email (or GitHub thread comment) to Tier-1 cohort.
- Day +2: onboarding email with setup guide + "what to test first" list.
- Day +7: nudge to non-responders (one nudge only; then drop per outreach
  follow-up principle).
- Weekly during the window: check-in message (Monday), triage pass
  (Friday).
- Week 3: close survey + decision digest + thank-you; request permission
  for beta-credits listing or quotes.
- Continuous: GitHub issue activity handled within 3 business days.

## 7. Feedback routing into development

The loop, concretely:

1. **Intake.** Participant files a `beta-v0.7` issue, or emails
   `tony@` and outreach files it.
2. **Triage (outreach, weekly).** Dedupe, classify (bug / UX / docs /
   feature / security), assign severity P0–P2, assess reproducibility.
3. **Route (outreach → kanban).** Each accepted issue becomes a kanban
   card assigned to `developer` (bugs and features) with the issue link in
   the body. P0/P1 security-sensitive items are routed through `default`
   to `legal` for review before any change (research package R5 invariant:
   no raw bodies, no leak channels).
4. **Fix or defer.** Developer resolves or explicitly defers with
   rationale. v0.7 scope discipline: feature requests go to backlog unless
   they are required by an in-scope pillar; they do not expand G3 slices.
5. **Close the loop.** Every issue gets a visible decision (accepted /
   fixed / wontfix / backlog). Participants receive the weekly decision
   digest and a final summary mapping their feedback to shipped changes
   before G5.
6. **Record.** Outreach mirrors beta outcomes into the Nexus
   (`ops/state/` beta-log or the release journal) so the program is
   auditable even after the GitHub thread goes quiet.

Success metrics: ≥60% invite acceptance among named Tier-1 targets; ≥8
active participants each filing ≥1 issue; ≥70% of issues reproducible and
actionable; all P0/P1 issues resolved or explicitly deferred before G5;
100% of issues get a visible decision.

## 9. Commitments and boundaries

- **No compensation is promised.** Value to participants: early access to
  the candidate and a direct line to the maintainer. Nothing else.
- **No NDA, no confidentiality.** MIT open-source project; participants
  test on their own machines. Do not imply otherwise.
- **No telemetry, no data collection** from participant machines. State it
  plainly.
- **No public release action from this card.** Publishing the candidate,
  the X post, or any release artifact is a separate Tony-approved action
  (G5).
- **Do not name the two open-issue reporters publicly** without their
  permission. Beta-credits listing and quotes require explicit opt-in.
- This plan does not mutate the outreach pipeline ledger; it is a release
  program, not a sponsorship deal.

## 10. Risks and mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Stargazer/PyPI pools do not respond (passive signal) | High | Medium | Prioritize named Tier-1 (issue/PR authors); X call widens the funnel |
| Participants without a working Hermes install cannot test | Medium | High | Criterion 1 is required; onboarding verifies install before the "what to test" list |
| Red CI blocks candidate freeze (R1) | Certain today | High | Beta start gated on G4 green; fix R1 before any candidate is offered |
| Feature requests expand v0.7 scope | Medium | Medium | Triage routes to backlog; only pillar-required requests enter G3 slices |
| Public issue thread becomes a leak/confusion channel | Low | High | Template is PII-safe; no raw bodies; outreach transcribes sensitive email to issues |
| Low participation → weak signal | Medium | Medium | Named-cohort invites first; weekly check-ins keep momentum; close survey captures reasons |
