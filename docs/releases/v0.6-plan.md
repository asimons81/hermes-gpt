## 2. Release objectives

The core promise of v0.6: turn Hermes GPT from "ChatGPT can call Hermes tools"
into a **safe local control plane** where a trusted client (ChatGPT first) can
observe, coordinate, constrain, review, and operate an entire Hermes + Codex
agent fleet — and verify that work is actually done, not just claimed.

Three capabilities ship **together** as one integrated release (brief §2), each
dependent on the others:

| # | Capability | One-line scope | Depends on |
|---|---|---|---|
| 1 | **Mission Control** | Read-only authenticated operational view (profiles, fleet, Codex jobs, cron, delegated work, failures, pending approvals, health + approved extras) | Observability foundation; nothing |
| 2 | **Outcome / Work Contracts** | Structured work orders with verifiable completion criteria, so "done" is checked not trusted | Mission Control view-model (contract satisfaction reads observed run state) |
| 3 | **Swarm Orchestration** | Coordinated multi-agent workflows (research→architecture→impl→review→acceptance→approval) with bounded parallelism + safe handoffs | Work Contracts (workflows run on contracts) + isolated worktrees |

### Success criteria (from brief §5 — the acceptance bar for the whole release)

- **S1.** A user asks "What is my entire Hermes fleet doing right now?" through a trusted client and gets a structured, accurate, bounded answer covering every listed surface (or an explicit "unavailable" with a reason).
- **S2.** A contracted work order can be dispatched and independently validated: Hermes GPT rejects / returns for rework a worker that claims completion without satisfying the contract's artifacts/tests/criteria.
- **S3.** A multi-stage swarm workflow completes end-to-end with ownership and handoffs tracked at each step.
- **S4.** Every mutation path in v0.6 remains dry-run-first and gated; read-only surfaces require no mutation privileges; approval required where consequence warrants.
- **S5.** Downstream planning artifacts complete and consistent with the brief (MET — all four artifacts landed; this plan is the last one).

### Non-goals carried forward (brief §6 — do not drift)

NG1 no weakening of Operator/Owner gates · NG2 no fake sandbox claims ·
NG3 no unauthenticated/public operational-data exposure · NG4 no multi-tenant/
SaaS · NG5 adopt (don't reinvent) upstream isolated worktrees · NG6 no scope
explosion.

## 4. Milestone detail

### 4.1 M0 — Mission Control (hermes-dev, ~7–10 engineer-days per design §11)

The design (t_0100037c) specifies this fully. Sequencing inside M0
(design §10.1):

1. **Foundation** — `operator_mission.py` skeleton: envelope builder, `_default_hermes_root`, audit-on-call, error envelopes, bounded-output helper, redaction helpers (prompt→`{prompt_len, prompt_sha256}`, truncate). Reuses `operator_policy`.
2. **Cheap surfaces** — `health`, `cron`, `fleet`, `audit` (reuse existing `hermes_operator_*` wrappers; lowest risk).
3. **Sensitive surfaces** — `profiles`, `delegations`, `failures`, `approvals` (expensive reads + highest redaction; inventory G4/G6/G7).
4. **Conditional surfaces** — `codex` (G1/G8), `vault`, `usage`.
5. **Overview** — compose all surfaces into `hermes_mission_overview`; enforce §8.4 size caps; add TTL cache (§8.2).
6. **server.py registration** + `HERMES_GPT_MISSION_ALLOWED_SURFACES` allowlist + docs.

Hard constraints (from risk review P0-1..P0-3, design D2/D5/D7):
- Read-only by construction: all SQLite opened `file:...?mode=ro`; no write/dry-run/apply args; no mutating shell calls.
- **No raw bodies** — no message, memory, transcript, request-dump, or profile-secret content ever crosses the surface; view-model is summaries/aggregates only.
- **No secrets/tokens** — auth.json, .env, a2a/MCP tokens, `hermes status` API keys, Vault secrets never in the view model.
- AuthN at the edge (VPN/Tailscale/private tunnel), authZ in the sidecar (operator level `read_only` + per-surface allowlist, D11/D12).
- Every mission call audited (D10).
- Conditional surfaces report `available:false + reason` rather than failing (D9).

M0 deliverable location: `operator_mission.py`, `test_operator_mission.py`, updated `server.py`, docs update.

### 4.2 M1 — Outcome / Work Contracts (hermes-dev)

**Requires a new design artifact** (brief §2.2; the current design doc covers M0 only). The M1 design must specify:
- contract schema (objective, assigned agent/profile, allowed scope, forbidden actions, expected artifacts, tests, review requirements, completion criteria — brief §2.2);
- a validator that checks completion against **observed** Mission Control state (run/outcome/artifacts) — not the worker's self-report (S2);
- reuse of the existing authority, policy, dry-run, audit, fleet work-order, and safety primitives (brief §2.2, constraint).

M1 exit: contract validation demonstrably rejects a false "done" claim.

### 4.3 M2 — Swarm Orchestration (hermes-dev)

**Requires a new design artifact** (brief §2.3). The M2 design must specify:
- a workflow engine that runs the canonical shape research → architecture → parallel implementation/tests/docs → integration review → Codex review → acceptance validation → human approval;
- **adoption (not reinvention)** of upstream Hermes isolated-worktree support (NG5) for delegated subagents;
- bounded parallelism, clear ownership, safe handoffs, verifiable completion (brief §2.3) — not "more agents for the sake of agents";
- Codex integration keeps its fixed-argv, `shell=False`, bounded-timeout, approved-working-directory posture (brief constraint).

M2 exit: S3 end-to-end workflow completes with handoffs tracked.

### 4.4 M3 — Integration, hardening, docs

- Integration review across M0–M2; verify success criteria S1–S4 from the real surface.
- Security/redaction test suite green (risk review §6 cross-cutting control 2 — a **release blocker**).
- **Retention policy** for request dumps (G9) and Codex transcripts (G8): default + hermes-dev decide owner and window (risk review §8). **Gate: retention policy documented before release.**
- Docs: README/operator-mode update, allowlist config, ChatGPT deployment note.

### 4.5 Legal / compliance workstream (legal) — runs across the release

This is a **parallel, gating** workstream, not a milestone. It owns the ESCALATE
items from the risk review (§9) and must clear them before the relevant gates:

1. **Jurisdiction / applicable privacy regime** (ESCALATE — counsel): determines which privacy duties apply to surfaced data (risk review §3, §9.1).
2. **OpenAI/ChatGPT third-party processing terms** — not yet inspected (risk review §9.2). Verify current terms before any data reaches ChatGPT.
3. **Third-party PII determination** — is any surfaced data third-party personal data requiring notice/consent vs. operator's-own (risk review §9.3)?
4. **Breach-notification duties** if a MC compromise exposes personal data (risk review §9.5).
5. **Future third-party client DPA/confidentiality** — conditional, only if an external client is added (P2-3; not in v0.6 unless Tony adds one).

**Legal does not render legal advice or bind Tony** (risk review Notice). Its
role: package the counsel packet, re-verify jurisdiction/terms, and hold the
ESCALATE gates. **ESCALATE items 1–3 are release-gating for transmitting data
to ChatGPT (risk review §9).**

## 5. Dependency graph

```
Planning (brief*→inventory→design→risk→plan)   ← G1: plan approved
        │
        ▼
       M0  Mission Control (hermes-dev)          ← G2: M0 design/security review (Tony)
        │
        ├────────────────────────────┐
        ▼                            ▼
       M1  Work Contracts            M2  Swarm Orchestration
       (new design → G3)            (new design → G4)
        │                            │
        └──────────────┬─────────────┘
                       ▼
                     M3  Integration/hardening/docs (+ retention policy)
                       │
                       ▼
                   RELEASE                              ← G5: Tony approval (release + outbound)
```

- **M0 → M1 → M2** serial (each builds on the prior).
- **M1 and M2** are parallel to each other *only after M0* (their designs can be drafted in parallel once M0 lands, but their implementations both consume M0's view-model). Practical path: draft M1 + M2 designs in parallel after M0; implement M2 after M1's contract engine (M2 runs on contracts).
- **Legal workstream** is a cross-cutting dependency feeding G2 (M0), G3/G4 (M1/M2), and G5 (release). ESCALATE items 1–3 block any live-ChatGPT data transmission regardless of milestone.
- **Gates block promotion, not work.** Work within a milestone proceeds to the edge of its gate; the gate must clear before its deliverable is used by the next milestone or exposed live.

## 6. Build / test / review / rollout stages

For every milestone, `default` enforces this stage ladder (mirrors how Hermes
GPT already ships verified code):

| Stage | What happens | Owner | Gate out |
|---|---|---|---|
| **Build** | Implement the milestone's deliverable on a feature branch (new branch off `sop/fleet-control-plane`; do not commit directly to main) | hermes-dev | Code compiles, self-review done |
| **Test** | Run the milestone's test suite. M0: `test_operator_mission.py` (~10 cases, design §10.4) on a temp `hermes_root` fixture — never production data | hermes-dev | All tests green |
| **Independent review** | `default` (or a review lane) reviews the diff against the design + risk constraints: redaction, no-raw-body, read-only guarantee, audit-on-call, allowlist enforcement | default | Findings resolved |
| **Gate** | Milestone's Tony gate (G2/G3/G4) cleared for anything that will touch live data or proceed to a dependent milestone | Tony | Approval recorded |
| **Integration** | Merge into `sop/fleet-control-plane`; verify success criteria from the real surface (mode=ro) | default | S1–S4 demonstrable |
| **Rollout (release only)** | Deploy to the live ChatGPT path; enable outbound-facing surfaces; any public/outbound action | default | **G5 — Tony approval** |

Rules:
- Never open a PR / merge untested. Verified code only (Tony's standing
  expectation).
- Tests run on fixtures; live verification is read-only (`mode=ro`).
- Every integration is verified from the real target surface by `default`, not
  taken on the worker's word.

## 8. Risks and mitigations

| ID | Risk | Level | Mitigation / owner | Gate |
|---|---|---|---|---|
| R1 | Sensitive data exposure via Mission Control (messages, transcripts, memory, tokens) | **Critical** | No-raw-bodies + secret-redaction + per-surface allowlist (risk P0-1..P0-3); mandatory redaction test is a release blocker | G2, G5 |
| R2 | "Trusted client" auth insufficient → compromise inherits everything | **Critical** | AuthN at edge + authZ in sidecar (D11/D12); deny-by-default per surface; read-access audit (risk T1) | G2 |
| R3 | OpenAI/ChatGPT third-party processing terms unknown + jurisdiction unestablished | **Critical (ESCALATE)** | Legal verifies terms + packages counsel packet before any data reaches ChatGPT (risk P0-4) | G5 (ESCALATE items 1–3) |
| R4 | Contract satisfaction trusts worker self-report (S2 fails) | **High** | M1 validator checks observed Mission Control run/outcome/artifacts, not claims | G3 |
| R5 | Swarm orchestration becomes "more agents for its own sake"; unbounded parallelism | **High** | Bounded parallelism + ownership/handoff tracking; adopt upstream worktrees (NG5); M2 design review | G4 |
| R6 | M1/M2 scope creep / missing designs block release | **Medium** | New M1/M2 design artifacts required before dispatch; scope held by brief non-goals; default gates | G3, G4 |
| R7 | Mission Control performance / context blowup (overview too big for ChatGPT) | **Medium** | §8.4 size caps (64KB/128KB overview; ≤~16k tokens); TTL cache; truncation with `count_total` | M0 review |
| R8 | Fragmentary sources (G1/G2/G4/G5) cause wrong/missing data | **Medium** | `available:false + reason` (D9); conditional surfaces; cross-board + per-profile aggregation (G3/G7) | M0 review |
| R9 | Read access not auditable → incident can't be reconstructed | **Medium** | Audit every mission call (D10); read-access logging required before release (risk T5) | G2, G5 |
| R10 | Retention gap: request dumps (G9) + Codex transcripts (G8) linger | **Medium** | Exclusion from data model + documented retention window/deletion (risk §8) | M3 (documented before release) |
| R11 | Release/outbound actions taken without approval | **High** | G5 gates all outbound + go-live; no agent posts/publishes/sends without Tony | G5 |
