## 2. Assessment of the five new M2 surfaces

### 2.1 Workflow status view-model (§9) — **consistent**

Swarm status flows through the M0 Mission Control contract layer (D-SW11, §9). The design explicitly reuses M0's bounded envelopes (`available`/`unavailable`, size caps) and redaction (`redact_output`), and states "no raw bodies — consistent with M0/P0-1/P1-1." Status fields are metadata/summary only (workflow_id, title, status, stage_count, stages_done, parallel_active, current_owners, awaiting, trace_id). This stays within P0-1 (no raw bodies) and P0-3 (authZ/redaction via M0).

**No finding.** The design does not open a parallel status channel or a new raw-body read.

### 2.2 Worktree retention (§7/§9) — **consistent**

Implementation stages use upstream kanban worktrees (NG5, D-SW2); the engine records a retention note so `default` can clean up after the milestone/release gate (§7, Q9). This is aligned with risk review §8 retention for transient work artifacts (worktrees here are transient code/review artifacts, not the §8 request-dump/transcript diagnostic data). The engine does not hand-roll tree management, and no stage writes outside its own worktree until the integration-merge stage — consistent with the "no direct commit to main" rule.

**No finding.** Retention of worktrees is delegated to the release gate, matching §8. See P2-2 for the Codex-artifact counterpart.

### 2.3 Codex review stage (§8) — **consistent, no posture regression**

The design drives the **existing** runner unchanged (D-SW7): fixed-argv, `shell=False`, bounded timeout `[10,3600]`, approved working directory (`require_workspace_path` on the integration worktree). Verified in code (§1). The engine reads only the `--json --ephemeral` **verdict** from observed state; it never reads or surfaces raw rollout transcripts. This is consistent with the M0 risk-review G8 finding (Codex CLI transcripts are High/ESCALATE, excluded from any v0.6 surface) and P1-3.

**No regression.** The Codex transcript exclusion is preserved; M2 adds a bounded verdict-JSON read, not a transcript read. See P2-1 on what the verdict JSON must not carry.

### 2.4 Mutation surfaces (§10, D-SW9/D-SW12) — **consistent, NG1/NG3 preserved**

All `hermes_swarm_*` mutations (`workflow_create`, `stage_dispatch`, `stage_advance`, `approve`) are operator-gated: `workspace`+ and direct mode + `confirm`, dry-run-first (D-SW9, verified `effective_dry_run`/`require_mutation`), and every action audited (D-SW10, `audit_record`). `approve` additionally requires `owner` level + direct (`require_owner`, D-SW8). No mutation exists from Mission Control (D-SW12) — the M0 view-model stays read-only, consistent with P1-1. There is no new public/unauthenticated surface (NG3 preserved; status reads only via M0).

**No finding.** NG1 (Operator/Owner gates) and NG3 (no public exposure) are not weakened.

### 2.5 Human approval gate (D-SW8) — **consistent**

The final stage is a real gate: it waits on `hermes_swarm_approve` (owner level, direct mode, audit) and the engine never auto-advances past it (S3/S4). Workflows surface `awaiting_approval` **view-only** via M0; the actionable approval is a swarm mutation tool, not an M0 surface — exactly matching P1-1 (approvals view-only from MC) and S3/S4.

**No finding.**

## 3. Relationship to the M0 risk-review findings

M2 introduces no new data-exposure surface, no raw-body read, no secret path, and no mutation from Mission Control. It therefore does not add to, or alter, the P0/P1 findings of the M0 risk review:

- **P0-1 / P0-3** (no raw bodies; authZ/redaction) — preserved by D-SW11/D-SW12 and reuse of the M0 redaction layer.
- **P1-1** (approvals view-only) — preserved by D-SW8 + M0 view-only surfacing.
- **P1-3** (Codex transcripts + request dumps excluded; retention set) — preserved by the verdict-JSON-only read; see P2-2 for the retention counterpart.
- **P0-4 / ESCALATE §9** (jurisdiction, OpenAI terms, third-party PII) — **unchanged and still open.** M2 status data flows to ChatGPT only via the M0 surface, so these remain release-gating for the M0→ChatGPT path (G2/G5), not new gates introduced by M2. They do not block G4.

## 4. Findings (P2 — conditions of approval, bind into M2 implementation)

| # | Priority | Finding | Design hook | Condition |
|---|---|---|---|---|
| P2-1 | **Moderate** | The Codex review **verdict JSON** M2 reads from observed state must itself be treated as bounded/summarized — it must not carry raw transcript or prompt text (only pass/fail verdict, stage/commit refs, structured findings), and must pass through the M0 redaction layer like any other surface. | §8 verdict-JSON read; D-SW11 | Implement the verdict read through `redact_output`/bounded envelope; assert no raw transcript/prompt fields in the verdict schema. Release-blocker only if a transcript field leaks — prevent by schema, not by testing. |
| P2-2 | **Moderate** | M2 generates **new transient artifacts** (integration worktree, Codex verdict/transcript files). The risk-review §8 retention window is currently defined only for request dumps (G9) and Codex transcripts (G8). | §7 retention note; Q9 | Extend §8 retention to cover M2-generated worktrees and any Codex transcript/verdict files; `default` confirms the cleanup owner/window at G5. Tied to P1-3's existing retention gate. |
| P2-3 | **Low–Moderate** | Q5 (optional Codex-as-implementation-owner with `workspace-write`) is a **future write path** currently off by default in the canonical shape. If adopted, it adds a `workspace-write` stage that must be re-reviewed before use. | Q5; §8 optional steering | Do not enable Codex implementation-owner stages in the M2 canonical shape; if added later, re-flag to risk review before enabling (the design already commits to this). |

These are conditions of approval, not blockers: the canonical M2 shape as designed is safe to implement. P2-1 and P2-2 must be honored in the M2 implementation and the G5 retention policy respectively.
