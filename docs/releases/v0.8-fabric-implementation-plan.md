# Hermes GPT v0.8 Fabric Implementation Plan

- Status: IN PROGRESS, G2 planning only
- Program: #27
- Architecture gate: #29
- Security gate: #30
- Implementation issues: #32, #33, #34, #35
- Integration gate: #36
- Live acceptance gate: #37

**No G4 implementation slice is authorized until G2 closes and G3 passes.**

## 1. Delivery strategy

Build Fabric as four isolated slices behind one architecture/security contract, then integrate and prove it on real machines.

The order protects the trust boundary:

1. define protocol/state/authority/evidence architecture;
2. adversarially review it;
3. implement remote execution and proof transport;
4. implement placement;
5. implement durable artifact/recovery semantics;
6. expose bounded visibility;
7. integrate all slices;
8. run two-machine acceptance;
9. require human ship approval.

## 3. Security gate: G3 / #30

Architecture is attacked before production code starts.

Minimum threat cases:

- arbitrary URL/token injection;
- peer identity spoof/drift;
- authority envelope widening;
- remote runner/sandbox escalation;
- remote self-certification;
- duplicate submit after timeout;
- stale capability placement;
- workspace/path escape;
- secret artifact export;
- artifact hash/size substitution;
- arbitrary artifact URL/SSRF;
- cancel/retry race;
- coordinator restart ownership loss;
- peer restart/task-store loss;
- evidence cross-task replay;
- router soft-score safety bypass;
- Flight Deck mutation bypass;
- protocol/version downgrade or mismatch.

Exit: no unresolved CRITICAL/HIGH trust-boundary finding.

## 4. G4-A / #32: Remote dispatch + evidence transport

### Goal

Make one existing Work Contract stage execute through a managed remote Fabric peer while preserving coordinator authority and validation ownership.

### Expected implementation areas

Names are architecture-dependent and not yet final:

- Fabric schema/model module;
- managed-node registry adapter;
- coordinator dispatch journal;
- A2A Fabric DispatchAdapter;
- deterministic peer Fabric acceptor;
- peer attempt journal;
- remote evidence builder/provider;
- Work Contract observed-evidence integration;
- audit/event hooks.

### Required behavior

- registry-only target resolution;
- live identity verification;
- deterministic envelope validation;
- stable dispatch/per-attempt identity;
- peer durable accept-before-write;
- bounded submit/poll/recover/cancel/collect primitives;
- timeout-after-submit recovery;
- evidence lineage validation;
- coordinator-owned final Work Contract verdict.

### Required focused tests

- happy-path remote read-only;
- happy-path authorized remote write;
- malformed/version-invalid envelope;
- unauthorized profile/class;
- remote self-certification ignored;
- timeout after successful submit;
- duplicate identical replay;
- conflicting duplicate identity;
- coordinator restart journal reload;
- peer restart journal reload;
- missing peer journal blocks safely;
- malformed/wrong-lineage evidence.

### Slice exit

A named managed peer can execute a bounded stage and return admissible observations without being able to certify itself or exceed contract authority.

## 5. G4-B / #33: Node capabilities + automatic execution router

### Goal

Support `execution.backend=auto` or the final equivalent by choosing only among eligible local/remote execution targets.

### Expected implementation areas

- capability schema;
- capability probe/cache;
- provenance/freshness model;
- eligibility engine;
- deterministic ranker;
- placement explanation model;
- contract execution normalization update;
- bounded node/placement read APIs.

### Required hard filters

- registry/identity;
- protocol compatibility;
- freshness/health;
- authorization/profile;
- runner/provider/model allowlists;
- tools/browser/vision/GPU;
- workspace mapping;
- confinement posture;
- artifact support;
- concurrency;
- forbidden/public/high-impact policy.

### Required soft ranking

Only after eligibility:

- locality/artifact affinity;
- load/capacity;
- recent latency;
- hardware/model/tool fit;
- optional grounded cost;
- stable deterministic tie-break.

### Required tests

- every hard exclusion independently;
- combinations of exclusions;
- stale/unknown positive facts;
- deterministic ties;
- explicit override still filtered;
- no-candidate result;
- router explanation redaction;
- soft score cannot resurrect excluded candidate;
- conversational A2A `best` is never used as scheduler policy.

### Slice exit

A contract can state bounded execution requirements and Hermes GPT can safely explain and select an eligible local/remote backend without changing ownership or authority.

## 6. G4-C / #34: Artifacts + restart/cancel reconciliation

### Goal

Make distributed execution operationally survivable and artifact-safe.

### Expected implementation areas

- remote artifact manifest;
- peer export/transfer binding;
- coordinator artifact admission;
- hash/size/type verification;
- denied path/special-file controls;
- distributed reconcile engine;
- attempt-specific cancellation;
- write ownership/lease-or-epoch mechanism;
- recovery state/reason codes.

### Required behavior

- safe logical artifact names;
- no client-facing remote absolute paths;
- bounded transfer;
- SHA-256 verification;
- secret/path protections on producer and consumer sides;
- no arbitrary artifact URL fetch by default;
- coordinator restart reconciliation;
- peer restart reconciliation independent of ephemeral A2A task store;
- idempotent cancel;
- cancel/completion race handling;
- no automatic second write attempt while prior attempt may still mutate.

### Required tests

- valid artifact;
- hash mismatch;
- oversize;
- traversal;
- symlink escape;
- special files;
- denied secret source;
- unsafe URL/SSRF attempt;
- coordinator restart during running stage;
- peer restart/lost A2A task record;
- cancel race;
- retry race;
- irreconcilable write becomes blocked/human escalation.

### Slice exit

Fabric can lose transport/process continuity and still recover to an explainable safe state with verifiable artifact lineage and no silent duplicate write.

## 7. G4-D / #35: Flight Deck distributed visibility

### Goal

Make Fabric inspectable without adding authority.

### Required read models

- managed nodes;
- identity/health/freshness;
- capability summary;
- active load/capacity;
- stage placement local/remote;
- explicit vs auto placement;
- placement explanation/exclusions;
- dispatch/attempt/remote-task identities;
- remote operational state;
- authority/scope summary;
- evidence/artifact summary;
- timeout/reconcile/cancel ambiguity;
- blocked reason.

### Mutation rule

Any stop/retry/reassign/cancel control continues through existing gated `hermes_*` operator tools/actions. No browser-only remote mutation path.

### Streaming scope

A2A subscriptions/push may be used as an optimization if architecture permits. Generic Flight Deck push infrastructure is not required for v0.8 correctness.

### Required tests

- redaction;
- stale/ambiguous rendering;
- placement explanation accuracy;
- node identity display is non-secret;
- authority summary reflects contract/local policy;
- UI mutation adapter cannot bypass existing gates.

### Slice exit

An operator can answer where a stage runs, why it was placed there, what it may do, what evidence exists, and exactly why it is blocked.

## 11. Branch/PR discipline

Recommended:

- G2 architecture branch: `v0.8-fabric-architecture`;
- each G4 slice uses a focused feature branch/PR from the accepted architecture/security baseline;
- do not combine unrelated slice implementation in one PR merely to reduce PR count;
- implementation PRs must identify accepted ADRs and risks they satisfy;
- timeout/recovery/security fixes discovered during a slice stay with the owning slice unless they require an architecture change;
- architecture-changing findings return to #29/#30 rather than being silently improvised in code.
