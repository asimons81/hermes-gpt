## 1. Purpose

This document is the technical design for the **Swarm Orchestration** capability
of Hermes GPT v0.6: a workflow engine that runs a canonical multi-stage agent
workflow — **research → architecture → parallel implementation/tests/docs →
integration review → Codex review → acceptance validation → human approval** —
across Hermes profiles, delegated Hermes agents, isolated Git worktrees, and
Codex.

It is the design task referenced in the brief (`docs/releases/v0.6-brief.md`
§2.3) and consumed by the risk review (legal) and the integrated release plan
(default). It **does not** re-design Mission Control (M0) or Work Contracts (M1);
it **consumes** them:

- **M0 view-model** — Swarm reads observed run/outcome/artifact state from
  Mission Control's contract layer to answer "is work actually done".
- **M1 contract engine** — every workflow stage is a **contract**. Stage
  completion is validated against **observed** Mission Control state, not the
  worker's self-report (success criterion S2/S3).

The design's core promise (from the brief): reliable decomposition, bounded
parallelism, clear ownership, safe handoffs, and verifiable completion — **not**
"more agents for the sake of agents".

**Acceptance (from the card):** a fresh engineer can estimate and implement
from this design without needing to re-interview the requester.

## 2. Design goals and non-goals

### Goals

- **G-SW1.** Run the canonical workflow shape end-to-end with ownership and
  handoffs tracked at every stage (success criterion S3).
- **G-SW2.** **Adopt (not reinvent)** upstream Hermes isolated-worktree support
  (NG5) for every delegated implementation stage — each worker works in its own
  Git worktree on its own branch, so parallel writers never collide.
- **G-SW3.** Bound parallelism explicitly: a per-workflow and per-board concurrency
  cap, a fan-in/fan-out model, and a scheduler that advances a stage only when
  its dependencies are satisfied **and** capacity exists.
- **G-SW4.** Give every stage exactly one owner (profile/agent) and record each
  handoff (who → whom, artifact ref, contract verdict) durably.
- **G-SW5.** Make completion **verifiable**: the engine runs the M1 contract
  validator against observed Mission Control state before promoting any stage —
  a false "done" claim is returned for rework, never trusted (R4/S2).
- **G-SW6.** Keep Codex integration on its existing posture: fixed-argv,
  `shell=False`, bounded-timeout, approved-working-directory (brief constraint).
- **G-SW7.** Reuse the existing operator layer (policy, audit, dry-run, fleet
  work-order, Codex runner, workspace/git helpers) rather than a parallel
  subsystem.
- **G-SW8.** Preserve every existing safety gate: dry-run-first mutation, human
  approval where consequence warrants (final stage), no weakening of
  Operator/Owner gates (NG1).

### Non-goals (this design)

- **NG-SW1.** No new agent runtime. Swarm coordinates existing agents/processes
  (Hermes profiles, delegated Hermes agents, Codex); it does not spawn or embed
  a new agent engine.
- **NG-SW2.** No reinvention of upstream worktrees (NG5). Worktree lifecycle is
  delegated to upstream kanban/project support; Swarm supplies the workflow
  policy on top.
- **NG-SW3.** No fake sandbox claims (NG2). Codex runs in its declared sandbox
  (`read-only`/`workspace-write`); Swarm reports the sandbox actually used and
  never claims isolation that does not exist.
- **NG-SW4.** No unauthenticated/public exposure (NG3). Swarm mutation tools are
  operator-level and gated exactly as today; workflow status is readable via
  Mission Control, not a new public surface.
- **NG-SW5.** No multi-tenant/SaaS (NG4). Single operator (Tony), single fleet.
- **NG-SW6.** No unbounded fan-out. Every workflow has a hard stage count and a
  concurrency cap; the engine refuses to schedule beyond them.
- **NG-SW7.** Not a UI. The engine is a programmatic + MCP surface; any dashboard
  is out of scope (consistent with M0 NG-MC5).
- **NG-SW8.** No scope explosion (NG6). Approval-inbox action, richer Codex
  steering, event timelines, and checkpointing are included only where required
  by the canonical shape; everything else is deferred (see §11).

## 3. Context: what exists today

### 3.1 The operator surface M2 builds on

`hermes-gpt` is a standalone FastMCP sidecar (`server.py`). Relevant existing
machinery (all reused, none replaced):

| Building block | Module | What M2 uses |
|---|---|---|
| Policy / levels / apply / dry-run / audit / redaction / error envelopes | `operator_policy.py` | Every swarm mutation gates on level + `effective_dry_run` + `require_mutation`; every action audited |
| Fleet work-order envelope + authority manifest | `operator_fleet.py` | The **contract envelope shape** (`hermes.fleet.work-order/v1`) and the peer-authority model M1 extends |
| Codex runner | `operator_codex.py` | The **Codex integration** — fixed-argv, `shell=False`, bounded timeout, approved workdir (§8) |
| Workspace / git helpers | `operator_workspace.py` | `hermes_git_status`/`hermes_git_diff`; worktree read/verify posture; owner-mode catastrophic guards |
| Mission Control view-model | `operator_mission.py` (M0) | The **observed-state source** the validator reads |
| Work Contracts validator | M1 (new design) | The **completion gate** M2 drives |

### 3.2 The authority / dispatch model today

- Operator levels: `read_only` → `cron` → `skills` → `skills_config` →
  `workspace` → `owner`. Mutation requires `workspace`+ and direct apply mode
  (`dry_run=False`, `confirm`).
- Fleet dispatch is **work-order-shaped** already: `hermes_fleet_dispatch_work_order`
  builds a canonical envelope (`agent`, `task_id`, `target_profile`, `objective`,
  `workspace`, `inputs`, `constraints`, `acceptance_checks`, `deliverables`,
  `authorization`), enforces an **authority manifest** (per-peer allowed profiles,
  max authorization class, forbidden action patterns incl. raw-secret / vault-policy
  / fleet-policy / public-action), verifies the live peer, then submits over A2A.
- Every operator action is written to `logs/hermes_gpt_operator_audit.jsonl`
  (tool/level/apply_mode/dry_run/changed/success/error/summary/trace_id).
- Owner Mode adds catastrophic-pattern + secret-path guards; denied paths (`.env`,
  `auth.json`, `vault/`, `mcp-tokens/`, `.ssh/`, `.aws/`) are never readable/writable
  through the surface.

### 3.3 Codex integration posture (brief constraint, must be preserved)

`operator_codex.py` already hard-codes:

- `shell=False` everywhere (`subprocess.Popen`/`run` with an argv list; never a
  shell string).
- **Fixed argv**: `codex exec [--json --ephemeral -C <workdir> -s <sandbox>]
  [--model <m>] [-c mcp_servers={}] <prompt>`; review mode uses
  `codex exec review --json --ephemeral {--uncommitted|--base <b>|--commit <sha>}`.
  Model identifiers and review targets are regex-validated (no flags/whitespace
  injection).
- **Bounded timeout**: clamped to `[MIN_TIMEOUT=10, MAX_TIMEOUT=3600]`; a watch
  thread kills the process on timeout → status `timed_out`.
- **Approved working directory**: `require_workspace_path(workdir)` — the workdir
  must be under the operator allowlist; sandbox is validated (`read-only` |
  `workspace-write`); workspace-write additionally requires
  `HERMES_GPT_ALLOW_CODEX_WRITE=1`.
- Launcher resolution (including the WindowsApps-shim protection) and `--version`
  probe are already hardened in `resolve_codex_exe`.

**M2 does not change any of this.** The swarm engine drives the existing runner
with the workflow's worktree as the `workdir`; it does not bypass policy.

### 3.4 Upstream isolated-worktree support (NG5 — adopt, don't reinvent)

Upstream Hermes Agent kanban supports **isolated Git worktrees for delegated
subagents** (inspected in `hermes_cli/kanban.py`, `hermes_cli/kanban_db.py`):

- `--workspace worktree` (or a project-linked task) gives a task its own worktree.
- Project-linked tasks anchor under the project's **primary repo** as
  `<repo>/.worktrees/<task-id>` with a **deterministic branch**
  `<project-slug>/<task-id>`; a plain `worktree` task uses a random branch
  `wt/<task-id>`.
- The dispatcher materializes the worktree (`git worktree add`) before the worker
  starts; the worker works inside it; only `scratch` workspaces are auto-removed,
  worktree/dir workspaces persist for review.
- This is the mechanism the brief points to (NG5): **adopt it** so each
  implementation stage gets a real, separate Git worktree and branch, and the
  engine never hand-rolls its own tree management.

**M2 design decision:** every Swarm implementation stage is dispatched as a
kanban task with `workspace_kind=worktree` anchored to the target project's repo.
The engine sets the stage's `workdir` to that worktree and (for Codex stages)
passes it to the Codex runner's approved-workdir gate. The engine does **not**
create branches or manage trees itself.

## 4. Design overview

### 4.1 Shape of the surface

Swarm Orchestration is delivered as:

1. **A workflow definition** — a declarative, validated DAG of stages that encode
   the canonical shape (§5). Defined once as a typed structure, not ad-hoc code.
2. **A workflow engine** (`operator_swarm.py`, new module) — schedules stages,
   dispatches each as a **contract** (M1), enforces the concurrency bound and the
   DAG order, validates completion from **observed** state (M0 view-model), records
   handoffs, and drives the human-approval gate.
3. **A set of MCP tools** (namespace `hermes_swarm_*`) on `server.py` —
   create/inspect/list/validate a workflow, and the mutating dispatch/approve
   tools that reuse the operator gates (dry-run-first, direct-mode, audit).

Three layers mirror M0:

```
                            ┌──────────────────────────────┐
                            │       Trusted client        │
                            │   (ChatGPT via MCP today)   │
                            └──────────────┬───────────────┘
                                           │ MCP (streamable-http / sse)
                                           ▼
┌───────────────────────────────────────────────────────────────────┐
│                    hermes-gpt MCP sidecar                           │
│  server.py  register_tools() → hermes_swarm_* tools               │
│   ├── operator_level / allowed_profiles / apply-model gate        │
│   ├── audit_record() on every swarm action                        │
│   └── dry-run-first mutation (effective_dry_run)                   │
└──────────────────────┬────────────────────────────────────────────┘
                       │
                       ▼
┌───────────────────────────────────────────────────────────────────┐
│  operator_swarm.py  (NEW)  — workflow engine                       │
│   • workflow defs (canonical shape) + stage DAG                    │
│   • scheduler: fan-in/fan-out + concurrency caps                   │
│   • dispatch each stage as an M1 contract                          │
│   • validate completion from M0 observed state                     │
│   • record ownership + handoffs; drive approval gate               │
└───────┬──────────────────┬───────────────────┬────────────────────┘
        │                  │                   │
        ▼                  ▼                   ▼
┌────────────────┐  ┌──────────────────┐  ┌─────────────────────────┐
│ M1 contract    │  │ M0 view-model    │  │ operator_* (existing)   │
│ engine (valid. │  │ (operator_mission)│ │ fleet work-orders,      │

│ observed state)│  │ outcome/artifacts│  │ git, upstream kanban    │
```

### 4.2 Tools

| Tool | Kind | Level required | Returns |
|---|---|---|---|
| `hermes_swarm_workflow_create` | mutation | `workspace` + direct | Register a workflow instance; returns `workflow_id` + stage plan (dry-run first) |
| `hermes_swarm_workflow_list` | read-only | `read_only` | Workflow instances + status (from observed state) |
| `hermes_swarm_workflow_status` | read-only | `read_only` | One workflow's stage map, owners, handoffs, verdicts |
| `hermes_swarm_workflow_validate` | read-only | `read_only` | Validate a proposed workflow DAG against the engine's rules (shape, caps, contracts) |
| `hermes_swarm_stage_dispatch` | mutation | `workspace` + direct | Dispatch one ready stage (or the workflow's next fan-out) as an M1 contract |
| `hermes_swarm_stage_advance` | mutation | `workspace` + direct | After a stage validates, promote to next stage(s); records the handoff |
| `hermes_swarm_approve` | mutation | `owner` + direct | Record the final human approval (the last stage gate) |

Read-only swarm status flows through the **Mission Control surface** (M0) so a
client can see the fleet's workflows in the same bounded overview — the swarm
engine writes its run/outcome/artifact state to the observed stores the M0
view-model reads; it does not open a parallel status channel.

### 4.3 Design decisions (binding)

| # | Decision |
|---|---|
| D-SW1 | **Workflows are DAGs of contracts.** Every stage is an M1 contract; the workflow is the ordering + handoff policy on top. No stage runs outside a contract. |
| D-SW2 | **Adopt upstream worktrees (NG5).** Implementation stages run in a kanban worktree (`<repo>/.worktrees/<task-id>` on `<slug>/<task-id>`). The engine never manages git itself. |
| D-SW3 | **Bounded parallelism.** One `max_parallel` per workflow (default 3) and one per board (default 4), plus a global stage cap per workflow (default 12). The scheduler refuses over-capacity. |
| D-SW4 | **Exactly-one owner per stage.** `owner` (profile or agent) is required and immutable per stage; the engine records it at dispatch and at every handoff. |
| D-SW5 | **Safe handoffs.** A stage's branch/worktree + artifacts are frozen and validated before the next stage is dispatched; the handoff record lists `from`, `to`, `artifact_refs`, `contract_verdict`. |
| D-SW6 | **Verifiable completion.** Stage promotion runs the M1 validator against **observed** Mission Control state (run/outcome/artifacts). A false "done" returns the stage for rework; it is never trusted (R4/S2). |
| D-SW7 | **Codex keeps its posture.** Swarm drives `operator_codex` unchanged: fixed-argv, `shell=False`, bounded-timeout, approved-workdir. The worktree is the approved workdir. |
| D-SW8 | **Human approval is a real gate.** The final stage waits on `hermes_swarm_approve` (owner level, direct mode, audit). The engine never auto-advances past it (S3/S4). |
| D-SW9 | **Dry-run-first mutation.** Every mutating swarm tool returns a plan at `dry_run=True` (default) and requires `confirm` + direct mode to execute — identical to existing operator mutation. |
| D-SW10 | **Every swarm action is audited** via `op_policy.audit_record` (tool, workflow_id, stage, owner, apply_mode, dry_run, changed, verdict). |
| D-SW11 | **Reads are read-only and bounded.** Status views go through M0's bounded envelopes (`available`/`unavailable`, size caps); no raw bodies. |
| D-SW12 | **No mutation from Mission Control.** Swarm mutations live only in the `hermes_swarm_*` tool namespace under operator gates; M0 view-model stays read-only (consistency with M0/P1-1). |

## 5. Architecture

### 5.1 The workflow model (canonical shape)

The canonical shape is a **directed acyclic graph (DAG)** of stages. The engine
ships the default shape from the brief and plan as a template, but the engine is
DAG-generic so a validated workflow may reuse subsets or add a bounded number of
scoped stages (subject to NG-SW6 and D-SW3 caps).

```
[research] ──▶ [architecture] ──▶ ┌───────────────────────────────┐
                                   │ parallel stage group:        │
                                   │  [implementation][tests][docs]│
                                   │  (bounded parallelism)       │
                                   └───────────────┬───────────────┘
                                                   ▼
                                   [integration review]
                                                   ▼
                                   [Codex review]   (hermes_codex_review_start)
                                                   ▼
                                   [acceptance validation]
                                                   ▼
                                   [HUMAN APPROVAL]  ──▶ DONE
```

Stage semantics:

| Stage | Kind | Owner | Gate out | Artifact expected |
|---|---|---|---|---|
| research | single | hermes-researcher | evidence doc committed | `docs/…/research` or notes + sources |
| architecture | single | hermes-dev | design doc committed | `docs/design/…` |
| implementation | **parallel** | per-file/profile owner | tests + code in its worktree | code + tests on its branch |
| tests | **parallel** | test owner | test suite green | test artifacts/run |
| docs | **parallel** | docs owner | docs updated | docs |
| integration review | single | reviewer | all parallel branches merged into an integration worktree; conflicts resolved | merged branch + diff |
| Codex review | single | Codex (read-only review) | `codex exec review` verdict on the merged diff | review JSON (`--json --ephemeral`) |
| acceptance validation | single | hermes-dev/verifier | M1 validator passes on observed state | verdict record |
| human approval | single | Tony (owner gate) | `hermes_swarm_approve` recorded | approval record |

### 5.2 Scheduler rules (bounded parallelism)

- A stage is **ready** when all its fan-in parents are `done` (or in the parallel
  group's case, when its group opens and the concurrency cap allows).
- The engine evaluates ready stages; it dispatches at most `min(workflow_cap_remaining,
  board_cap_remaining)` concurrently. Defaults: `max_parallel` per workflow = 3,
  per-board = 4, total stages per workflow = 12.
- The **parallel group** (implementation/tests/docs) is opened only when
  `architecture` is `done`. Group members run in separate worktrees and separate
  branches (NG5), so they never touch each other's files.
- A stage is **blocked** (needs_input) when it fails validation and no auto-rework
  is permitted (see §5.3) — it surfaces on the board as requiring a human, never
  silently retried past a bound.

### 5.3 Completion and rework

- On a stage completing (its worker claims done), the engine runs **D-SW6**
  validation: read the observed run/outcome/artifacts via the M0 view-model and
  evaluate against the stage's M1 contract (artifacts present, tests run, criteria
  met).
- **Pass** → record verdict `satisfied`, freeze the worktree/branch, dispatch the
  next ready stage(s), write the handoff.
- **Fail** → record verdict `returned_for_rework` with the specific unmet
  criterion, and requeue the same stage once (bounded). A second failure sets the
  stage `blocked` for a human. This is the S2 behavior: a false "done" is rejected,
  not trusted.
- Rework is always gated: it does not auto-escalate past the bounded retry, and it
  never weakens operator/owner gates (NG1).

### 5.4 Module layout

```
server.py                          # register hermes_swarm_* tools (one add_tool each)
operator_swarm.py                  # NEW: workflow engine (defs, DAG, scheduler, validation hook, handoffs)
operator_swarm_workflows.py        # optional split: the canonical shape + validated stage DAGs
test_operator_swarm.py             # NEW tests
docs/design/v0.6-swarm-orchestration.md  # THIS DESIGN
```

`operator_swarm.py` follows the existing `operator_*` conventions:
- imports `operator_policy as op` for policy/audit/redaction/error helpers;
- imports the **M1 contract engine** and **M0 view-model** (the concrete hooks are
  the M1 validator + `operator_mission` surface reads);
- every public function returns `str` (JSON), like the other `hermes_*` wrappers;
- every mutating function is dry-run-first and calls `audit_record`.

### 5.5 Building blocks reused

| Capability | Reuse |
|---|---|
| Policy/level/audit/redaction/error envelopes | `operator_policy.py` |
| Work-order/contract envelope + authority model | `operator_fleet.py` (`_canonical_work_order`, `_authorize_order`, authority manifest) |
| Codex runner | `operator_codex.py` (`hermes_codex_start`, `hermes_codex_review_start`) — unchanged |
| Git/worktree read + verify | `operator_workspace.py` (`hermes_git_status`, `hermes_git_diff`), upstream kanban worktree |
| Observed state | M0 `operator_mission` surfaces (M1's validation reads these) |
| Contract validation | M1 contract engine (completion vs observed state) |
| Worktree dispatch | Upstream kanban `workspace_kind=worktree` / project-link (NG5) |

## 6. Contracts for stages

Each stage is dispatched as an M1 contract. The engine builds the contract from
the stage definition + the workflow context. A stage contract carries (per brief
§2.2 and the M1 schema):

- **objective** — the stage's goal (from the workflow DAG).
- **assigned agent/profile** — the stage `owner` (D-SW4).
- **allowed scope** — the worktree path + branch for implementation stages;
  read-only scope for review stages.
- **forbidden actions** — inherited from the authority model: no raw-secret
  requests, no vault/fleet-policy edits, no public actions, no `git add -A` /
  force-push (existing catastrophic guards).
- **expected artifacts** — the files/branch the stage must produce (e.g. the
  research doc, the design doc, the code + tests on the branch).
- **tests** — the verification commands the stage must run (e.g. `pytest`,
  `ruff`) via the workspace `run_test` allowlist or the M1 test harness.
- **review requirements** — which stages must be reviewed (integration, Codex)
  before acceptance.
- **completion criteria** — the M1-validated conditions; the engine checks these
  against **observed** state (§5.3).

The contract **authorization** field follows the existing fleet model: an
authorization class (`read_only` | `reversible_write` | `high_impact`) with
`approved` + `approved_by` + `approval_reference` for high-impact work. Swarm
implementation stages are `reversible_write` (they write only inside their
worktree/branch — reversible by branch discard); nothing is ever `high_impact`
without explicit human approval metadata.

## 7. Worktree lifecycle (adopting NG5)

- **Create:** when a stage that writes code/docs is dispatched, the engine creates
  a kanban task with `workspace_kind=worktree` (project-linked when the workflow is
  anchored to a project, so branch = `<slug>/<task-id>`, path =
  `<repo>/.worktrees/<task-id>`). Upstream materializes the worktree.
- **Work:** the worker/agent operates only inside its worktree. Codex stages pass
  the worktree as the approved `workdir` (D-SW7).
- **Freeze on completion:** once the stage validates, the branch is frozen (no
  further worker writes); its ref + artifact list are recorded in the handoff.
- **Merge on integration:** the integration-review stage merges the parallel
  branches into the integration worktree/branch, resolving conflicts. No stage
  merges into `main` or `sop/fleet-control-plane` directly; only the release/integration
  path does, under the plan's gates (consistent with "do not commit directly to main").
- **Retention:** worktrees persist for review (upstream only auto-removes `scratch`);
  the engine records a retention note in the workflow so `default` can clean them
  after the milestone/release gate (aligned with risk review §8 retention for
  transient work artifacts).

## 8. Codex integration (unchanged posture)

Swarm drives the **existing** Codex runner. Two roles:

1. **Codex review stage** — the engine calls `hermes_codex_review_start` with:
   - `workdir` = the integration worktree (must pass `require_workspace_path`);
   - `target` = the merged branch (`base:<integration-branch>` or `commit:<sha>`),
     or `uncommitted` during in-progress review;
   - sandbox `read-only`, `ignore_user_config`, a bounded `timeout`;
   - the engine reads the `--json --ephemeral` verdict from the job's observed state.
2. **Optional implementation steering** (not required by the canonical shape; used
   only when a stage explicitly names Codex as its owner) — `hermes_codex_start`
   with sandbox `read-only` by default, `workspace-write` only if
   `HERMES_GPT_ALLOW_CODEX_WRITE=1` and the stage authorization permits it.

The fixed-argv, `shell=False`, bounded-timeout (`[10, 3600]` clamp), and
approved-working-directory gates are all inherited from `operator_codex` and are
**not** re-implemented or relaxed by the swarm engine (D-SW7).

## 9. View-model for swarm status (read side)

Swarm status is exposed **through the M0 Mission Control contract layer**, not a
new store. The engine writes its run/outcome/artifact records into the observed
stores M0 already reads (kanban task runs, operator audit), so a client sees
workflow progress in the same bounded envelope:

```
hermes_mission_overview → workflows: {
  "available": true,
  "workflows": [
    {"workflow_id", "title", "status": "running|blocked|done|awaiting_approval",
     "stage_count", "stages_done", "parallel_active",
     "current_owners": ["..."], "awaiting": ["human approval"], "trace_id"}
  ]
}
```

Per-workflow detail (`hermes_swarm_workflow_status`, read-only, via M0 redaction):
each stage's owner, status (`todo|running|validated|returned_for_rework|blocked|done`),
contract verdict, handoffs (`from→to`, `artifact_refs`), and the approval record.
No raw bodies — consistent with M0/P0-1/P1-1.

## 10. Authorization and security boundaries

| Boundary | Enforcement | v0.6 status |
|---|---|---|
| Swarm **read** (status) | Mission Control read-only surface, level `read_only`, M0 authZ/allowlist/redaction | M0 (reused) |
| Swarm **mutation** (create/dispatch/advance/approve) | operator level `workspace`+ and direct mode + `confirm`; `approve` requires `owner` + direct; dry-run-first (D-SW9) | NEW in v0.6 (reuses operator gates) |
| Worktree isolation | upstream kanban worktree; separate branch per stage; no shared-tree writes | NEW (adopt NG5) |
| Codex | existing runner posture (fixed-argv, shell=False, bounded timeout, approved workdir) | Existing |
| Contract authority | authority manifest + authorization classes + forbidden-action patterns (fleet model) | Existing (extended by M1) |
| Audit | `audit_record` on every swarm action | Existing |
| Human approval | `hermes_swarm_approve` requires owner ack + direct mode; never auto-advanced | NEW |

**Non-goals restated (security):** NG1 (no weakening of Operator/Owner gates),
NG2 (no fake sandbox claims — report the sandbox actually used), NG3 (no
unauthenticated/public exposure), NG4 (no multi-tenant). Pending approvals from a
workflow surface via the M0 approval view **view-only**; actionable approval is a
swarm mutation tool (`hermes_swarm_approve`), not an M0 surface (P1-1).

## 11. Open questions (require Tony / integration decisions)

| # | Question | Default assumed for this design | Impact if changed |
|---|---|---|---|
| Q1 | **Parallelism caps**: are `max_parallel=3`/workflow, `4`/board, `12` stages/workflow the right defaults? | Yes (bounded per NG-SW6/R5). | Tune in implementation; the engine reads caps from config/env, not hard-coded values. |
| Q2 | **Board-level cap**: should the per-board cap be global across all workflows, or per-workflow only? | Per-board global cap (protects the machine). | If per-workflow only → remove board cap; risk of unbounded machine load. |
| Q3 | **Integration merge**: who merges parallel branches into the integration worktree — an agent stage or `default`? | An agent integration-review stage with `reversible_write`; `default` verifies. | If `default` must do it → a manual step before Codex review. |
| Q4 | **Rework policy**: confirm a single bounded auto-rework retry before `blocked` is acceptable. | Yes (bounded, then human). | If no auto-rework → every failed stage blocks for a human immediately (more conservative). |
| Q5 | **Codex steering**: is Codex used only for the review stage in the canonical shape, or also as implementation owners for some stages? | Review stage only by default; implementation owners are Hermes profiles. | If Codex also implements → add `workspace-write` stages under the same gates; flag to risk review. |
| Q6 | **Workflow persistence**: is the run/outcome/artifact record written to kanban/audit (read by M0) sufficient, or is a dedicated `swarm_workflows` store needed? | Reuse kanban task runs + operator audit; no new store (NG-MC2-style, aligns with M0). | A dedicated store → new schema + M0 surface; larger scope. |
| Q7 | **Approval mechanics**: confirm `hermes_swarm_approve` at owner level is the approval gate (view-only surfacing in M0). | Yes (S3/S4, P1-1). | If approvals must be actionable from M0 → add an M0 write path, contradicting M0 view-only. |
| Q8 | **Remote fleet nodes**: are workflows single-host (this machine + Codex) only? | Single-host + local A2A registry (consistent with M0 Q3). | Remote nodes → swarm dispatch needs a remote worktree/A2A path; larger scope. |
| Q9 | **Retention of worktrees**: confirm `default` cleans up workflow worktrees after the release gate per the plan's retention policy. | Yes, documented in §7/§12. | If kept indefinitely → disk accumulation; flag to risk review §8. |

### 12.4 Test plan outline

`test_operator_swarm.py` (mirrors existing `test_operator_*.py` style; all on temp
fixtures, never production data):

1. **Workflow DAG validation**: the canonical shape validates; a cyclic DAG, a
   stage over the cap, or a stage without an owner is rejected.
2. **Scheduler bounds**: fan-out never exceeds `max_parallel`; a stage is not
   dispatched until its parents are `done`; board cap enforced globally.
3. **Contract dispatch**: each stage emits a valid M1 contract (objective, owner,
   scope=worktree, artifacts, tests, criteria, authorization).
4. **Verifiable completion (S2)**: a worker claims done but observed state shows
   no artifact → verdict `returned_for_rework`; a genuine artifact + green tests →
   `satisfied`.
5. **Bounded rework**: first failure requeues once; second failure → `blocked`
   (never unbounded).
6. **Worktree isolation (NG5)**: implementation stages run in separate worktrees/
   branches; no cross-stage file collision; merge into integration branch works.
7. **Codex posture**: review stage calls the existing runner with fixed-argv,
   `shell=False`, bounded timeout, approved workdir; a non-approved workdir is
   refused.
8. **Approval gate**: the workflow stays `awaiting_approval` until
   `hermes_swarm_approve` (owner + direct) records it; it never auto-advances.
9. **Mutation gates**: create/dispatch/advance at `dry_run=True` return a plan and
   do not mutate; execute requires `confirm` + direct mode.
10. **Audit**: every swarm action appends an audit record with
    workflow_id/stage/owner/verdict.
11. **Read redaction**: workflow status via M0 returns bounded, redacted output; no
    raw bodies.
