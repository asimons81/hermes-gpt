# Hermes GPT v0.8 Fabric ADR Set

- Status: ACCEPTED, G2
- Program: #27
- Gate: #29
- Security gate: #30
- Research source: `docs/releases/v0.8-fabric-research-package.md`
- Frozen implementation evidence baseline: `4bb85d1eb7abf0974077b63c131013613793bb72`

These ADRs define the G2 architecture. They do not authorize G4 implementation until G3 closes PASS.

## ADR-009: Use official Hermes A2A v1.0 as Fabric transport

**Status:** Accepted

**Decision:** Use configured and authenticated Hermes A2A v1.0 peers for Fabric network transport. Do not create a second network stack for v0.8.

**Constraint:** A2A transport success, task state, streaming, push, and peer text are transport facts only. They are never Work Contract proof.

## ADR-010: Require a managed deterministic Fabric peer for verified remote stages

**Status:** Accepted

**Decision:** A remote stage qualifies as verified Fabric execution only when the target is an enrolled managed node that exposes the deterministic Hermes GPT Fabric acceptance boundary.

Generic A2A agents remain valid ordinary delegation targets, but they cannot satisfy a Fabric verified-stage placement requirement.

**Security reason:** Current generic inbound A2A work ultimately reaches an agent session. Natural-language interpretation cannot enforce a write-capable authority envelope.

## ADR-011: Add Fabric-specific distributed interfaces without redefining v0.7 seams

**Status:** Accepted

**Decision:** Keep the v0.7 `DispatchAdapter` and `EvidenceProvider` behavior intact. Add Fabric-specific adapters/models with explicit distributed lifecycle operations:

- capability/availability probe;
- dispatch;
- poll;
- recover;
- evidence collection;
- artifact collection;
- cancel;
- reconcile.

Schema identifiers are versioned independently from Python protocol/class names.

## ADR-012: Persist coordinator dispatch and attempt lineage in a transactional journal

**Status:** Accepted

**Decision:** Use a coordinator-owned durable transactional journal. The implementation may use Python's standard-library SQLite support and must provide atomic uniqueness and state transitions.

Minimum logical records:

### `dispatch`
- `dispatch_id` primary key;
- workflow/stage/task lineage;
- `contract_sha256`;
- canonical requirements digest;
- logical write-scope digest when write-capable;
- creation timestamp;
- current coordinator lifecycle state.

### `attempt`
- `attempt_id` primary key;
- `dispatch_id`;
- attempt sequence;
- target peer/backend;
- canonical envelope digest;
- capability snapshot digest;
- authority/scope digest;
- negotiated Fabric version/features;
- remote A2A task ID when known;
- write epoch when applicable;
- state/reason code;
- recovery/cancel lineage;
- bounded timestamps.

### `write_claim`
- logical write-scope digest;
- owning `dispatch_id` and `attempt_id`;
- monotonically increasing epoch;
- ACTIVE/RELEASED state;
- timestamps and release reason.

An ACTIVE coordinator write claim is unique per logical write scope.

## ADR-013: Persist peer acceptance before write-capable execution

**Status:** Accepted

**Decision:** The managed peer keeps a durable transactional Fabric journal independent of upstream A2A task retention.

Before any write-capable runner is started, one transaction must:

1. validate the request;
2. insert or resolve the attempt identity;
3. acquire the peer-local write claim for the resolved local scope;
4. persist the accepted envelope/authority/workspace digests and write epoch;
5. commit.

Only after that transaction commits may the runner begin mutation.

If the peer restarts and cannot prove terminal runner state, the attempt becomes `LOST_AMBIGUOUS` and its write claim remains ACTIVE.

## ADR-014: Separate stable dispatch identity from attempt identity

**Status:** Accepted

**Decision:** `dispatch_id` identifies one logical stage execution intent. `attempt_id` identifies one actual execution attempt.

Rules:

- one dispatch can have multiple attempts over its lifetime;
- identical replay of the same `(dispatch_id, attempt_id, envelope_sha256)` returns existing state;
- reuse of an existing attempt identity with different canonical content is rejected as `FABRIC_IDEMPOTENCY_CONFLICT`;
- retries use a new `attempt_id`;
- contract or bounded execution-request changes create a new dispatch lineage rather than mutating historical identity;
- remote A2A task IDs are transport mappings, not stable Fabric identity.

## ADR-015: Keep managed-node enrollment and authority server-controlled

**Status:** Accepted

**Decision:** Introduce `hermes.fabric-node-registry/v1` as a server-owned registry model.

A node record binds:

- stable Fabric node name;
- configured A2A peer name;
- expected Agent Card identity/card digest policy;
- enabled/disabled state;
- allowed profiles;
- maximum authorization class;
- public/high-impact action posture;
- allowed logical workspace mappings;
- runner/provider/model allowlists or policy references;
- supported Fabric protocol policy;
- artifact-transfer policy;
- operator-readable non-secret labels.

Bearer tokens, OAuth/API credentials, peer URLs, and local absolute paths are never supplied by Work Contracts, routing requests, or Flight Deck callers.

Enrollment, credential changes, identity changes, and authority-ceiling changes are administrative configuration mutations outside the Fabric placement API.

## ADR-016: Separate capability facts by provenance and freshness

**Status:** Accepted

**Decision:** Use `hermes.fabric-capability/v1` with field-level provenance classes:

- `coordinator_observed`;
- `coordinator_policy`;
- `peer_attested`;
- `coordinator_derived`;
- `soft_hint`.

Every positive hard-eligibility fact must carry or inherit `observed_at` and `expires_at`. The coordinator caps freshness according to local policy; a peer cannot extend its own trust lifetime.

Rules:

- stale/unknown hard positive facts evaluate as unavailable;
- identity/card drift invalidates the capability snapshot;
- write-capable dispatch performs a fresh identity/health check immediately before acceptance;
- stale/missing soft hints such as load or latency are ignored for ranking rather than treated as authority;
- capability advertisement never creates authorization.

The coordinator records both the remote manifest digest and the effective joined snapshot digest used for placement.

## ADR-017: Route by hard exclusion, then deterministic lexicographic ranking

**Status:** Accepted

**Decision:** `execution.backend=auto` uses two phases.

### Phase 1: hard eligibility

Exclude any target that fails a required condition, including:

- registry enrollment;
- live expected identity;
- Fabric protocol/features;
- freshness/health;
- authorization/profile;
- public/high-impact policy;
- runner/provider/model allowlist;
- required tool/browser/vision/GPU capability;
- logical workspace mapping;
- required read/write confinement;
- artifact support;
- hard concurrency/capacity ceiling;
- unresolved write claim or uncertain prior write attempt.

### Phase 2: soft ranking

Rank only eligible targets with the versioned `fabric-router-v1` tuple, lower is better:

1. locality/artifact-affinity penalty;
2. specialized-hardware fit penalty;
3. load/capacity bucket;
4. recent-latency bucket;
5. optional grounded-cost bucket;
6. stable target identifier `(node_name, backend)` as final tie-break.

Missing soft data receives the worst soft bucket, not an authority failure.

The placement record stores the policy ID, candidate exclusions, material tuple inputs, selected target, and capability snapshot digest.

Conversational A2A `best` selection is never used as Fabric scheduling policy.

## ADR-018: Explicit placement remains filtered

**Status:** Accepted

**Decision:** Explicit peer/backend selection bypasses soft ranking only. It does not bypass any hard eligibility, authority, workspace, protocol, freshness, or confinement check.

An unsafe explicit target fails closed with bounded reason codes.

## ADR-019: Use server-owned logical workspace mappings

**Status:** Accepted

**Decision:** Fabric requests reference a logical workspace identity. Each managed node resolves that identity to a peer-local path from server-owned configuration.

Rules:

- caller-provided remote absolute paths are rejected;
- traversal or alternate-path tricks are rejected before mapping;
- peer-local allowed-path, denied-secret-path, symlink, and confinement policy still apply;
- a mapping revision/digest is bound into the accepted attempt so later configuration drift is detectable;
- no remote absolute path is exposed in client-facing evidence, events, or Flight Deck models.

## ADR-020: Remote evidence is admissible input, never the verdict

**Status:** Accepted

**Decision:** Managed peers return `hermes.fabric-evidence/v1`. Coordinator admission requires exact binding to:

- `dispatch_id`;
- `attempt_id`;
- `contract_sha256`;
- managed peer identity;
- negotiated Fabric version/features;
- capability snapshot digest;
- effective authority/scope digest;
- terminal remote execution state.

Evidence classes are:

1. coordinator-observed transport fact;
2. managed-peer structured observation;
3. coordinator-verified artifact;
4. coordinator-local observation;
5. worker statement/handoff data.

Class 5 never proves completion. A remote `SATISFIED`, `PASS`, or equivalent verdict field is ignored or rejected as proof. Only the coordinator Work Contract validator owns the machine completion verdict.

## ADR-021: Transfer artifacts by coordinator-pulled bounded A2A chunks

**Status:** Accepted

**Decision:** v0.8 uses managed A2A as the artifact transport. A peer first returns `hermes.fabric-artifact-manifest/v1`. When bytes are requested, the coordinator pulls bounded chunks from the deterministic Fabric acceptor using artifact identity plus offset/length.

Rules:

- no caller-controlled URL fetch;
- no peer-provided arbitrary external URI fetch;
- artifact source must already be admitted into the peer's approved attempt artifact set;
- producer enforces allowed workspace, denied-secret-path, regular-file, symlink/special-file, extension/media, per-artifact, and per-attempt bounds;
- coordinator writes chunks to a temporary local file/resource, enforces total bounds while receiving, computes SHA-256, compares size/digest to the manifest, then atomically admits the artifact;
- failed/incomplete/hash-mismatched transfers are discarded and never become evidence;
- large artifacts beyond configured v0.8 limits remain remote and are reported as non-admitted metadata, not silently truncated.

This is a bounded A2A application binding, not a second network transport.

## ADR-022: Make cancellation attempt-specific, idempotent, and durable

**Status:** Accepted

**Decision:** Fabric cancellation targets `attempt_id`, not merely an A2A task ID.

Flow:

1. coordinator records `CANCEL_REQUESTED`;
2. request is sent through the deterministic Fabric binding;
3. peer records cancel intent before acting on the runner;
4. peer reconciles runner state and records terminal or ambiguous outcome;
5. coordinator polls/reconciles until terminal proof or `CANCEL_AMBIGUOUS`.

Duplicate cancel requests return current durable state.

A transport-level A2A `CancelTask` may be used, but it is insufficient by itself to release a Fabric write claim.

## ADR-023: Prevent concurrent uncertain writers with non-expiring write claims plus monotonic epochs

**Status:** Accepted

**Decision:** Use a durable write-claim model, not a time-expiring lease.

For every write-capable attempt, compute a canonical logical `write_scope_sha256` from the managed node/workspace-independent logical scope granted by the Work Contract.

Coordinator rules:

- only one ACTIVE claim may exist for a logical write scope;
- each newly acquired claim receives a monotonically increasing `write_epoch`;
- a new write attempt cannot be created while any previous claim for that scope is ACTIVE or ambiguous;
- claims do not expire merely because time passed, the coordinator restarted, the peer is unreachable, or a cancellation was requested;
- automatic release requires terminal evidence that the runner can no longer mutate plus successful reconciliation;
- read-only attempts do not acquire a write claim.

Peer rules:

- resolve the logical scope to the local mapping;
- reject a second local ACTIVE claim for the same mapped write scope;
- reject stale/lower epochs;
- persist the claim before starting the runner;
- do not release the claim on A2A task loss alone.

The epoch is a stale-command guard and audit fence. It is not treated as magical filesystem fencing. Because ordinary filesystems do not enforce Fabric epochs, a higher epoch is never issued automatically while an earlier writer may still exist.

Irreconcilable write ownership fails to `BLOCKED_WRITE_OWNERSHIP`. v0.8 does not auto-force-release such a claim. External operator intervention must first establish that the old writer is stopped/isolated, after which normal reconciliation may release the claim. History is never rewritten to pretend the old state was known.

## ADR-024: Treat restart and transport ambiguity as blocked, never successful

**Status:** Accepted

**Decision:** Coordinator restart, peer restart, lost A2A task state, transport loss, push/SSE loss, and ambiguous cancellation never auto-advance a stage or create a satisfied contract.

Coordinator restart reloads the durable journal before any retry/placement decision. Peer restart reloads its Fabric journal before accepting a conflicting write attempt.

If durable state cannot establish safety, the state is blocked/ambiguous and write ownership remains active.

## ADR-025: Polling plus durable journals define correctness

**Status:** Accepted

**Decision:** A2A streaming, subscription, and push may reduce latency. Correctness must remain achievable using authenticated bounded polling plus coordinator/peer journals.

Loss of optional liveness channels never changes a success/failure verdict.

## ADR-026: Extend Event History and Flight Deck through bounded read models only

**Status:** Accepted

**Decision:** Coordinator records bounded Fabric lifecycle events and exposes read models for:

- managed nodes;
- identity/health/freshness;
- capability summary;
- placement and explanation;
- dispatch/attempt/remote task mapping;
- authority/scope summary;
- evidence/artifact admission;
- ambiguity/recovery/cancel state;
- blocked reason.

No generic WebSocket control-plane redesign is required in v0.8. UI mutations continue through gated `hermes_*` operator actions. Fabric read models cannot execute remote work directly.

## ADR-027: Preserve local-only behavior

**Status:** Accepted

**Decision:** Existing local Work Contracts, Swarms, explicit `fleet`, `pi_rpc`, `omx`, and `codex` runners, Operator/Owner gates, secret-path policy, and final human approval remain valid.

Fabric `auto` and managed remote placement are additive. Contracts that do not request Fabric behavior retain documented v0.7 compatibility semantics.

## ADR-028: State the compromised-peer boundary honestly

**Status:** Accepted

**Decision:** Fabric defends against malformed input, policy drift, authority injection, accidental duplicate execution, stale routing, buggy or overclaiming agents, artifact boundary failures, and restart/transport ambiguity.

Fabric does not claim cryptographic truth about observations produced by a fully compromised remote OS that controls its own runtime credentials and local evidence sources.

Mitigations for that boundary are enrollment discipline, bounded authority, independent coordinator observations where available, artifact hashing during transfer, audit lineage, and independent review. They are not remote attestation.

## ADR-029: Bind deterministic Fabric operations to structured A2A DataParts

**Status:** Accepted

**Decision:** A managed peer advertises Fabric support through a versioned Agent Card extension/capability marker. Fabric requests are sent as structured A2A DataParts using `hermes.fabric-request/v1`; responses use `hermes.fabric-response/v1`.

Required operations:

- `capabilities`;
- `accept`;
- `status`;
- `cancel`;
- `evidence`;
- `artifact_manifest`;
- `artifact_chunk`;
- `reconcile`.

For attempt operations:

- A2A `contextId` is bound to `dispatch_id`;
- `attempt_id` is present in the structured payload;
- any returned A2A task ID is persisted as a transport mapping only.

The managed Hermes GPT peer intercepts and validates these structured Fabric operations before ordinary agent-session dispatch. Generic A2A messages continue through normal Hermes behavior.

A Fabric operation that reaches the generic LLM path is a protocol failure and cannot count as verified execution.

## ADR-030: Use explicit Fabric version and feature negotiation with no silent downgrade

**Status:** Accepted

**Decision:** v0.8 supports Fabric major version 1 with explicit schema identifiers and required feature tokens.

Rules:

- coordinator live-probes the managed peer's supported Fabric major versions/features;
- unknown major versions fail closed;
- unknown required features fail closed;
- optional unknown fields may be ignored only when the v1 schema marks them optional and bounded;
- the selected version and required feature set are recorded in the attempt journal;
- evidence/artifact responses must be compatible with the recorded negotiation;
- failure of v1 negotiation never falls back to generic A2A execution for a verified stage.

## ADR-031: Define explicit coordinator and peer operational state machines

**Status:** Accepted

**Decision:** Fabric operational states are not Work Contract verdicts.

Coordinator attempt states:

`PLANNED -> SUBMITTING -> {SUBMITTED | SUBMISSION_AMBIGUOUS}`

`SUBMITTED -> {RUNNING | CANCEL_REQUESTED | RECONCILING | TERMINAL_REPORTED}`

`RUNNING -> {CANCEL_REQUESTED | RECONCILING | TERMINAL_REPORTED}`

`SUBMISSION_AMBIGUOUS -> RECONCILING`

`CANCEL_REQUESTED -> {CANCELLED | CANCEL_AMBIGUOUS | TERMINAL_REPORTED}`

`CANCEL_AMBIGUOUS -> RECONCILING`

`RECONCILING -> {SUBMITTED | RUNNING | TERMINAL_REPORTED | CANCELLED | BLOCKED}`

`TERMINAL_REPORTED -> EVIDENCE_PENDING -> VALIDATING -> {COMPLETED | FAILED | BLOCKED}`

Terminal operational states: `COMPLETED`, `FAILED`, `CANCELLED`, `BLOCKED`.

Peer attempt states:

`RECEIVED -> ACCEPTED -> {RUNNING | CANCEL_REQUESTED}`

`RUNNING -> {SUCCEEDED | FAILED | CANCEL_REQUESTED | LOST_AMBIGUOUS}`

`CANCEL_REQUESTED -> {CANCELLED | SUCCEEDED | FAILED | LOST_AMBIGUOUS}`

Peer terminal report states `SUCCEEDED`, `FAILED`, `CANCELLED` do not imply Work Contract satisfaction.

State transitions are compare-and-set/transactional. Unknown or illegal transitions are rejected and audited.

## ADR-032: Define canonical envelopes and digests

**Status:** Accepted

**Decision:** Fabric security-relevant digests use canonical JSON serialization with sorted keys, UTF-8, no insignificant whitespace, and SHA-256.

The dispatch envelope binds at minimum:

- schema/version and required features;
- `dispatch_id` and `attempt_id`;
- workflow/stage/task lineage;
- `contract_sha256`;
- bounded objective/execution-request digest or canonical bounded request;
- selected managed node/backend;
- execution requirements;
- authorization class and forbidden action classes;
- logical workspace identity;
- canonical read/write scope;
- expected checks/artifacts;
- capability snapshot digest;
- expiry/created timestamps used for replay bounds;
- retry parent attempt when applicable;
- write-scope digest and epoch when write-capable.

Forbidden payload categories include credentials, arbitrary peer URLs, caller-defined authority ceilings, remote absolute paths, and unbounded prompt/log bodies.
