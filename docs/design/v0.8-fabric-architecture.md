## 1. Purpose

Define the implementation-ready architecture for Hermes GPT v0.8 Fabric without changing the v0.7 trust model.

Fabric changes **placement**, not **truth**.

A Work Contract or Swarm stage may execute on another managed machine, but:

- the coordinator remains the authority owner;
- server-controlled policy determines eligible peers and authorization ceilings;
- remote execution never upgrades Work Contract authority;
- remote self-report never certifies completion;
- final validation remains coordinator-owned;
- final Swarm approval remains human/Owner-gated;
- ambiguous distributed state fails closed.

## 2. Architecture thesis

> A2A transports the work. Fabric controls the work. Work Contracts decide whether the work is satisfied.

Official Hermes A2A v1.0 remains the network/task transport substrate. Fabric adds the deterministic control-plane semantics that generic agent-to-agent messaging does not provide by itself.

## 3. Required components

### 3.1 Coordinator-side components

#### Fabric node registry

Server-controlled managed-node records containing non-secret identity and policy references.

Responsibilities:

- map stable peer name to configured A2A peer;
- bind expected Agent Card identity;
- bind local authorization ceiling and allowed profiles;
- expose no bearer token to contracts/UI;
- reject caller-provided arbitrary peer URL/token;
- track compatibility/freshness metadata.

#### Capability collector/cache

Collect bounded node capabilities and classify each field by provenance:

- coordinator-observed;
- peer-attested;
- coordinator-derived;
- soft hint.

Unknown or stale positive requirements are not affirmative capability.

#### Placement router

Two phases:

1. hard eligibility filtering;
2. deterministic ranking among eligible candidates.

The router cannot widen authority or bypass runner/provider/model allowlists.

#### Durable dispatch/attempt journal

Persist coordinator-owned distributed execution lineage before/around network operations.

Minimum identity:

- dispatch ID;
- attempt ID;
- workflow/stage/task identity;
- contract hash;
- selected peer/backend;
- remote task ID when known;
- capability snapshot digest;
- authority/scope digest;
- lifecycle state;
- recovery/cancel lineage;
- bounded timestamps/reason codes.

#### A2A Fabric DispatchAdapter

Translate a canonical Fabric dispatch envelope into the approved A2A binding, without exposing raw credentials or arbitrary destinations.

Responsibilities:

- submit;
- poll;
- recover ambiguous submission;
- cancel;
- collect bounded remote evidence/artifact manifests;
- preserve stable dispatch and attempt identities.

#### Fabric EvidenceProvider

Admit only versioned, provenance-bearing remote observations.

It does **not** accept a remote `SATISFIED` verdict as proof.

#### Artifact admission/transfer layer

Validate:

- logical artifact identity;
- expected artifact mapping;
- media type where applicable;
- byte size bounds;
- SHA-256;
- producer peer/attempt lineage;
- denied secret/path rules;
- transfer-scheme allowlist.

#### Existing Work Contract validator

Remains the final machine decision engine.

Fabric evidence extends its observed inputs. It does not replace its verdict semantics.

### 3.2 Managed peer components

#### Deterministic Fabric acceptor

A verified Fabric peer must expose a compatible Hermes GPT Fabric acceptance surface.

The acceptor must validate before write-capable execution:

- authenticated coordinator identity;
- schema/protocol version;
- dispatch ID and attempt ID;
- contract hash;
- envelope bounds;
- local peer authorization ceiling;
- allowed local workspace mapping;
- selected runner/backend;
- runner/provider/model allowlists;
- required confinement posture;
- duplicate/idempotency state.

A remote LLM may perform the requested work, but it is not the parser or enforcer of the authority envelope.

#### Durable peer attempt journal

Must survive A2A gateway/peer process restart independently of upstream A2A's current in-memory task store.

Before a write-capable attempt begins mutation, the peer must durably record enough identity/state to prevent a retry from becoming an unnoticed concurrent writer.

#### Local runner and confinement boundary

Reuse the existing runner architecture and local security posture wherever possible.

#### Remote evidence builder

Generate bounded observations and artifact manifests tied to:

- dispatch ID;
- attempt ID;
- contract hash;
- peer identity;
- runner/backend;
- effective authority/scope;
- terminal execution state.

The peer reports observations, not the coordinator's final contract verdict.

## 4. Proposed protocol objects

Names remain proposed until ADR acceptance.

### 4.1 `hermes.fabric-dispatch/v1`

Required categories:

- protocol/schema version;
- stable `dispatch_id`;
- per-attempt `attempt_id`;
- workflow/stage/task lineage;
- `contract_sha256`;
- objective hash / bounded execution request;
- selected peer and backend identifiers;
- execution requirements;
- authorization class;
- logical workspace request;
- forbidden-action classes;
- expected artifact/check descriptors;
- capability snapshot digest;
- expiry/timestamps;
- retry parent reference.

Forbidden categories:

- bearer tokens;
- OAuth/API credentials;
- caller-chosen peer URL;
- caller-defined peer authorization ceiling;
- unbounded prompt/log bodies.

### 4.2 `hermes.fabric-capability/v1`

Candidate categories:

- peer/card identity and digest;
- Fabric protocol versions;
- Hermes GPT/Agent versions where safely observable;
- OS/architecture;
- runner availability and safe posture;
- tool/browser/vision/GPU capabilities;
- model/provider identifiers only;
- artifact-transfer support/bounds;
- health probe state/freshness;
- active load/capacity;
- optional latency/cost hints.

Local authority fields are joined by the coordinator and are not trusted from remote advertisement.

### 4.3 `hermes.fabric-evidence/v1`

Candidate categories:

- dispatch/attempt/task identity;
- remote A2A task ID;
- contract hash;
- peer/card identity reference;
- Fabric runtime and runner/backend;
- capability snapshot digest;
- effective authority/scope digest;
- bounded timestamps and terminal state;
- bounded observed checks;
- artifact manifests;
- cancellation/recovery lineage.

Evidence classes:

1. coordinator-observed transport fact;
2. managed-peer observation;
3. coordinator-verified artifact;
4. coordinator-local observation;
5. worker statement, which is handoff data only.

## 5. Node enrollment and identity

Proposed policy:

- Fabric peers are configured server-side.
- User/LLM calls reference peer names only.
- Peer URLs and auth material remain in local Hermes configuration.
- A local authority registry binds peer name to expected card identity, profile ceiling, authorization ceiling, and public/high-impact posture.
- Live identity verification is required before write-capable dispatch and after relevant freshness/drift events.
- Generic third-party A2A peers remain usable through ordinary A2A delegation but are not verified Fabric nodes unless they implement the Fabric acceptance contract.

Open design item: evolve the current narrow fleet authority manifest to a safe general managed-node registry without preserving the current built-in-name restriction as an accidental long-term API.

## 6. Workspace model

Remote absolute coordinator paths are not portable authority.

Proposed model:

- contract refers to a logical workspace identity or approved project/workspace reference;
- coordinator registry maps that logical identity to an allowed peer-local workspace definition;
- peer acceptor resolves the local path from server-owned configuration;
- caller cannot submit an arbitrary remote absolute path;
- local secret/path/confinement rules still apply on the peer.

## 7. Placement algorithm

### 7.1 Hard filters

Applicable requirements include:

- registry membership;
- live expected identity;
- compatible Fabric protocol;
- fresh capability snapshot;
- healthy peer;
- authorization ceiling;
- allowed profile;
- runner availability/allowlist;
- model/provider availability/allowlist;
- tool/browser/vision/GPU requirements;
- workspace mapping;
- read/write confinement posture;
- artifact-transfer capability;
- hard concurrency limit;
- forbidden/public/high-impact policy.

A candidate failing any required hard filter is excluded.

### 7.2 Soft ranking

Only eligible candidates may be ranked by grounded signals such as:

- locality/artifact affinity;
- available capacity/load;
- recent observed latency;
- hardware fit;
- model/tool fit;
- optional known cost.

Stable peer/backend identity is the deterministic final tie-break.

### 7.3 Explanation contract

Every `auto` decision returns bounded reasons:

- requirements;
- exclusions and reason codes;
- eligible candidates;
- selected candidate;
- material ranking inputs;
- capability snapshot age/digest.

## 8. Distributed execution lifecycle

Proposed coordinator attempt states:

- `PLANNED`
- `SUBMITTING`
- `SUBMISSION_AMBIGUOUS`
- `SUBMITTED`
- `RUNNING`
- `CANCEL_REQUESTED`
- `CANCEL_AMBIGUOUS`
- `RECONCILING`
- `EVIDENCE_PENDING`
- `TERMINAL_REPORTED`
- `VALIDATING`
- `BLOCKED`
- `COMPLETED`
- `FAILED`
- `CANCELLED`

These are Fabric operational states, not Work Contract verdicts.

A terminal remote execution still requires coordinator validation.

## 9. Timeout/idempotency semantics

### Stable dispatch identity

One stage execution intent gets one stable `dispatch_id`.

Retries get unique `attempt_id` values linked to the same stage/dispatch lineage.

### Submit timeout

Preserve current fleet behavior:

- try to recover the remote A2A task by context/identity;
- if exactly one task is recovered, bind it to the same attempt;
- never blindly resubmit;
- if recovery is not unique, mark the attempt ambiguous and block according to authority/risk.

### Peer duplicate acceptance

- identical replay of the same dispatch/attempt returns existing durable state;
- conflicting content for an existing identity is rejected and audited.

## 10. Write-race invariant

> Hermes GPT must never silently create two write-capable attempts against the same bounded work scope because it was unsure whether the first attempt stopped.

G2 must choose a concrete enforcement mechanism such as lease/epoch ownership, but the invariant itself is mandatory.

Until an old write attempt is proven terminal/cancelled under the defined model, automatic replacement is forbidden.

Human override of an irreconcilable state must be explicit and audited and cannot rewrite history to claim the old attempt was known stopped.

## 11. Restart reconciliation

### Coordinator restart

- reload durable Fabric journal;
- compare Swarm/contract stage state to active attempts;
- re-probe peer identity/capability when needed;
- poll/reconcile active remote attempts;
- block ambiguity;
- never auto-mark a stage satisfied.

### Peer restart

Because pinned upstream A2A task state is in-memory:

- remote Fabric attempt journal must be queried independently of ephemeral A2A task history;
- if durable attempt state maps to an active/durable runner job, resume observation;
- if neither A2A nor Fabric durable state can prove the attempt state, block as lost/ambiguous;
- write-capable retry remains prohibited until the defined safety condition is met.

## 12. Cancellation

Fabric cancellation must be:

- peer-bound;
- attempt-bound;
- idempotent;
- durable;
- safe under completion races.

A2A `CancelTask` is the transport primitive, but Fabric must reconcile it against the peer Fabric journal/runner state.

## 13. Artifact architecture

Preferred v0.8 behavior:

- remote peer creates a bounded manifest;
- artifact references use an approved Fabric/A2A transfer binding only;
- arbitrary external fetch URLs are rejected by default;
- coordinator validates size/hash/type/lineage before admission;
- remote absolute paths stay private;
- secret-path and special-file policy is enforced at the producing peer before export;
- coordinator stores only bounded artifact metadata/evidence unless bytes are explicitly retrieved through the approved resource path.

## 14. Evidence and validation

Remote peer evidence is accepted only when:

- schema/version is supported;
- dispatch/attempt/contract identities match coordinator state;
- peer identity matches the managed node record;
- evidence is bounded/redacted;
- artifact/check lineage is structurally valid;
- any required artifact bytes/hash checks pass.

Even then, the evidence is input to the existing coordinator validator.

The peer never owns `SATISFIED`.

## 15. Events and Flight Deck

Coordinator should write bounded Fabric events for:

- capability probe/update;
- placement decision;
- dispatch planned/submitted/ambiguous/recovered;
- peer task state transition;
- cancel request/result;
- reconcile action/result;
- evidence received/rejected;
- artifact admitted/rejected;
- validation verdict;
- review/final approval linkage.

Flight Deck additions should remain read-model adapters over these bounded records.

No generic v0.8 WebSocket control-plane redesign is required for correctness. Polling remains the correctness fallback even if A2A streaming/push is used as a liveness optimization.

## 16. Threat boundary

Fabric is designed to defend against:

- malformed/untrusted agent input;
- caller authority injection;
- stale/incorrect capability routing;
- accidental duplicate execution;
- timeout/restart ambiguity;
- buggy or overclaiming workers;
- artifact path/hash/bounds errors;
- ordinary peer identity/config drift.

Fabric cannot make a fully compromised remote OS truthfully attest its own filesystem or process state if that OS also controls the credentials/runtime used to produce observations.

G3 must preserve this honest boundary and not imply cryptographic remote attestation that is not actually implemented.

## 17. Backward compatibility

Required:

- existing local Work Contracts remain valid;
- existing Swarms remain valid;
- explicit `fleet`, `pi_rpc`, `omx`, and `codex` backends remain supported;
- current default/legacy dispatch behavior remains defined;
- Fabric `auto` is additive and opt-in through an approved contract schema change;
- existing Operator/Owner/secret-path gates remain authoritative;
- existing final human Swarm approval remains unchanged.
