## 1. Purpose

Hermes GPT v0.8 Fabric adds managed cross-machine execution while preserving the v0.7 trust model.

Fabric changes placement, not truth.

A Work Contract or Swarm stage may execute on another managed machine, but:

- the coordinator remains the authority owner;
- server-controlled policy determines eligible peers and authorization ceilings;
- remote execution never upgrades Work Contract authority;
- remote self-report never certifies completion;
- final validation remains coordinator-owned;
- final Swarm approval remains human/Owner-gated;
- ambiguous distributed state fails closed.

## 2. Architecture thesis

> A2A transports the work. Fabric controls the work. Work Contracts decide whether the work is satisfied.

Official Hermes A2A v1.0 remains the network/task transport substrate.

Fabric adds:

- managed-node enrollment;
- deterministic peer-side request acceptance;
- capability provenance/freshness;
- deterministic placement;
- durable coordinator and peer attempt journals;
- idempotent dispatch/recovery/cancel semantics;
- write-ownership protection;
- bounded evidence admission;
- bounded artifact transfer/admission;
- distributed event/read models.

## 3. Trust and responsibility boundary

### 3.1 Coordinator owns

- Work Contract and Swarm authority;
- managed-node registry and local authorization ceilings;
- capability trust policy;
- placement eligibility and ranking;
- stable dispatch identity;
- global logical write claims;
- authoritative distributed attempt lineage;
- evidence admission;
- artifact admission;
- Work Contract validation;
- Event History lineage;
- review/final approval integration.

### 3.2 Managed peer owns

- deterministic Fabric request parsing/validation;
- local authorization ceiling enforcement;
- logical workspace resolution;
- local runner/provider/model/tool allowlist enforcement;
- local filesystem confinement;
- durable peer attempt state;
- peer-local write claims;
- runner lifecycle observation;
- bounded evidence construction;
- safe artifact export.

### 3.3 A2A owns only transport

A2A task success, streaming, push, peer prose, or Agent Card capability advertisement does not create Fabric authority and does not prove contract satisfaction.

### 3.4 Worker/LLM owns neither authority nor truth

The remote worker may execute bounded work. It is not the authority-envelope parser and it cannot certify its own completion.

## 4. Managed Fabric node registry

Fabric uses server-owned `hermes.fabric-node-registry/v1`.

Minimum node record:

```json
{
  "schema": "hermes.fabric-node-registry/v1",
  "node_name": "stable-name",
  "a2a_peer_name": "configured-peer-name",
  "enabled": true,
  "expected_identity": {
    "agent_name": "expected-card-name",
    "card_digest_policy": "pinned-or-refresh-controlled"
  },
  "allowed_profiles": ["..."],
  "max_authorization": "read-only|workspace|system",
  "public_action_posture": "deny|explicit-only",
  "workspace_mappings": {
    "logical-workspace-id": {
      "local_path": "<server-owned, never client supplied>",
      "revision": "..."
    }
  },
  "runner_policy_ref": "...",
  "provider_model_policy_ref": "...",
  "fabric_protocol_policy": {
    "allowed_major_versions": [1],
    "required_features": []
  },
  "artifact_policy_ref": "..."
}
```

Security rules:

- caller may reference `node_name` only;
- peer URL/token resolution comes from existing server configuration;
- credentials never enter Work Contracts, dispatch envelopes, events, evidence, artifacts, or Flight Deck read models;
- enrollment and authority changes are administrative configuration operations, not placement operations;
- live identity drift disables eligibility until re-established through the administrative trust path.

## 5. Deterministic Fabric binding over A2A

### 5.1 Agent Card advertisement

A managed peer advertises a versioned Fabric extension/capability marker with:

- supported Fabric major versions;
- supported required-feature tokens;
- supported operation set;
- non-secret capability discovery marker.

Advertisement is discoverability only. It does not establish authorization.

### 5.2 Structured request/response binding

Fabric uses A2A structured DataParts:

- request schema: `hermes.fabric-request/v1`;
- response schema: `hermes.fabric-response/v1`.

Required operations:

- `capabilities`;
- `accept`;
- `status`;
- `cancel`;
- `evidence`;
- `artifact_manifest`;
- `artifact_chunk`;
- `reconcile`.

For attempt operations:

- A2A `contextId` is bound to `dispatch_id`;
- `attempt_id` is inside the structured request;
- A2A task ID is persisted only as a transport mapping.

### 5.3 Deterministic interception

The managed Hermes GPT peer intercepts Fabric DataParts before ordinary agent-session dispatch.

The acceptor validates schema, identity, authority, workspace, idempotency, protocol, local policy, and write ownership before invoking a runner.

If a Fabric request falls through to generic LLM handling, the request is a protocol failure and cannot count as verified Fabric execution.

## 6. Protocol version negotiation

v0.8 supports Fabric major version 1.

Before verified placement/dispatch:

1. coordinator probes the managed peer;
2. supported major versions/features are intersected with coordinator policy;
3. unknown major or missing required feature fails closed;
4. selected version and feature set are written into the coordinator attempt record;
5. peer binds the same negotiation into accepted attempt state.

Rules:

- no silent downgrade to generic A2A;
- no fallback from failed Fabric v1 negotiation to unverified execution;
- evidence/artifact responses must match the negotiated attempt;
- unknown optional v1 fields may be ignored only when explicitly optional and bounded.

## 7. Canonical Fabric objects

Security-relevant objects use canonical JSON:

- UTF-8;
- sorted object keys;
- no insignificant whitespace;
- SHA-256 digest.

### 7.1 `hermes.fabric-dispatch/v1`

Required fields/categories:

- schema/version and required features;
- `dispatch_id`;
- `attempt_id`;
- workflow/stage/task lineage;
- `contract_sha256`;
- bounded objective/execution request;
- selected managed node/backend;
- execution requirements;
- authorization class;
- forbidden action classes;
- logical workspace identity;
- canonical read/write scope;
- expected checks/artifacts;
- capability snapshot digest;
- created/expiry/replay-bound timestamps;
- retry parent attempt when applicable;
- `write_scope_sha256` and `write_epoch` when write-capable.

Forbidden categories:

- bearer tokens;
- OAuth/API credentials;
- caller-chosen peer URL;
- caller-defined peer authorization ceiling;
- caller-chosen remote absolute path;
- unbounded prompts/log bodies.

### 7.2 `hermes.fabric-capability/v1`

Capability categories:

- peer/card identity and remote manifest digest;
- supported Fabric versions/features;
- safely observable Hermes GPT/Agent versions;
- OS/architecture;
- runner availability and confinement posture;
- provider/model identifiers;
- tool/browser/vision/GPU capabilities;
- artifact-transfer support/bounds;
- health state;
- hard capacity ceiling;
- soft current load;
- recent latency;
- optional grounded cost.

Each positive hard fact has provenance and freshness.

Provenance classes:

- `coordinator_observed`;
- `coordinator_policy`;
- `peer_attested`;
- `coordinator_derived`;
- `soft_hint`.

The coordinator joins remote facts with local policy and records an `effective_snapshot_sha256`.

### 7.3 `hermes.fabric-evidence/v1`

Required binding:

- dispatch/attempt identity;
- contract hash;
- managed peer identity;
- negotiated version/features;
- remote A2A task mapping where known;
- runner/backend;
- capability snapshot digest;
- effective authority/scope digest;
- bounded timestamps;
- peer terminal execution state;
- structured observed checks;
- artifact manifests;
- cancel/recovery lineage.

Evidence classes:

1. coordinator-observed transport fact;
2. managed-peer structured observation;
3. coordinator-verified artifact;
4. coordinator-local observation;
5. worker statement/handoff data.

Class 5 cannot prove completion.

### 7.4 `hermes.fabric-artifact-manifest/v1`

Minimum manifest fields:

- logical `artifact_id`;
- bounded logical name;
- dispatch/attempt identity;
- producer peer identity;
- producer runner/backend;
- media type where useful;
- size bytes;
- SHA-256;
- source-policy result;
- transfer eligibility;
- creation timestamp.

Remote absolute path is never included in client-facing metadata.

## 8. Capability freshness and identity

Rules:

- stale or unknown positive hard requirements evaluate as unavailable;
- coordinator policy caps the maximum acceptable age of peer facts;
- peer-provided expiry can shorten but cannot lengthen coordinator trust;
- card/identity drift invalidates the effective capability snapshot;
- write-capable dispatch performs a fresh identity/health check immediately before acceptance;
- stale soft hints are ignored or assigned the worst soft ranking bucket;
- capability advertisement never creates authorization.

## 9. Placement

### 9.1 Candidate construction

Candidates are local and enrolled managed remote execution targets that could satisfy the contract's execution shape.

### 9.2 Hard filters

A candidate is excluded for any unmet required condition:

- registry enrollment;
- live expected identity;
- compatible Fabric protocol/features;
- required freshness/health;
- authorization ceiling;
- allowed profile;
- public/high-impact action posture;
- runner/provider/model allowlist;
- tool/browser/vision/GPU requirements;
- logical workspace mapping;
- confinement posture;
- artifact-transfer requirement;
- hard concurrency/capacity;
- forbidden action class;
- unresolved write claim/uncertain prior writer.

### 9.3 Explicit placement

Explicit node/backend selection skips ranking only. It still passes every hard filter.

### 9.4 Automatic ranking

Eligible candidates are ranked with `fabric-router-v1`, lower tuple wins:

1. locality/artifact-affinity penalty;
2. specialized-hardware fit penalty;
3. load/capacity bucket;
4. recent-latency bucket;
5. optional grounded-cost bucket;
6. stable `(node_name, backend)` tie-break.

A placement decision records:

- router policy ID;
- requirements digest;
- all candidate exclusions/reason codes;
- eligible candidates;
- ranking tuples/material inputs;
- selected target;
- capability snapshot digest/age.

Conversational A2A `best` is never used.

## 10. Logical workspace model

Contracts reference a logical workspace identity, not a peer-local absolute path.

Flow:

1. coordinator checks that selected node has an approved mapping;
2. mapping identity/revision is placed in the bounded request;
3. peer resolves local path from its server-owned configuration;
4. local allowed-path/denied-secret-path/symlink/confinement rules run;
5. mapping revision/digest is bound into peer attempt state.

Caller-provided remote absolute paths fail before runner invocation.

## 11. Durable coordinator journal

Use a transactional durable store with atomic uniqueness and compare-and-set transitions. Python standard-library SQLite is an acceptable v0.8 implementation.

Logical records:

### `dispatch`
- `dispatch_id` primary key;
- workflow/stage/task lineage;
- contract hash;
- requirements digest;
- logical write scope digest where applicable;
- coordinator state;
- timestamps.

### `attempt`
- `attempt_id` primary key;
- dispatch ID;
- sequence;
- node/backend;
- envelope digest;
- capability digest;
- authority/scope digest;
- protocol/features;
- A2A task mapping;
- write epoch;
- operational state/reason;
- cancel/recovery lineage;
- timestamps.

### `write_claim`
- write-scope digest primary identity;
- owning dispatch/attempt;
- monotonically increasing epoch;
- ACTIVE/RELEASED;
- release reason/timestamps.

The journal must be loaded before retry/placement decisions after process restart.

## 12. Durable peer journal

The peer journal is independent of upstream A2A TaskStore retention.

Before write-capable runner start, one durable transaction must:

- accept/validate attempt identity;
- detect idempotent replay or conflict;
- bind contract/envelope/version/capability/authority/workspace digests;
- acquire peer-local write claim;
- persist write epoch;
- commit accepted state.

Only then may mutation begin.

Peer journal records runner job identity/state where available.

If peer restart loses the A2A task but journal/runner state survives, `status`/`reconcile` uses the peer journal.

If runner state cannot be proven terminal after restart, peer state becomes `LOST_AMBIGUOUS` and the write claim stays ACTIVE.

## 13. Identity and idempotency

- `dispatch_id` is stable for one logical execution intent;
- `attempt_id` is unique for one actual attempt;
- retries get new attempt IDs;
- exact `(dispatch_id, attempt_id, envelope_sha256)` replay returns existing state;
- conflicting content under an existing attempt identity is rejected;
- contract/request changes create new dispatch lineage;
- remote A2A task ID never substitutes for Fabric identity.

## 14. Write ownership

### 14.1 Write scope

For write-capable work, the coordinator computes canonical `write_scope_sha256` from the logical writable scope granted by the Work Contract.

The scope must be independent of peer-local absolute path so it serializes equivalent logical writes across candidate nodes.

### 14.2 Non-expiring write claim

Fabric does not use a time-expiring lease to authorize replacement writers.

Coordinator:

- permits one ACTIVE claim per logical write scope;
- assigns a monotonically increasing epoch to each successfully acquired claim;
- refuses a new write attempt while an earlier claim is ACTIVE or ambiguous;
- does not release a claim because time elapsed, network failed, coordinator restarted, peer became unreachable, or cancel was merely requested.

Peer:

- persists a local active claim before runner start;
- rejects duplicate active local scope;
- rejects stale/lower epoch;
- does not release on A2A task loss.

### 14.3 Release safety

Automatic release requires reconciled terminal proof that the prior runner can no longer mutate.

The epoch is an audit/stale-command fence only. Ordinary filesystems do not enforce it, so a newer epoch is never treated as proof that an older writer stopped.

Irreconcilable ownership becomes `BLOCKED_WRITE_OWNERSHIP`.

v0.8 has no automatic force-release. External operator intervention must establish old-writer termination/isolation and normal reconciliation must then observe a safe terminal condition before Fabric retries.

## 15. Operational state machines

Fabric operational states are not Work Contract verdicts.

### 15.1 Coordinator attempt states

- `PLANNED`
- `SUBMITTING`
- `SUBMISSION_AMBIGUOUS`
- `SUBMITTED`
- `RUNNING`
- `CANCEL_REQUESTED`
- `CANCEL_AMBIGUOUS`
- `RECONCILING`
- `TERMINAL_REPORTED`
- `EVIDENCE_PENDING`
- `VALIDATING`
- `COMPLETED`
- `FAILED`
- `CANCELLED`
- `BLOCKED`

Legal high-level transitions:

```text
PLANNED -> SUBMITTING
SUBMITTING -> SUBMITTED | SUBMISSION_AMBIGUOUS
SUBMITTED -> RUNNING | CANCEL_REQUESTED | RECONCILING | TERMINAL_REPORTED
RUNNING -> CANCEL_REQUESTED | RECONCILING | TERMINAL_REPORTED
SUBMISSION_AMBIGUOUS -> RECONCILING
CANCEL_REQUESTED -> CANCELLED | CANCEL_AMBIGUOUS | TERMINAL_REPORTED
CANCEL_AMBIGUOUS -> RECONCILING
RECONCILING -> SUBMITTED | RUNNING | TERMINAL_REPORTED | CANCELLED | BLOCKED
TERMINAL_REPORTED -> EVIDENCE_PENDING
EVIDENCE_PENDING -> VALIDATING | BLOCKED
VALIDATING -> COMPLETED | FAILED | BLOCKED
```

### 15.2 Peer attempt states

- `RECEIVED`
- `ACCEPTED`
- `RUNNING`
- `CANCEL_REQUESTED`
- `SUCCEEDED`
- `FAILED`
- `CANCELLED`
- `LOST_AMBIGUOUS`

Peer `SUCCEEDED` means runner execution terminated as success. It never means Work Contract satisfied.

Illegal/unknown transitions are rejected and audited.

## 16. Submit timeout and recovery

Submit flow:

1. persist coordinator attempt and any required write claim;
2. set `SUBMITTING`;
3. send `accept`;
4. bind returned A2A task mapping when known;
5. advance to `SUBMITTED`/`RUNNING` based on observed state.

If submit times out:

- attempt becomes `SUBMISSION_AMBIGUOUS`;
- do not blindly resubmit;
- try current A2A context/task recovery;
- query deterministic peer `status`/`reconcile` by Fabric IDs;
- if one matching durable attempt is proven, bind/recover the same attempt;
- if no unique safe answer exists, remain ambiguous/blocked.

A write-capable ambiguous attempt keeps its write claim.

A read-only ambiguous attempt may be retried under a new attempt ID only if read-only authority/confinement is independently established and duplicate observation work is acceptable to the contract.

## 17. Cancellation

Cancellation is attempt-specific.

Coordinator:

1. transactionally records `CANCEL_REQUESTED`;
2. sends Fabric `cancel`;
3. polls/reconciles durable peer state;
4. records `CANCELLED`, terminal completion race, or `CANCEL_AMBIGUOUS`.

Peer:

1. transactionally records cancel intent;
2. invokes runner cancellation where supported;
3. observes runner state;
4. records terminal or `LOST_AMBIGUOUS`.

A2A `CancelTask` may assist transport cancellation. It does not release a write claim by itself.

No replacement write starts until terminal safety is proven.

## 18. Coordinator restart

On startup/recovery:

1. load coordinator journal before dispatching Fabric work;
2. find nonterminal attempts;
3. restore ACTIVE write claims;
4. compare Swarm/contract stage state to Fabric attempts;
5. re-probe identity/capability when required;
6. poll/reconcile peer durable state;
7. block any unresolved ambiguity;
8. never auto-mark a Work Contract satisfied.

This preserves the existing fail-closed recovery posture.

## 19. Peer restart

On peer startup:

1. load peer journal before accepting Fabric write work;
2. restore active local write claims;
3. reconnect durable runner observations where supported;
4. accept idempotent status/reconcile queries even if A2A TaskStore lost the original task;
5. mark irrecoverable active attempts `LOST_AMBIGUOUS`;
6. keep their write claims ACTIVE until terminal safety is established.

## 20. Evidence admission

Coordinator admits remote evidence only when:

- schema/version is supported;
- dispatch/attempt/contract identities match exactly;
- managed peer identity matches registry/current trust;
- negotiated features match the attempt;
- capability/authority/scope digests match;
- evidence is bounded/redacted;
- check/artifact lineage is structurally valid;
- required artifact verification passes.

Remote verdict strings are never mapped directly to Work Contract satisfaction.

Missing, malformed, wrong-lineage, stale, or unprovable required evidence makes validation inconclusive/failed according to existing Work Contract semantics.

## 21. Artifact transfer and admission

### 21.1 Producer-side export

Peer artifact source must:

- belong to the approved attempt/workspace;
- be a regular file;
- remain under allowed mapped roots;
- not resolve through symlink escape;
- not match denied secret/credential paths;
- satisfy configured extension/media and size policy;
- have a computed SHA-256;
- be registered to the attempt artifact set before transfer.

### 21.2 Manifest first

Coordinator requests `artifact_manifest` and validates metadata before bytes.

### 21.3 Coordinator-pulled chunks

Coordinator requests `artifact_chunk` using only:

- attempt identity;
- artifact ID;
- offset;
- bounded length.

Peer resolves artifact ID from its own attempt artifact set. Caller never supplies a remote path or arbitrary URL.

### 21.4 Consumer-side admission

Coordinator:

- writes to temporary bounded storage;
- rejects overflow/incomplete transfer;
- computes SHA-256 during/after receive;
- verifies declared size/digest;
- atomically promotes only after complete verification;
- discards rejected temporary bytes;
- records admission/rejection event.

Large artifacts beyond configured v0.8 transfer policy remain remote with explicit `TRANSFER_LIMIT` metadata. They are not partially admitted.

## 22. Event lineage

Coordinator writes bounded Fabric events for:

- capability probe/update;
- identity drift;
- placement decision;
- dispatch planned/submitting/submitted/ambiguous/recovered;
- peer state transition;
- write claim acquire/release/block;
- cancel request/result;
- reconcile request/result;
- evidence received/admitted/rejected;
- artifact manifest/transfer/admission/rejection;
- Work Contract validation verdict;
- review/final approval linkage.

Minimum event binding:

- event ID/time;
- dispatch/attempt ID where applicable;
- node/backend safe identifiers;
- old/new state;
- bounded reason code;
- relevant digest references.

No bearer token, credential, remote absolute path, artifact bytes, or unbounded worker output enters Event History.

## 23. Flight Deck

Read models expose:

- managed node name;
- identity/health/freshness;
- capability summary;
- active capacity/load;
- local/remote stage placement;
- explicit/auto placement;
- placement explanation/exclusions;
- dispatch/attempt/A2A task identity mapping;
- operational state;
- authority/scope summary;
- evidence/artifact summary;
- write ownership state;
- timeout/recovery/cancel ambiguity;
- blocked reason.

Any cancel/retry/reassign/stop control continues through gated server-side `hermes_*` actions. The browser does not gain a direct remote mutation API.

Streaming/push is optional UX. Polling plus journals remains sufficient.

## 24. Backward compatibility

Required:

- existing local Work Contracts unchanged;
- existing Swarms unchanged;
- explicit `fleet`, `pi_rpc`, `omx`, and `codex` backends unchanged;
- contracts omitting Fabric behavior retain documented compatibility behavior;
- Operator/Owner gates remain authoritative;
- secret-path policy remains authoritative;
- final human Swarm approval remains unchanged.

Fabric `auto` and verified managed remote placement are additive.

## 25. Threat boundary

Fabric is designed to defend against:

- malformed/untrusted agent input;
- caller URL/token/authority injection;
- stale capability routing;
- policy/identity drift;
- accidental duplicate execution;
- timeout/restart ambiguity;
- buggy or overclaiming workers;
- wrong-lineage evidence;
- artifact traversal/hash/bounds/secret failures;
- cancel/retry races;
- UI mutation bypass.

Fabric cannot cryptographically prove that a fully compromised remote OS truthfully reports its own filesystem, process state, or locally generated evidence if that OS controls the runtime credentials.

v0.8 does not claim hardware remote attestation.

## 26. G2 architecture review verdict

The G1 decision list is resolved:

1. transport: A2A v1.0 accepted;
2. managed peer: deterministic acceptor required;
3. interfaces: additive Fabric-specific distributed interfaces;
4. coordinator journal: transactional durable schema/state accepted;
5. peer journal: durable accept-before-write accepted;
6. identity/idempotency: dispatch/attempt/task mapping and replay semantics accepted;
7. node registry/authority: server-controlled registry accepted;
8. capability trust: provenance/freshness/digests accepted;
9. placement: hard filters plus deterministic `fabric-router-v1` accepted;
10. remote workspace: logical mapping accepted;
11. evidence: coordinator-owned verdict and admissibility classes accepted;
12. artifacts: manifest plus coordinator-pulled bounded A2A chunks accepted;
13. cancellation/retry: attempt-specific cancel plus non-expiring write claims/epochs accepted;
14. recovery: coordinator/peer restart and task-loss behavior accepted;
15. events/UI: bounded coordinator lineage/read models accepted;
16. compatibility: explicit version negotiation/no downgrade/local compatibility accepted;
17. threat model: compromised-peer boundary accepted.

Architecture-level blockers are resolved into explicit mechanisms and fail-closed states.

This does not close security risk. G3 #30 must adversarially attack these assertions before any G4 implementation is authorized.
