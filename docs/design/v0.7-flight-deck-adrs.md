## ADR-001 — Durable encrypted token storage (D1)

**Status:** Proposed (recommendation A; ratification at G1/G2 by Tony + legal)

**Context.** OAuth credentials are memory-backed today; restarting Hermes GPT
invalidates all issued credentials and requires the connector to re-authorize
(`docs/oauth.md`). This is the largest continuity caveat against the
"durable" thesis component.

**Decision.** Ship durable encrypted token storage in v0.7 (brief D1 Option A).

- New module `token_store.py`; envelope at
  `<hermes_data>/secrets/hermes_gpt_tokens.json` (0600).
- AES-256-GCM encryption (new required dependency `cryptography`).
- Key management precedence: OS keyring (`keyring` lib, optional dependency) →
  key file `<hermes_data>/secrets/hermes_gpt_token_key` (0600, created on
  first use) → env `HERMES_GPT_TOKEN_MASTER_KEY` (CI/test only, documented
  weakest).
- Rotation via `kid`; revocation deletes the envelope (optionally rotates key);
  revocation administration through owner-gated `hermes_oauth_revoke` (pending
  legal sign-off, else documented manual path).
- No token material ever in audit records or MCP responses.

**Alternatives considered.**

- B (memory-backed, documented): cheaper, smaller surface, but the "durable"
  claim stays qualified and restart re-authorization remains for another
  release.
- C (defer): lowest risk; continuity gap persists into v0.8.

**Consequences.**

- New dependency; must pass package hygiene and security review (legal).
- Restart no longer invalidates credentials; revocation becomes a real,
  audited operation.
- If legal or Tony rejects A, the design degrades to B without touching any
  other pillar: slice S5 is dropped, `oauth.md` documents re-authorization as
  intentional, and the research-package caveat remains disclosed.

**Evidence.** `oauth_auth.py` (memory-backed stores, MAX_* caps),
`docs/oauth.md` ("Durable encrypted token storage … separate future features"),
research §3.3/§5.6.

## ADR-002 — Flight Deck UI shape (D2)

**Status:** Proposed (recommendation A; ratification at G1/G2)

**Context.** The root card lists "Flight Deck UI integration". The research
brief identifies three shapes: theme-only MCP surface, read-only dashboard, or
interactive dashboard. The media lane (t_dd366ab6) is tasked with interaction
design and must align with the architecture.

**Decision.** "Flight Deck" is the **control-plane release theme**; the
trusted-client MCP surface is the UI (brief D2 Option A).

- No new server-rendered dashboard in v0.7 by default.
- A **read-only presentation contract** (§9.2 of the architecture document)
  defines what a Flight Deck UI may render: bounded Mission Control JSON,
  `hermes_events_*`, contract/swarm status surfaces. Any dashboard built later
  is a thin consumer of the same view models with **no new authority**.
- Media designs wireframes and flows against this contract; implementation
  slice S8 (optional) consumes it only if Tony/legal approve and media flags no
  conflicts.

**Alternatives considered.**

- B (read-only dashboard): real visual deck, medium effort, still no new
  authority; deferred unless media/positioning justify it.
- C (interactive dashboard): highest effort/risk; rejected for v0.7 (R6 scope
  creep, needs separate design + security review).

**Consequences.**

- Fastest path; zero new attack surface; keeps the v0.6 posture.
- Media's design package must explicitly target the presentation contract;
  conflicts flagged on the media card.

**Evidence.** Research §5.5-Q2, §5.6-D2, risk R6, root card pillar list,
media card t_dd366ab6 body.

## ADR-003 — Review-accept writer authority (D3)

**Status:** Proposed (recommendation A; ratification at G1/G2)

**Context.** v0.6 shipped a fail-closed contract validator with no production
review-accept writer; accepted evidence is (1) an audit record of
`hermes_contract_validate` by a distinct reviewer, or (2) a human approval
reference. The v0.7 review-evidence pillar must add a write path without
weakening independence.

**Decision.** Owner-gated review-accept writer (brief D3 Option A).

- New tool `hermes_review_accept(...)`: requires `owner` level + direct apply
  mode + `confirm`, is audited, and writes a ReviewAcceptanceRecord (§6.2).
- Distinct-reviewer rule enforced **in code at write time** (`reviewer !=
  assignee`) and re-checked at validate time; self-review rejected both ways.
- Evidence is referenced (`evidence_refs`), never copied; raw prompts and
  transcripts never stored.
- `operator_contract._check_review` reads the new store as an additional
  evidence source while keeping the existing two paths (backward compatible).

**Alternatives considered.**

- B (workspace-level distinct reviewer writes directly): faster/more
  autonomous; higher abuse risk; rejected for v0.7 (keeps the swarm final-human
  philosophy).
- C (human-only external approval reference): keeps v0.6 behavior; adds no
  writer; rejected because the pillar explicitly requires closing the gap.

**Consequences.**

- Closes the single named verification gap; S2 success criterion satisfiable
  through a production tool.
- Requires adversarial tests (self-review rejected, distinct reviewer enforced,
  bounded verdict vocabulary) and legal review of the independence model.

**Evidence.** `operator_contract.py` `_check_review` (lines 692–735),
`docs/release-notes-v0.6.0.md` limitation, research §3.4/§5.4-R3/§5.6-D3.

## ADR-004 — Event history surface (D4)

**Status:** Proposed (recommendation A; ratification at G1/G2)

**Context.** Event history is fragmented across swarm-workflows JSON, codex-jobs
JSON, cron executions.db, kanban task_events, and the operator audit JSONL.
There is no unified queryable timeline.

**Decision.** New `hermes_events_*` read surface (brief D4 Option A),
implemented as a **read-model aggregator**:

- `operator_events.py` normalizes the existing durable stores into the
  EventRecord view schema (§6.3) at query time; **no parallel write path** is
  introduced in v0.7 (ADR-005).
- Tools: `hermes_events_query`, `hermes_events_tail`; both `read_only`,
  allowlisted via `HERMES_GPT_EVENTS_ALLOWED_SOURCES` (unset = all, list =
  only listed, empty = none), bounded caps, retention window
  (`HERMES_GPT_EVENTS_MAX_AGE_DAYS`, default 90, legal review), and Mission
  Control redaction invariants.

**Alternatives considered.**

- B (extend Mission Control with an events surface): simpler registration but
  bloats the overview and couples two concerns; rejected — a dedicated
  namespace keeps the allowlist orthogonal.
- C (document existing stores): cheapest, but does not answer "what happened,
  in order, to which work" from one surface; rejected.

**Consequences.**

- One redaction contract for the whole timeline; no new mutation surface; no
  data duplication.
- Query cost is bounded by source-scan caps; tests must prove no-raw-body and
  truncation behavior.

**Evidence.** Research §3.5, §5.6-D4; Mission Control allowlist semantics in
`operator_mission.py` / AGENTS.md.

## ADR-005 — Event timeline is a derived read-model, not a write-through ledger

**Status:** Proposed.

**Context.** A write-through event ledger (emit at every transition) would give
a single queryable store but requires instrumenting every domain transition and
maintaining a second source of truth alongside the audit log and per-domain
stores, with divergence risk.

**Decision.** The event surface is **derived**: it normalizes existing durable
stores at query time into the EventRecord schema. Sources are the operator
audit JSONL, swarm-workflows JSON, codex-jobs JSON, cron executions.db, and
kanban task_events (read-only SQLite/file reads). A small in-process cache with
TTL mirrors Mission Control's approach.

**Consequences.**

- No new write path, no divergence, no migration; v0.6 sources remain
  authoritative.
- If a future release needs write-through (e.g. for cross-machine), the seam is
  the `EvidenceProvider` interface (ADR-008); the read-model stays valid.

**Evidence.** `operator_mission.py` caching/allowlist design; research §3.5.

## ADR-006 — Review evidence and token stores: locations and hygiene

**Status:** Proposed.

**Context.** New durable stores must follow the repo's atomic-write, redaction,
and secret-path hygiene conventions.

**Decision.**

- Review acceptances: append-only JSONL at
  `<hermes_data>/review-evidence/review-acceptances.jsonl`, atomic
  tmp-write+replace per record, 0600 (contains identity + references only, no
  bodies).
- Tokens: encrypted envelope at `<hermes_data>/secrets/hermes_gpt_tokens.json`
  (0600) per ADR-001; the `secrets/` directory is added to the denied-path
  policy for all tools.
- Both stores are created lazily; neither is included in package data; both
  are covered by retention policy (review: 30d+, legal review).

**Evidence.** `operator_policy.py` DEFAULT_DENIED_BASENAMES, atomic write
pattern in `operator_swarm._save_workflow`, retention-policy.md.

## ADR-007 — Restart reconciliation is fail-closed, never auto-advancing

**Status:** Proposed.

**Context.** Swarm workflow state persists but advancing a stage after a
restart is manual; OAuth credentials are lost (until ADR-001). Auto-resuming
work after a crash risks double-execution and contradicts the observed-state
philosophy.

**Decision.** A thin `operator_recovery.py` runs on startup (and via the
existing `hermes_operator_recover` surface, dry-run-first) that:

- marks swarm stages found in `running` as `blocked` with
  `reason: interrupted_by_restart`;
- reloads the durable token envelope and verifies integrity;
- reports a bounded reconciliation summary.

It **never auto-advances or auto-dispatches** work; the operator explicitly
re-advances through the existing gated `hermes_swarm_stage_advance`.

**Consequences.**

- Restart-safe continuity without weakening evidence rules.
- `hermes_swarm_stage_advance` becomes idempotent for already-validated stages
  (re-advance returns current state instead of erroring), so recovery is
  simple and safe.

**Evidence.** `operator_swarm.py` stage statuses (`running`, `validated`,
`done`, `blocked`), `operator_diagnostics.py` recover tool, research §3.2/§3.3.

## ADR-008 — Cross-machine swarm: interfaces only, validated by a local fake

**Status:** Proposed (stretch; matches brief).

**Context.** Cross-machine swarm execution is stretch. The honest seam is the
existing A2A fleet dispatch, but the swarm validator reads host-local observed
state only. Remote execution must not be implemented in v0.7.

**Decision.** Define two `typing.Protocol` interfaces in `seams.py`:

- `DispatchAdapter` — `dispatch/poll/collect` work orders; local impl today,
  A2A fleet adapter tomorrow.
- `EvidenceProvider` — `collect(contract_sha256, task_id, host)`; local
  host-state impl today, remote observed-state collector tomorrow.

Authority propagation stays in the work-order envelope (existing
`operator_fleet`). Validation is a **two-process-one-host fake** test that
exercises both interfaces over loopback; no remote behavior is promised.

**Consequences.**

- Seam interfaces are real code with a passing test; cross-machine stays
  unimplemented and unclaimed.
- Future cross-machine work composes into the existing architecture without
  rework.

**Evidence.** `operator_fleet.py` work orders, research §3.8, §5.4-R7.
