# v0.9 — Deterministic placement scoring (filter-and-score over the capability manifest)

Implements architecture proposal §8.2 ("Where") / D7 / §17 item 5, sibling card
`t_167ac591`. It is the **WHERE-to-run** decision for a plan-node work unit: a
deterministic, auditable filter-and-score over the derived capability-manifest
index (`operator_capability_manifest`).

## Scope and boundary

- **Dry-run only.** This slice never assigns, never dispatches, never mutates a
  Mission or a plan node's lifecycle, and never performs an action. Every
  decision returns `would_assign=false` and records `assigned_agent="auto"`
  distinct from the stage/plan-node `owner`. The controller *proposes*; actual
  dispatch goes through the existing `hermes_contract_dispatch` /
  delegation / fleet authority surfaces (authority is never overridden).
- **Deterministic (D7).** No LLM in the scoring hot path; only bounded
  arithmetic over manifest data. The same inputs always produce the same
  decision (`candidate_set`, `score_breakdown`, `filter_optouts`,
  `top_candidate`, `decision_sha256`).
- **Auditable (D7 / AC-7).** Every decision records `score_breakdown` +
  `candidate_set` + `filter_optouts`; when the operator policy allows a direct
  write it is also persisted in `placement_decisions` in
  `missions/missions.db`, and every public call is audited (bounded summary).
- **No candidate passes ⇒ `no_capable_target`.** The candidate set is empty
  after the hard filters; the decision classifies `no_capable_target` and
  records a *stubbed* escalation (`would_raise_signal: capability`,
  `path: stubbed`) — the escalation is never executed here.

## Inputs

The planner reads the derived capability-manifest index built by
`operator_capability_manifest` (Fabric node registry + Fleet authority manifest
+ profile toolsets/skills + provider registry). Each manifest entity is
normalized into a placement `target` with the fields the filter/score consume
(`enabled`, `reachable`, `identity_configured`, `authorization_ceiling`,
`allowed_profiles`, `features`, `workspaces`, `backends`, `skills`, `model`,
`provider`, `host_role`, `allow_public_actions`). Fields a source does not
carry degrade to a neutral default and are recorded as a `caveat`
(e.g. `authorization_ceiling_unavailable`, `workspace_scope_unavailable`),
which guarantees determinism instead of failing open or silently skipping.

For a plan node the **requirement** is derived from its `capability_req`
(`profile`, `skills`, `authorization_class`) plus its bounded `budget`
(`est_minutes` / `est_tokens`), its `kind`, and its `owner`. Optional
`features` / `workspace` / `backends` constraints may be supplied by the caller.

## Hard filters (any fail ⇒ excluded; reason recorded in `filter_optouts`)

| # | Filter | Opt-out code | Semantics |
|---|--------|--------------|-----------|
| F1 | enabled + reachable + identity | `disabled` / `unreachable` / `identity_unconfigured` | target must be enabled, reachable, and carry a configured identity |
| F2 | required features/operations present | `required_features_missing` | `requirement.features ⊆ target.features` |
| F3 | authorization ceiling not exceeded | `auth_ceiling_exceeded` | `rank(target.authorization_ceiling) >= rank(requirement.authorization_class)`; unknown ceiling passes but records `authorization_ceiling_unavailable` |
| F4 | profile in scope | `profile_out_of_scope` | `requirement.profile ∈ target.allowed_profiles` |
| F5 | workspace in scope | `workspace_out_of_scope` | when the target declares workspaces, `requirement.workspace` must be present; when unknown it passes with `workspace_scope_unavailable` |
| F6 | per-profile concurrency headroom | `concurrency_full` | when concurrency data is present, `in_progress < max_in_progress`; `max_in_progress == 0` treats the profile as unlimited |
| F7 | forbidden-action policy | `forbidden_action` | a `forbidden_actions` context containing `public` excludes targets that `allow_public_actions` |

## Soft scores (0–1 among survivors; deterministic weights)

| Dimension | Weight | Definition |
|-----------|--------|------------|
| `capability_fit` | 0.30 | fraction of required `features` covered, or `1.0` for an executor kind (profile/fabric node) when no feature list is given (`0.4` for provider/peer) |
| `authorization_match` | 0.20 | prefer *just-enough*: `1.0` at exact ceiling, decays `max(0, 1 − 0.4·excess)` as the target is over-privileged; `0.5` (neutral) when the ceiling is unknown |
| `affinity` | 0.15 | fraction of required `skills` the target *owns*; when no skill list, `1.0` for the manifest owner of the profile, else `0.5` |
| `load_headroom` | 0.15 | `1 − in_progress/max_in_progress`, clamped to `[0,1]`; `1.0` when no concurrency data (neutral idle) |
| `health` | 0.10 | derived reputation from `task_runs` outcomes (`success_rate`); `0.5` neutral when absent or zero samples |
| `cost_priority` | 0.10 | fits the node's estimated spend within the mission budget envelope scaled by mission priority; `1.0` when no budget constraint |

`total = Σ weight_i × score_i`, and survivors are ranked by
`(total desc, authorization_excess asc, entity_id asc)` — fully deterministic
so identical inputs order identically regardless of input ordering.

## Decision record

```
{
  schema, schema_version,
  mission_id, node_id,
  requirement,            # bounded; no raw objective / prompt / secret (INV-9)
  classification,         # assigned | no_capable_target | human_approval
  assigned_agent,         # "auto" (distinct from owner) | "owner" | ""
  owner,                  # the stage/plan-node owner (never auto)
  top_candidate,          # entity_id + name + kind + total (or null)
  candidate_set,          # survivors with per-candidate scores
  score_breakdown,        # per-candidate dimension scores + total + caveats
  filter_optouts,         # excluded candidates → list of opt-out codes
  decision_sha256,        # content-addressed digest of requirement + verdict
  would_assign: false,    # dry-run: never a dispatch
  escalate,               # {would_raise_signal, classification, path:"stubbed"}
}
```

**INV-9** holds: only refs, bounded metadata, and content-addressed hashes cross
the surface. A redaction check rejects secret-like requirement input, and
free-text fields are sanitized (`[REDACTED]`). No raw prompt, transcript,
memory body, credential, or secret-path content is stored or emitted.

## Verification

See `test_operator_placement.py` (25 tests): determinism (same inputs → same
output + digest), every hard filter, every soft score and tie-break,
`no_capable_target` + stubbed escalation, approval-node `human_approval`
classification, `assigned_agent=auto` ≠ `owner`, INV-9 containment, and the
read-only / dry-run no-side-effect guarantee (no durable rows, no content-file
writes). Connector surface acceptance reports the merged tool count (129).
