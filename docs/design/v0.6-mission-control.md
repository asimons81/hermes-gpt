## 1. Purpose

This document is the technical design for the **Mission Control surface** of
Hermes GPT v0.6: a read-only, authenticated operational view of the entire
Hermes ecosystem (profiles, fleet agents, Codex jobs, cron activity, delegated
work, failures, pending approvals, health, and approved additional surfaces),
exposed to **trusted clients** — ChatGPT first, plus a programmatic API for
future trusted clients.

It is the design task referenced in the brief (`docs/releases/v0.6-brief.md` §9)
and consumed by the risk review (legal) and the integrated release plan
(default). It does **not** cover Work Contracts or Swarm Orchestration, which
are separate v0.6 capabilities with their own design work; Mission Control is
the **observability foundation** those capabilities build on.

**Acceptance (from the card):** a fresh engineer can estimate and implement
from this design without needing to re-interview the requester.

## 2. Design goals and non-goals

### Goals

- **G-MC1.** Provide one read-only surface through which a trusted client can
  answer "what is my entire Hermes fleet doing right now?" as a structured,
  bounded JSON document covering every required surface (or an explicit
  `unavailable` with a reason — success criterion S1).
- **G-MC2.** Authenticate and authorize trusted clients. Read-only
  observation must require no mutation privileges (S4) and no operator
  `apply_mode=direct`.
- **G-MC3.** Define stable view-model contracts (the JSON shapes) and a tool
  registry, so clients and downstream capabilities consume a contract, not
  ad-hoc scraping.
- **G-MC4.** Aggregate data that is fragmented today (per-profile `state.db`,
  cross-board kanban, ad-hoc delegated-work) without migrating any upstream
  schema (data inventory gaps G3, G6, G7).
- **G-MC5.** Provide a health snapshot derived from existing signals without
  requiring a metrics backend (G5).
- **G-MC6.** Respect every sensitivity class from the data inventory §5:
  never expose raw HIGH content; redact, summarize, or hash.
- **G-MC7.** Reuse the existing operator layer (`operator_*`, operator policy,
  audit log, redaction) rather than building a parallel subsystem.

### Non-goals (this design)

- **NG-MC1.** No write/mutation surfaces. Mission Control is read-only. Mutating
  actions (dispatch, cron run, approvals acting) remain in the existing
  operator toolset, gated exactly as today.
- **NG-MC2.** No new persistent store. Mission Control computes views from
  existing sources; any caching is ephemeral and in-process (see §8).
- **NG-MC3.** No upstream Hermes schema migration. Aggregation reads
  `mode=ro`; cross-board normalization happens in the view model (G3).
- **NG-MC4.** No public/unauthenticated exposure. This design specifies the
  authN/authZ model and the non-goals of remote deployment without real auth.
- **NG-MC5.** Not a UI. The design is an API/view-model surface; the desktop
  or web dashboard that might consume it is out of scope.
- **NG-MC6.** No OAuth provider implementation. Where ChatGPT requires a real
  OAuth layer, this design defines the boundary and interface but assumes the
  enforcement lives at the transport/edge (see §7).

## 3. Context: what exists today

### 3.1 The sidecar

`hermes-gpt` is a standalone FastMCP sidecar (`server.py`). It imports selected
Hermes Agent internals at runtime and exposes them as MCP tools, never
modifying Hermes Agent source. Tool registration is centralized in
`register_tools(server)` / `build_codex_mcp_server`.

Current tool groups:
- **Base read-only:** `hermes_read_file`, `hermes_search_files`,
  `hermes_memory` (search), `hermes_skill_list`, `hermes_skill_view`,
  `hermes_session_search`.
- **Env-gated:** write/patch, terminal, vision, web, memory-write.
- **Operator/Owner Mode** (`operator_*` modules, registered unconditionally,
  mutating ones refuse unless policy grants them):
  - policy/status/audit/doctor/snapshot/release-doctor/recover
  - fleet (list, status, dispatch, dispatch_work_order, task, result, authority_drift)
  - cron (list, status, create, run, pause, copy, move)
  - skills, config/env, gateway/workspace/git/owner, codex (`hermes_codex_*`).

### 3.2 The authN/authZ model today

- **Transport:** default bind `127.0.0.1`. Remote reach is only through a
  tunnel (e.g. cloudflared) with **"No Authentication"** — the README is
  explicit that remote/public release is not supported until real
  OAuth or another ChatGPT-compatible authentication layer is added. Operator
  Mode does **not** add auth; it is defense-in-depth, not a security boundary.
- **Authorization levels** (ordered, each includes the levels below it):
  `read_only` → `cron` → `skills` → `skills_config` → `workspace` → `owner`.
- **Apply model:** `HERMES_GPT_OPERATOR_APPLY_MODE` defaults to `dry_run`;
  mutation requires `direct` **and** the tool's `dry_run=False`.
- **Redaction:** config `get` redacts secret-looking keys; env tools never
  return values; prompts logged as `prompt_len` + `prompt_sha256`; denied
  paths (`.env`, `auth.json`, `mcp-tokens/`, `.ssh/`, `.aws/`, `vault/`,
  secret-looking filenames). `shell=False` everywhere; no `git add -A`/`push`.
- **Audit:** every operator action is written to
  `logs/hermes_gpt_operator_audit.jsonl` (2,491 records observed) with
  tool/level/apply_mode/dry_run/changed/success/error/summary/trace_id.

### 3.3 Data sources (from the inventory)

27 sources inventoried (`S01`–`S27`). The 8 required surfaces map to them as:

| Surface | Primary sources | Availability |
|---|---|---|
| Profiles | S01 (`~/.hermes/profiles/*`), `hermes profile list` | ✅ |
| Fleet agents | S02 gateway_state, S03 A2A registry/tasks, S04 authority manifest | ✅ (G2 conditional) |
| Codex jobs | S05 operator `codex-jobs/`, S06 `~/.codex` sessions, audit | ⚠️ G1 (conditional) |
| Cron activity | S07 jobs.json, S08 executions.db, S09 heartbeat/output | ✅ |
| Delegated work | S10/S11 `async_delegations`, kanban task_runs S15 | ⚠️ G6 (ad hoc) |
| Failures | S13 logs, S08 cron fails, S15 kanban errors, S14 audit, S16 vault deny | ✅ |
| Pending approvals | S17 interrupted_turns, S16 vault access_requests, S18 action-items, S19 approval-inbox | ⚠️ G4 (no canonical store) |
| Health | S02 gateway, S27 monitoring, doctor/snapshot, logs | ⚠️ G5 (derived) |

Additional approved candidates: Vault (S16, metadata only), memory (S20),
LCM (S12), session usage/cost (S10 `session_model_usage`), skills registry,
gateway channels (S23), operator audit trail (S14).

### 3.4 Gaps the design must handle (from inventory §4)

- **G1** operator Codex job store absent on host → conditional surface.
- **G2** fleet authority manifest absent → surface "not configured", don't fail.
- **G3** no cross-board kanban aggregation → glob `boards/*/kanban.db`, add
  board slug in view model.
- **G4** no canonical pending-approval store → adopt approval-inbox
  aggregation contract as the view.
- **G5** no structured health/metrics store → derive a health snapshot.
- **G6** delegated-work aggregation ad hoc → define the join + redaction.
- **G7** per-profile state fragmentation → enumerate profiles, open each
  `state.db` `mode=ro`.
- **G8** Codex transcripts unindexed/high-sensitivity → never expose raw
  transcripts; summaries only.
- **G9** `request_dump_*.json` raw/unredacted → **excluded** from the model.

## 4. Design overview

### 4.1 Shape of the surface

Mission Control is delivered as **a coherent group of MCP tools** (namespace
`hermes_mission_*`) plus a **defined view-model contract** (the JSON shapes).
This is the natural choice because ChatGPT is an MCP client and the existing
sidecar is already an MCP server; a REST/gRPC surface is out of scope
(NG-MC5) but the view-model contracts are transport-agnostic so a future
programmatic client can be layered on the same shapes.

Three layers:

1. **Aggregation layer** (`operator_mission.py`, new module): reads the
   sources `mode=ro`, normalizes, joins, redacts, and produces bounded view
   models. No writes, no schema migration, no secrets.
2. **Contract layer**: the view-model JSON schemas (§6) — stable, versioned.
3. **Surface layer**: `server.py` registers `hermes_mission_*` tools backed by
   the aggregation layer, each carrying operator-level authorization + audit.

```
                            ┌──────────────────────────────┐
                            │       Trusted client        │
                            │   (ChatGPT via MCP today;    │
                            │   future programmatic API)   │
                            └──────────────┬───────────────┘
                                           │ MCP (streamable-http / sse)
                                           ▼
┌───────────────────────────────────────────────────────────────┐
│                    hermes-gpt MCP sidecar                       │
│  server.py  register_tools() → hermes_mission_* tools          │
│   ├── operator_level / allowed_profiles authorization          │
│   ├── audit_record() on every mission call                     │
│   └── redaction / bounded output                               │
└───────────────┬───────────────────────────────┬───────────────┘
                │                               │
                ▼                               ▼
┌──────────────────────────┐   ┌──────────────────────────────────┐
│  operator_mission.py     │   │  existing operator_* modules     │
│  (NEW aggregation layer) │   │  policy/diagnostics/fleet/cron/  │
│  open read-only, join,   │   │  codex/workspace/config/skills   │
│  normalize, redact       │   └──────────────────────────────────┘
└───────────────┬──────────┘
                │  mode=ro reads of existing sources (no migration)
                ▼
   Hermes stores: state.db (main+profiles), cron/*, kanban boards,
   a2a/tasks.sqlite3, gateway_state.json, logs, audit, vault.db,
   memory_store.db, lcm.db, ~/.codex, interrupted_turns.json,
   action-items.json, approval-inbox aggregator
```

### 4.2 Tools

| Tool | Kind | Level required | Returns |
|---|---|---|---|
| `hermes_mission_overview` | composite | `read_only` | One bounded JSON: all surfaces summarized + `unavailable` reasons |
| `hermes_mission_health` | surface | `read_only` | Derived health snapshot |
| `hermes_mission_profiles` | surface | `read_only` | Profile list + per-profile operational summary |
| `hermes_mission_fleet` | surface | `read_only` | Fleet agents + A2A registry/tasks + authority state |
| `hermes_mission_codex` | surface | `read_only` | Codex jobs + native sessions (summaries) + health |
| `hermes_mission_cron` | surface | `read_only` | Cron jobs + executions + scheduler liveness |
| `hermes_mission_delegations` | surface | `read_only` | Delegated work + kanban runs (redacted) |
| `hermes_mission_failures` | surface | `read_only` | Failures across sources (bounded, recent) |
| `hermes_mission_approvals` | surface | `read_only` | Pending approvals (aggregated) |
| `hermes_mission_vault` | surface | `read_only` | Vault health + access-request queue (metadata only) |
| `hermes_mission_usage` | surface | `read_only` | Session usage/cost aggregates |
| `hermes_mission_audit` | surface | `read_only` | Recent operator audit records (redacted summaries) |

All are read-only: they require **no** `apply_mode=direct` and never mutate.
They run at operator level `read_only` (the default) — meaning Mission Control
observation works with the sidecar's safest posture. Individual sensitive
fields are additionally gated by the per-client surface allowlist (§7).

### 4.3 Design decisions (binding)

| # | Decision |
|---|---|
| D1 | **Namespace `hermes_mission_*`.** Distinct from existing tools; discoverable; matches brief language. |
| D2 | **Read-only enforced structurally.** Mission tools live in `operator_mission.py`, take no `dry_run`/`apply` args, never shell out to mutating paths. |
| D3 | **Level `read_only` suffices.** Observation must not require mutation privileges (S4). No `direct` apply mode. |
| D4 | **No new persistent store.** Views are computed on demand with an in-process TTL cache (§8). |
| D5 | **Aggregation is read-only by construction.** All SQLite opened `file:...?mode=ro`; directories enumerated; no writes. |
| D6 | **Contract-versioned output.** Every mission response includes `schema_version` and per-source `available: bool` + `reason` when unavailable. |
| D7 | **Redaction by class** (inventory §5): HIGH bodies never returned; MED aggregated; LOW as-is. §6.3 table. |
| D8 | **Board slug added in view model, not schema.** Cross-board normalization is a view-model concern (G3). |
| D9 | **`unavailable` beats failing.** Gaps surface as `available:false, reason:` rather than errors (G1, G2, G5). |
| D10 | **Every mission call is audited** via existing `op_policy.audit_record`. |
| D11 | **AuthN at the edge; authZ in the sidecar.** Transport auth (tunnel/edge) is out-of-scope enforcement; the sidecar enforces surface allowlists + redaction server-side regardless. |
| D12 | **Per-client surface allowlist** via new `HERMES_GPT_MISSION_ALLOWED_SURFACES` env (default: all read-only surfaces). Future OAuth scopes map onto the same allowlist. |

## 6. View-model contracts

### 6.1 Envelope (every response)

```json
{
  "schema_version": "0.6-mc.1",
  "success": true,
  "tool": "hermes_mission_health",
  "surface": "health",
  "generated_at": "2026-08-13T00:00:00Z",
  "available": true,
  "unavailable_reason": null,
  "counts": {"profiles": 9},
  "data": { "... surface-specific ..." },
  "warnings": [],
  "trace_id": "..."
}
```

- `available:false` + `unavailable_reason` is used for conditional surfaces
  (G1/G2/G5) and per-source partial failures (D9).
- `warnings` collects non-fatal per-source read issues (e.g. a profile
  `state.db` open failed) without failing the whole call.

### 6.2 Composite overview (`hermes_mission_overview`)

The S1 surface: one bounded document that answers "what is the fleet doing".
Each section is the summary form of its surface tool, plus a per-section
`available` flag.

```json
{
  "schema_version": "0.6-mc.1",
  "tool": "hermes_mission_overview",
  "surface": "overview",
  "generated_at": "...",
  "fleet_health": { "overall": "pass|warn|fail", "checks": {...} },
  "profiles": { "available": true, "count": 9, "gateway_served": 9, "active": [...names] },
  "fleet_agents": { "available": true, "peers": 1, "authority": "not_configured" },
  "codex": { "available": true, "operator_jobs": 0, "native_sessions": 5, "health": {...} },
  "cron": { "available": true, "jobs": 29, "enabled": 26, "failed_recent": 2, "scheduler_live": true },
  "delegations": { "available": true, "total": 40, "in_flight": 3, "completed": 29, "failed": 4, "unknown": 4 },
  "failures": { "available": true, "recent_error_count": 1, "top": [...] },
  "pending_approvals": { "available": true, "count": 2, "items": [...] },
  "vault": { "available": true, "credential_state": {"active":2,"invalid":1,"unknown":7}, "pending_requests": 0 },
  "usage": { "available": true, "sessions_24h": 12, "estimated_cost_24h_usd": 0.41 },
  "surfaces_unavailable": ["...", "..."],
  "trace_id": "..."
}
```

Bounds: the overview is size-capped (e.g. 64 KB default, hard cap; see §8.4).
Sections that would exceed their bound are truncated with
`"truncated": true, "count_total": N` and the caller is directed to the
specific surface tool for detail.

### 6.3 Redaction policy by sensitivity class (inventory §5)

| Class | Sources | Mission Control handling |
|---|---|---|
| PUBLIC-OK | monitoring status, desktop-build-stamp | return as-is |
| LOW | profile names/models, gateway platform state, cron names/schedules (no prompts) | return as-is |
| MED | cron executions (status/timestamps/errors), kanban task metadata, session_model_usage (tokens/cost) | aggregate; strip prompts; no full bodies; no raw `prompt`/`script`/`deliver` text; job `name` + `last_status` + `next_run_at` only |
| HIGH | message content, async_delegations task/result JSON, codex transcripts, operator audit summaries, profile auth.json/.env/SOUL/memories, vault credential metadata + audit chain, interrupted_turns prompts | **never raw**; summarize/redact/hash; per-surface allowlist; do not include bodies |

Concrete redaction rules:
- **Prompts anywhere** → `{prompt_len, prompt_sha256}` only (consistent with
  existing operator policy). Never the prompt text.
- **`async_delegations`** → `delegation_id`, `state`, `dispatched_at`,
  `completed_at`, origin/parent session id; **no** `task_json`/`result_json`
  bodies (G6).
- **Kanban runs** → task id, title, assignee, status, board slug, outcome,
  run error string (MED, may contain stack text); **no** `body`/`metadata`/
  full comments (G3/G6).
- **Codex** → job id, state, timestamps, workdir, model, exit status; native
  `~/.codex` sessions as count + latest activity only; **no** rollout
  transcripts (G8). G1 fallback documented.
- **Audit** → the existing audit record shape is already summary-based; return
  as-is but cap body length; never raw command stdout that was not already
  logged as a summary.
- **Vault** → metadata only (service/alias/status/lease); **never** credential
  payloads or keys; audit chain as allow/deny counts + recent denials (S16).

## 7. Authentication and authorization

### 7.1 Model: authN at the edge, authZ in the sidecar (D11)

- **Authentication (who is calling)**: enforcement lives at the transport
  boundary — loopback bind by default; for remote reach a VPN / Tailscale /
  private tunnel (e.g. cloudflared Access) is the authentication layer. This
  is consistent with the brief's constraint that Operator Mode is
  defense-in-depth, not a security boundary. **v0.6 does not ship an OAuth
  provider**; it defines the boundary and the authZ interface so one can be
  inserted later. This is flagged as an open question requiring Tony's
  call (§9 Q3) because ChatGPT's connector historically wants "No
  Authentication" at the MCP URL with the trust enforced by the tunnel/VPN.
- **Authorization (what each client may see)**: the sidecar enforces
  server-side, regardless of transport:
  1. Operator level `read_only` or higher is required for every `hermes_mission_*`
     tool (D3). This is the default, so observation works in the safest posture.
  2. **Per-client surface allowlist** (`HERMES_GPT_MISSION_ALLOWED_SURFACES`,
     D12). Default is all read-only surfaces. A deployment may restrict a
     client to a subset (e.g. health+profiles only). This allowlist is the
     seam where a future OAuth scope maps onto surfaces.
  3. **Class-based redaction** always applies (D7 / §6.3), so even an
     authorized client never receives raw HIGH bodies.
  4. No `apply_mode=direct` is ever consulted for mission tools — they are
     structurally read-only (D2).

### 7.2 Security boundaries

| Boundary | Enforcement | v0.6 status |
|---|---|---|
| Network | loopback bind default; warn on non-loopback | Today |
| Edge auth (who) | VPN / Tailscale / private tunnel (cloudflared Access) | Operates today as the real boundary; recommend Access-auth tunnel |
| Sidecar authZ (what) | operator level + `HERMES_GPT_MISSION_ALLOWED_SURFACES` | NEW in v0.6 |
| Redaction | class-based (§6.3) + bounded output (§8.4) | NEW in v0.6 |
| Audit | `audit_record` on every mission call | Reuses existing |
| Denied paths | `.env`, `auth.json`, `mcp-tokens/`, `.ssh/`, `.aws/`, `vault/`, secret-like | Existing operator policy |
| No mutation | structural (no apply/dry_run args, no mutating calls) | NEW in v0.6 |

### 7.3 Non-goals restated (security)

- **NG-MC4** — no public/unauthenticated exposure. A mission tool reached over
  an unauthenticated public URL is a misconfiguration, not a supported mode;
  `hermes_operator_status` will report `remote_without_auth` as a hard warning
  if the server detects a non-loopback bind, consistent with today's behavior.
- **NG-MC6** — no OAuth provider implementation in v0.6; boundary defined, flag
  for post-v0.6 or as a scoped sub-task if ChatGPT requires it.

## 8. Refresh / caching strategy

### 8.1 Source cadences

| Source | Cadence | Read cost |
|---|---|---|
| gateway_state.json | live (rewritten on change) | low |
| state.db / per-profile state.db | live per message | **high** (145k+ messages on host; opening many profiles) |
| cron jobs.json | rewritten on cron change | low |
| executions.db | append per run | low-medium |
| kanban boards | live per task/run | low-medium |
| a2a tasks.sqlite3 | live per task | low |
| audit jsonl | append per action | low |
| ~/.codex sessions | live per session | low (glob/count only) |
| logs | streaming/rotating | low-medium (tail) |
| vault/memory/lcm | live | low |
| interrupted_turns / action-items | live | low |

### 8.2 Strategy: compute-on-demand + bounded in-process TTL cache

- **Primary path: on-demand computation.** Each `hermes_mission_*` tool reads
  fresh sources. This guarantees the overview is never stale for the "what is
  the fleet doing right now" question (S1).
- **Per-surface TTL cache** for expensive aggregate reads, keyed by surface:
  - `profiles` and `delegations` (which open many `state.db`) — **TTL 15s**,
    since they are the most expensive (G6/G7).
  - `codex`, `failures`, `usage`, `vault` — **TTL 10s** (native session glob,
    usage sums).
  - `health`, `cron`, `fleet`, `approvals`, `audit` — **TTL 5s** (cheap,
    fast-changing).
  - `overview` — composes cached sub-views; TTL = min of dependencies (5s).
- **Cache is in-process, ephemeral (NG-MC2).** A simple dict
  `{surface: (expires_at, payload)}` in `operator_mission.py`. No disk, no
  cross-process cache. A `force_refresh: bool = False` tool arg bypasses the
  cache for interactive debugging.
- **Never cache secrets.** Cached payloads are already post-redaction
  (D7), so cache holds only redacted/bounded data.

### 8.3 Freshness contract

- Each response records `generated_at` and, when served from cache, a
  `served_from_cache: true` + `age_ms` field so clients can reason about
  freshness.
- A `meta` block lists per-source `read_at` timestamps so partial staleness is
  visible.

### 8.4 Bounded output

- Overview default size cap 64 KB, hard cap 128 KB.
- Surface tools default cap 256 KB, hard cap 512 KB.
- Lists truncate with `truncated:true, count_total:N`; callers page with
  `limit`/`offset` args where the tool supports them (delegations, failures,
  audit, usage).
- Token budget: an overview is designed to fit comfortably in ChatGPT's
  context without summarization — target ≤ ~16k tokens of rendered JSON.

### 10.4 Test plan outline

`test_operator_mission.py` (mirrors existing `test_operator_*.py` style, all
on a temp `hermes_root` fixture — no real production data):

1. **Envelope/contract**: every tool returns the envelope with
   `schema_version`, `success`, `available`, bounded size.
2. **Redaction**: prompts appear as `prompt_len`+`prompt_sha256` only; async
   delegation bodies never returned; kanban `body`/`metadata` stripped; codex
   transcripts absent; `.env`/`auth.json` never present.
3. **Conditional availability (D9)**: with no codex-jobs dir → `available:
   false, reason`; no fleet-authority manifest → `authority:
   not_configured`; missing profile → excluded with warning, not failure.
4. **Read-only guarantee**: monkeypatch / assert no `db.execute("...")` with
   write mode; all opens use `mode=ro` URI; no shell to mutating commands.
5. **Cross-board (G3)**: two fixture kanban boards → normalized with board
   slug; task ids unique.
6. **Per-profile aggregation (G7)**: fixture profiles with their own
   `state.db` → delegations/usage joined.
7. **Overview composition**: all sections present; per-section `available`;
   size cap enforced (force a large fixture → `truncated`).
8. **Cache**: second call within TTL returns `served_from_cache`; force_refresh
   bypasses; cache never holds raw bodies.
9. **Authorization**: with `HERMES_GPT_MISSION_ALLOWED_SURFACES=health`
   → other surfaces return an authorization denial (not a data error).
10. **Audit**: each mission call appends an audit record.
