# Autopilot (v0.13) — design + invariants

**Status:** PR1 (durable Autopilot runtime), PR2 (parallel DAG scheduler) and
PR3 (automatic node advancement) are implemented. PR4–PR11 below are the planned remainder of the slice; they
are not yet built. This
document is Step 0 of the build order and is the implementation contract every
later PR must be checked against.

**Lineage:** verified against code at commit `42ec9f1` (this repo has no PR #81 —
that reference does not resolve here; treat it as external). Grounded in direct
reads of `operator_job_supervisor.py`, `operator_mission_runtime.py`,
`operator_mission_plan.py`, `operator_controller.py`, `operator_skill_resolution.py`,
`operator_placement.py`, `operator_contract.py`, `operator_delegations.py`,
`operator_mission_budget.py`, `operator_live_events.py`, `operator_policy.py`,
`ui_missions.py`, `BOUNDARY.md`, `docs/missions.md`, `docs/delegations.md`,
`docs/live-events.md`.

## North star

One user objective drives Mission → Plan → capability validation → placement →
parallel execution → evidence → recovery → approval → completion, without a
human re-triggering every node by hand. Hermes GPT remains the sole authority
boundary throughout.

## Non-negotiable architecture rule

`BOUNDARY.md` already states this and it binds Autopilot exactly as it binds
the controller:

> "Reuse the existing Mission, Work Contract, Swarm, Fabric, Fleet, Delegation,
> Event/live-event, review, recovery, and policy primitives as peers. The
> controller layer is a caller, not a competing owner of any of these
> primitives." (`BOUNDARY.md:25-29`)

Autopilot is **one layer further out**: a caller of the controller/placement/
contract/delegation/budget/live-event surfaces, exactly as the controller is a
caller of Mission/Plan/Contract/Delegation. It must not become "a new execution
engine," "a second judge stack," "a separate evidence database," or "a second
gateway/command plane" — all explicitly on `BOUNDARY.md`'s do-not-rebuild list.
Concretely:

- No `autopilot_dispatch()`. Every node dispatch goes through the existing
  `hermes_placement_score` → `hermes_contract_define` →
  `hermes_contract_dispatch` / `hermes_delegation_dispatch` chain, gated by
  `operator_skill_resolution.validate_required_skills` exactly as
  `operator_mission_plan._validate_plan_skill_requirements` already gates plan
  creation.
- No second DAG/state store. `plan_nodes` (in `missions.db`) stays the only
  authoritative node-state table. Autopilot's own `autopilot_runs` store (PR1)
  holds orchestration metadata only — concurrency limits, replan counters,
  worker liveness — never a shadow copy of node/delegation state.
- No second approval mechanism. The Approval Frontier (PR4) is a *derived
  read* over `authorization_class` / Mission `awaiting_approval`, not a new
  gate; `hermes_mission_approve` remains the only way through it.
- No second scheduler-lease primitive where one already exists. `operator_job_supervisor`'s
  per-job-id record (register/mark_running/terminalize, one JSON file + one
  flock per job) is the reused "one worker owns this Mission" primitive for
  Autopilot's own process lifecycle (see PR1 below). `operator_controller`'s
  own `controller_pass_lease` table is untouched and is a *separate* lease for
  a *separate* thing (one reconcile pass), reused as-is when Autopilot calls
  the controller.

## Invariants (verbatim, code-grounded)

**No worker self-certifies completion**
- `docs/missions.md:62` — "Completion remains based on coordinator-observed
  evidence and explicit approval boundaries... unverified legacy success is
  reconciled fail-closed to `blocked`."
- `docs/delegations.md:19` — "A delegation never marks work successful because
  a worker says it succeeded."
- `operator_contract.py` (`hermes_contract_validate` docstring) — "The
  worker's own `result`/`completion_bundle` is never accepted as proof (D4)."

**Idempotent dispatch**
- `docs/missions.md:66` — exact-retry-is-idempotent / different-lineage-is-rejected.
- `operator_controller.py:44-45` — idempotency key =
  `sha256(mission_id|node|stage_id|contract_sha|attempt_seq)`.
- `operator_delegations.py` — `task_id` is `UNIQUE`; `dispatch_phase` CAS
  (`reserved -> invoking -> dispatched`) makes concurrent dispatch calls
  collapse to one.

**One authoritative scheduler lease**
- `operator_controller.py:33-39` — per-mission pass lease, TTL-bounded,
  heartbeat-renewed, crash-reclaimed by TTL expiry; conflation (one in-flight
  pass, a second trigger marks "recheck needed" rather than running two passes).
- `operator_job_supervisor.py:100-101` — per-job-id `flock`, "serialize writers
  across independently restarted server processes."

**No authority widening**
- `operator_controller.py:225-227` — `L2_FORBIDDEN_AUTH_CLASSES = frozenset({"high_impact"})`;
  the controller "never self-authorizes high-impact work (it approves
  nothing)."
- `docs/live-events.md:7` — "A missing, delayed, duplicated, or reconnected
  event must never advance work or change an authority decision."
- `docs/flight-deck-missions.md:3` — the Flight Deck browser surface gains no
  mutation/dispatch/approval authority, ever.

Autopilot adds no exception to any of the four invariants above. It is bound by
all of them at every PR in this slice.

## Build order and per-PR contract

### PR1 — Durable Autopilot runtime (**shipped in this change**)

`operator_autopilot.py` + three MCP tools: `hermes_autopilot_start`,
`hermes_autopilot_status`, `hermes_autopilot_stop`. Default OFF behind the
`HERMES_GPT_AUTOPILOT=1` machine gate (server-side tool-registration gate,
mirroring `server.py`'s `ENABLE_*` idiom) plus the standard three-step
`OperatorPolicy` gate (`require_level("workspace")` →
`require_mutation(dry_run)` → `confirm=True` required on any non-dry-run call),
matching the pattern documented for every existing mutating tool.

Durable state: one JSON file per Mission at `<hermes_root>/autopilot/<mission_id>.json`,
written with the same atomic-write-plus-flock discipline as
`operator_job_supervisor._atomic_json` / `_record_lock` (temp file, `fsync`,
`os.replace`, mode 0600/0700; per-mission `flock` around every read-modify-write).
Fields: `mission_id, enabled, state, attempt, job_id, max_concurrency,
max_replans, replans_used, started_at, updated_at, last_tick_at,
last_event_cursor, config_sha256, pid`. This store holds orchestration
metadata only — it is never consulted as the source of truth for Mission/node/
delegation state; every status read re-derives worker liveness from
`operator_job_supervisor` and Mission state from
`operator_mission_runtime.hermes_mission_get`.

**"Cannot live inside the MCP request process"** is satisfied by reusing the
exact detach pattern already used by `operator_codex.py`/`operator_runners.py`:
`hermes_autopilot_start` registers a job with `operator_job_supervisor` and
`subprocess.Popen`s a re-invocation of `operator_autopilot.py --worker
<mission_id> --job-id <job_id> --root <hermes_root>` with
`start_new_session=True` and all standard streams redirected to `DEVNULL`. The
job_id is `f"autopilot:{mission_id}:{attempt}"` — **not** fixed per Mission —
because `operator_job_supervisor` terminal states are monotonic/final by
design (`mark_running` refuses to resurrect a terminal record); a fixed job_id
would make a restart after a stop/crash silently no-op forever (caught
empirically while writing this slice's own test: a second `hermes_autopilot_start`
after a `hermes_autopilot_stop` spawned a real new process, but the worker's
own `mark_running` call was a no-op against the old, still-terminal record, so
`hermes_autopilot_status` kept reporting the dead attempt). The attempt counter
lives on the `autopilot_runs` record itself, incremented by `_claim_run`.

The parent deliberately does **not** call `mark_running(job_id, proc.pid)`
itself: reading `/proc/<pid>/cmdline` this soon after `Popen()` returns can
race a still-in-progress `execve()` and observe a transiently empty cmdline (a
second, independent race caught empirically the same way — a corrupted
`cmdline_sha256` hashing an empty string), durably recording the wrong process
identity. Instead the worker calls `mark_running(job_id, os.getpid())` itself
as the first thing it does — guaranteed post-exec, therefore always correct —
and until that happens `operator_job_supervisor` truthfully reports
`status="queued"` rather than a confidently wrong `"running"`. The worker
process is independent of the MCP server's process lifetime;
`operator_job_supervisor.reconcile_job`'s PID-reuse-resistant identity check
(`process_identity`/`verify_process`) is what makes "disconnect MCP, restart
the server, reconnect, and the state is still truthful" hold, because every
`hermes_autopilot_status` call reconciles against that identity rather than
trusting the cached `autopilot_runs` record.

**One Mission, one scheduler lease** is enforced by `_claim_run`: it reads the
current `autopilot_runs` record and, if none exists or the existing one is
terminal, writes a fresh "starting" record with the next attempt number — all
inside one `_record_lock` critical section, so two concurrent
`hermes_autopilot_start` calls cannot both observe "nothing running" and both
spawn a worker for the same Mission. (An earlier version of this design leaned
on `operator_job_supervisor.register_job`'s own idempotency for this instead,
keyed on a fixed job_id; that turned out to be the same bug as the paragraph
above — a terminal job_id can't be un-terminaled, so it couldn't double as the
per-Mission lease either. The lease now lives entirely in `autopilot_runs`,
which is Autopilot's own store, not a repurposed job-supervisor invariant.)

PR1's worker loop is intentionally a skeleton: each tick it checks (a) has the
owning `job_supervisor` job been externally cancelled (`hermes_autopilot_stop`),
in which case it syncs its own state and exits; (b) has the Mission reached a
terminal status, in which case it terminalizes the job as `completed` and
exits. It does **not** yet call the controller, the scheduler, or any dispatch
primitive — that begins at PR3. This keeps PR1 reviewable and independently
testable against its own exit gate: *start → disconnect MCP → reconnect later →
Autopilot is still alive and state is truthful.*

`hermes_autopilot_start` validates, in order, before any write: mission_id
format (`operator_mission_runtime.MISSION_ID_RE`), Mission exists and is not
terminal (`hermes_mission_get`, `TERMINAL_STATUSES`), a MissionPlan exists and
has at least one node (`hermes_plan_get`), and every node's `capability_req`
resolves through `operator_skill_resolution.validate_required_skills` — the
same canonical resolver `operator_mission_plan._validate_plan_skill_requirements`
already gates plan creation with. A second `hermes_autopilot_start` call while
a non-terminal run exists for that Mission is idempotent (returns the existing
run, does not restart the worker).

### PR2 — Parallel scheduling layer (**shipped**)

`operator_autopilot.schedule_tick` runs inside the PR1 worker loop every tick.
It is a peer caller one level above `operator_controller`;
`_frontier()` (one node per pass, in-flight before new work) and
`hermes_controller_reconcile` are unchanged and still tested as such.

Each tick, in order: machine gate (`HERMES_GPT_AUTOPILOT=1`, live read) →
Mission status (nothing new is started while `paused`/`blocked`/
`awaiting_approval` or terminal) → acquire the controller's per-mission pass
lease → `hermes_plan_review` snapshot (`version`, node states, `ready_nodes`) →
`slots = max_concurrency - count(dispatched|running)` → for each ready node in
`node_id` order, up to `slots`: adopt-or-dispatch (below) → release the lease
(also on error). There is no `autopilot_dispatch()`; a node goes through
`hermes_placement_score` (recorded, `dry_run=False`) →
`hermes_contract_define` → the controller's `_l2_target_binding` (only a
`fleet_peer` is dispatchable; anything else is held, never invented) →
`hermes_delegation_dispatch` (via the controller's `_l2_dispatch`) →
`hermes_plan_node_transition(..., "dispatched")`.

**Plan-version CAS (new, additive).** `hermes_plan_node_transition` gained an
optional `expected_plan_version`; when given it is compared with
`mission_plans.version` inside the same `BEGIN IMMEDIATE` transaction, before
the dry-run branch, and a mismatch returns `PLAN_VERSION_CONFLICT`. `None`
keeps the historical unchecked behavior for every existing caller. Autopilot
dry-run-checks it before the remote dispatch (no side effect on a stale plan)
and re-checks it on the real transition. `hermes_plan_create` is unchanged; it
still replaces the whole plan last-writer-wins, and the CAS is what stops
Autopilot from writing against a plan that no longer exists.

**Idempotency, as built.** `dispatch_key = sha256(mission_id|plan_version|
node_id|attempt|contract_sha256)` (`attempt` = `plan_nodes.retries`) derives a
deterministic `task_id` (`ap-<mission>-<node>-<key16>`) and a deterministic
`delegation_id` (`dlg-<key20>`). Order is delegation first, node transition
second, so a crash between them leaves a `pending` node plus a delegation that
the next tick **adopts** instead of dispatching again. A delegation counts as
"reached a backend" only when `dispatch_phase != 'reserved'`; a rejected
dispatch rolls back to `reserved` and is never adopted.

**Findings from building it (all verified, two were latent bugs):**

- `hermes_delegation_dispatch` salts its default `delegation_id` with the wall
  clock. Retrying the same `task_id` *without* an explicit `delegation_id` is
  rejected as "different lineage", so "exact retry is idempotent" only holds
  for callers that pass a stable id. `operator_controller._l2_dispatch` gained
  an optional `delegation_id` (default unchanged) for this.
- The controller's L2 rung dispatches through the delegation surface but never
  transitions `plan_nodes`, so a controller-dispatched node stays `pending`.
  Autopilot therefore also adopts an existing `ctl-<mission>-<node>-*`
  delegation rather than dispatching that node a second time. The controller
  lease held for the tick keeps a reconcile pass from dispatching concurrently.
- Plan nodes carry no `priority` (only the Mission does), so ordering is
  `node_id`, not `(priority, node_id)`.
- The plan store keeps only a hash of each node objective (INV-9), so the
  contract objective is a deterministic pointer and `expected_artifacts` is
  empty. Evidence requirements are PR3's job and must fail closed.
- Error envelopes are flat: `code` is top-level and `error` is a string.

**Held, never dispatched, in PR2:** approval nodes and `high_impact` nodes
(`owner_gate`, PR4 owns the frontier); `no_capable_target`;
non-`fleet_peer` targets; nodes whose prior attempt failed or was cancelled
(`prior_attempt_terminal`, PR5 owns recovery). A rejected dispatch is retried
at most `MAX_DISPATCH_FAILURES` (3) times per `(plan_version, node)`, tracked
in `autopilot_runs.dispatch_failures` (orchestration metadata only).

**Known limits, deliberately left for later PRs:** nothing observes or
completes dispatched nodes yet (PR3), so a Mission stays in flight until then;
replacing a plan while delegations are running orphans those delegations
(the CAS only prevents Autopilot writing against the old plan); Autopilot does
not require plan `status == approved` before dispatching (starting Autopilot
with `confirm=true` is the owner authorization) — flagged for review.

### PR3 — Automatic node advancement (**shipped**)

Runs inside the same lease-held tick as PR2, **before** scheduling, so a
completion frees its slot and unblocks its children within the same tick (the
plan is re-read after advancing; a changed `version` aborts the tick).

For each node in `dispatched`/`running` (and the `awaiting_*` states, see
below), Autopilot finds the node's delegation (deterministic `task_id`, or an
adopted controller `ctl-…` one) and calls
`hermes_delegation_reconcile(delegation_id, apply=True)`. That existing call
already does the observation (runner/Fabric/kanban records — never the
worker's self-report) and the Work Contract validation, and only promotes a
delegation to `succeeded` when the contract verdict is `SATISFIED`; Autopilot
adds no judge of its own. Mapping:

| observed delegation state | node action |
|---|---|
| `succeeded` **and** `_verified_success` | walk `dispatched → running → awaiting_review → validated → awaiting_approval → completed`, one CAS-guarded transition per step |
| `failed` / `cancelled` | `failed` (children stay `pending`; recovery is PR5) |
| `running` (node still `dispatched`) | `running` |
| `queued` / `reconciling` / unobserved | no change (fail closed) |

`_verified_success` requires all of: reconcile `success`, delegation state
`succeeded`, `validation_verdict == "SATISFIED"`, and the returned
`evidence_ref == "contract:<delegation contract_sha256>"`. A missing or partial
result completes nothing. A dispatch response claiming `completed` is stored as
`reconciling` by the delegation layer and is never completion.

**Approval boundary.** Only `awaiting_review`/`validated`/`awaiting_approval`
states that Autopilot itself parked are advanced: before the first step it
records `walking[node_id] = plan_version` in `autopilot_runs` (orchestration
metadata), clears it on completion, and resumes from it after a crash. A node
found in those states without that marker may be an owner's manual gate and is
held as `review_gate` even if its evidence is `SATISFIED`. Approval-kind and
`high_impact` nodes are never advanced (they are never dispatched either).
Autopilot never completes or approves the Mission; `final_approval_required`
and `hermes_mission_approve` are untouched.

Intermediate transitions are ordinary state-machine steps, not a claim that a
review or approval happened; the Work Contract's `review_requirements` and
`completion_criteria` (via reconcile) are what gate completion. PR3 contracts
still carry no `expected_artifacts` (INV-9 — see PR2), so artifact-based
evidence requirements are not yet expressible from an Autopilot dispatch.

### PR4 — Approval Frontier (planned)

A derived read, not a new gate: the frontier is active exactly when the next
runnable item is a `kind: "approval"` node or any node whose
`capability_req.authorization_class == "high_impact"` — the same
`AUTH_CLASSES` vocabulary already shared by `operator_mission_plan`,
`operator_placement`, and `operator_controller.L2_FORBIDDEN_AUTH_CLASSES`.
Autopilot state becomes `waiting_for_owner`; it stops issuing new dispatches
past that point. Resolution is still exactly `hermes_mission_approve` — PR4
adds no new approval tool.

### PR5 — Recovery and bounded replanning (planned)

Level A (retry on alternate placement) reuses `hermes_placement_score` against
the same node requirement with a different target pool; it never touches
`plan_nodes.contract_sha256`/lineage — a new attempt, same logical node,
preserved history. Level B (semantic replan) builds on the *existing*
`escalate_semantic` / `replan_proposal` machinery in
`operator_failure_semantics.py`, which today is **always proposal-only**
(`replan_proposal.executed` is never set `True` anywhere in the codebase).
Autopilot PR5 is the first thing allowed to execute that proposal — bounded by
`max_replans`, CAS-checked against plan version, re-validated through
`operator_skill_resolution` and DAG-acyclic validation
(`operator_mission_plan._validate_node_dag`) on every patch, and forbidden by
construction from touching a `completed` node, deleting evidence, lowering an
`authorization_class`, or removing an approval node — enforced the same way
`operator_mission_plan._canonical_node`/`_validate_node_dag` already refuse
malformed plans, not by a new check bolted onto Autopilot.

### PR6 — Mission limits (planned)

`operator_mission_budget.enforce_budget_breaker` is the existing D3
hard-block path (pauses the Mission, raises `budget_breaker`); Autopilot calls
`hermes_budget_check(enforce=True)` before each new dispatch and treats a
paused Mission as a hard stop. `max_concurrency` / `max_replans` /
`max_attempts_per_node` / `max_runtime_seconds` are Autopilot-only operational
config (already the `autopilot_runs` shape from PR1) — no changes to
`operator_mission_budget`'s spend-unit model.

### PR7 — Event-driven wakeups (planned)

`operator_live_events.hermes_live_events_since(wait_ms=...)` long-polls today;
an out-of-process Autopilot worker calls it as an ordinary client (it cannot
share the in-process `threading.Condition`). Per `docs/live-events.md:7`, a
wakeup is never itself proof of anything — every wakeup re-reads durable state
via the same reads PR2/PR3 already do. `last_event_cursor` (already in the PR1
schema) is what makes this resumable after a restart.

### PR8 — Flight Deck Autopilot UI (planned)

Extends `ui_missions.py` read-only, following its own stated convention
exactly: pull through existing `hermes_*` read tools only (never a new query
path), capture the live-event cursor before the durable read (as
`_mission_detail` already does), stamp `"read_only": True`, and add no POST/PUT
route (`docs/flight-deck-missions.md:3`).

### PR9 — `hermes_autopilot_status` v2 (planned)

Expands PR1's status payload to the full bounded summary (progress counts,
workers, budget status, recovery/replan counters, approval frontier) — additive
fields only, no shape break for PR1 callers.

### PR10 — Real acceptance test (planned)

The scenario in the original spec stands as written: ≥4 nodes, ≥3 independent,
≥2 placements, mid-run peer kill + reroute with no duplicate mutation-capable
attempt, a real approval frontier stop/resume, and a repeat of the whole run
with the MCP server restarted mid-Mission. This is the gate for calling the
slice done — PR1 alone only proves the narrower "restart-survives" claim for
the runtime shell itself.

## Release blockers (unchanged from the original brief)

Any of the following blocks shipping v0.13, at any PR:

duplicate mutation-capable execution; a completed node rewritten during
replan; worker self-report accepted as completion evidence; Autopilot crossing
the approval frontier; a budget crossing that still allows new dispatch; an
MCP/server restart that loses Autopilot ownership; stale capability data
bypassing `operator_skill_resolution`; a Fabric peer gaining authority beyond
its Work Contract; a missing artifact/evidence treated as success; a semantic
replan removing a human gate; two schedulers controlling the same Mission
concurrently.
