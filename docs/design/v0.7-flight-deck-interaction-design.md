## 1. Purpose

This document specifies the interaction and visual design for the **Flight
Deck** control-plane theme of Hermes GPT v0.7.0.

The Flight Deck is **not a new product surface with new authority**. Per
decision D2-A (ADR-002) it is a **read-only presentation layer** over the
existing MCP surface: the MCP tools remain the only interface to the system,
and the Flight Deck theme governs how those surfaces are presented,
structured, and understood by the operator.

It covers:

- the four required user flows (launch/monitor, event history, evidence
  review, authority),
- wireframes for each flow,
- visual direction (theme tokens, typography, layout, states),
- interaction specs (gates, dry-run, redaction, error handling),
- a reusable asset list for implementation,
- design conflicts flagged against the architecture contract.

**Acceptance (from the card):** design package approved by default and ready
for implementation.

---

## 2. Visual thesis

> **The Flight Deck makes durable autonomy legible: every long-running task,
> every event, every piece of evidence, and every authority grant is visible,
> inspectable, and gated — without giving the operator a bypass.**

One glance at the Deck answers four questions:

1. What is running, and is it healthy?
2. What happened, in order, across all stores?
3. Can this work be trusted, and on what evidence?
4. What am I allowed to do, and what will it cost (dry-run → confirm)?

## 3. Design principles

Derived directly from the architecture contract (§9.2) and v0.6 invariants.

| # | Principle | Architecture anchor |
|---|---|---|
| P1 | **Read-only by construction.** Every rendered value comes from a read surface (`hermes_mission_*`, `hermes_events_*`, `hermes_contract_status`, `hermes_swarm_workflow_status`). The UI never reads stores directly. | §9.2 |
| P2 | **No new authority.** Any action the UI offers must call the existing gated `hermes_*` tool. There are no UI-only mutation buttons. | §9.2, D2-A |
| P3 | **Redaction is visible, not silent.** Redacted fields render as explicit `[REDACTED]` markers with a reason, never as missing data. | §9.2, §6.3 |
| P4 | **Dry-run before confirm, always.** Mutations surface in the Deck as two-step: compute plan (no-op) → explicit confirm. | v0.6 posture |
| P5 | **Evidence over assertion.** Status labels link to the evidence that justifies them. "Done" without evidence is shown as `NOT_SATISFIED`, fail-closed. | Work Contract validator |
| P6 | **Fail-closed visibility.** Interrupted/blocked states are shown loudly with a reason and the explicit recovery path (reconcile → blocked → operator advances). Never auto-advance. | §8.2, R6 |
| P7 | **Authority transparency.** Every surface displays the level class, gate, and apply mode that governs it. | G6 |
| P8 | **Bounded everything.** Lists, timelines, and payloads are bounded and paginated; the UI never requests unbounded reads. | Mission Control caps, events limit |

## 4. Information architecture

Five primary views, one persistent chrome.

```
FLIGHT DECK (persistent chrome)
├── 01 OVERVIEW          — system status, active tasks, recent events, authority posture
├── 02 LAUNCH            — define → validate → dry-run → confirm → dispatch
├── 03 TASK MONITOR      — stage ladder, evidence, gated actions, related events
├── 04 EVENT HISTORY     — unified redacted timeline with filters
├── 05 EVIDENCE REVIEW   — observed evidence, review acceptance (owner-gated)
└── 06 AUTHORITY         — level ladder, apply mode, surface gates, explainability
```

Chrome (persistent):

- **Top bar**: identity (`FLIGHT DECK`), release tag, current operator
  level + apply mode (always visible — P7), client identity.
- **Left rail**: view navigation; mission surface list (read-only entry
  points); context-independent.
- **Footer**: contract line — sources used, `redacted · read-only`, slice
  reference. Keeps provenance visible on every view.

Wireframes: `docs/design/v0.7-flight-deck-wireframes.html`.

## 5. User flows

### Flow 1 — Launch and monitor long-running tasks

**Goal:** the operator can define, validate, dispatch, and watch durable work
across swarm/contract/codex/cron without ever bypassing the authority gates.

**Trigger:** any of —

- a swarm workflow needs dispatch (`hermes_swarm_stage_dispatch`);
- a work contract needs dispatch (`hermes_contract_dispatch`);
- an async Codex job or cron run is expected and must be watched.

**Steps (Launch):**

1. **Define work.** Operator supplies or edits contract/workflow JSON.
   `hermes_contract_define` / `hermes_swarm_workflow_validate` validates
   schema, caps, forbidden actions, review requirements.
2. **Validate.** Fail-closed observed-state validation. On failure, show the
   error list and return to step 1 — **no dispatch attempted**.
3. **Dry-run dispatch.** Call dispatch with `dry_run=true`. The Deck shows
   the computed plan (target, stages, estimated cost) and writes an audit
   event. Nothing mutates.
4. **Confirm.** Explicit `confirm=true` at the gated tool — the only mutation
   point. Denied if level is insufficient (`AUTHZ_DENIED` envelope +
   `suggested_action` rendered verbatim).
5. **Dispatched & monitoring.** Task created, event written, monitor view
   opens. From this point the task is restart-safe (S2 reconcile).

**Steps (Monitor):**

1. **Stage ladder.** Workflow stages render left→right with status colors:
   done (emerald), current (flight), pending (muted), blocked (amber).
2. **Evidence panel.** Shows the contract SHA, observed state, artifact refs.
3. **Gated actions.** `advance stage`, `reconcile`, `review accept` — each
   renders as dry-run → confirm, tagged with required level.
4. **Related events.** `hermes_events_query(subject_id=...)` inline strip.

**States and transitions:**

| State | Rendered as | Meaning |
|---|---|---|
| `running` | flight dot + elapsed | stage executing |
| `blocked` | amber + reason line | interrupted/needs operator; **never auto-advances** |
| `awaiting_approval` | violet badge | evidence review pending |
| `done` | emerald badge | terminal, evidence-linked |
| `NOT_SATISFIED` | violet badge | contract validated but no acceptance record |

**Failure paths:**

- validation fail → back to define, errors listed;
- dispatch denied → AUTHZ_DENIED + suggested action;
- restart mid-flight → reconcile marks interrupted stages `blocked`; operator
  re-advances explicitly;
- stale cache → surface shows `refresh` affordance, 5s TTL.

### Flow 2 — Inspect structured event history

**Goal:** the operator can answer "what happened, in order" across
swarm/contract/cron/codex/kanban/audit through one unified, redacted,
bounded timeline.

**Trigger:** entry from Overview recent events, from any subject in a task
monitor, or directly from the rail.

**Steps:**

1. **Filters** map 1:1 to `hermes_events_query` args: `source`,
   `subject_id`, `kind`, `since`, `until`, `limit`. Apply → query. Reset →
   defaults.
2. **Timeline** renders normalized `EventRecord`s (event_id, ts, source,
   kind, actor, subject_id, status_before/after, summary, refs, trace_id).
3. **Redaction markers** render as `[REDACTED]` with the invariant reason —
   no raw bodies, no transcripts, no credentials.
4. **Pagination** uses bounded `limit` (default 50) and `hermes_events_tail`
   for the recent strip.
5. **Drill-down** from any event to the subject's task monitor or evidence
   review, when the subject is a workflow/contract.

**Constraints the design honors:**

- retention window (default 90d, `HERMES_GPT_EVENTS_MAX_AGE_DAYS`) shown in
  the filter bar;
- allowlist semantics (`HERMES_GPT_EVENTS_ALLOWED_SOURCES`: unset = all,
  list = only listed, empty = none) — the UI simply renders what the surface
  returns, including denials;
- no raw bodies ever; refs only.

### Flow 3 — Review production evidence

**Goal:** the operator can close the v0.6 gap — accept a contract with
referenced evidence through the owner-gated `hermes_review_accept` writer —
and see validation flip to `SATISFIED`.

**Trigger:** contract in `awaiting_approval` / validation returned
`NOT_SATISFIED`.

**Steps:**

1. **Inspect observed evidence.** Read-only: expected artifacts present,
   contract SHA pinned, forbidden-actions audit, current acceptance status.
2. **Fill review acceptance.** Reviewer (must be distinct from assignee —
   enforced in code, surfaced as a visible constraint), verdict
   (bounded vocabulary), evidence refs (required).
3. **Dry-run accept.** `hermes_review_accept(dry_run=true)` — no mutation.
4. **Confirm.** owner level + direct + confirm; audited.
5. **Record written.** Append to `review-evidence/review-acceptances.jsonl`;
   `record_id` returned.
6. **Re-validate.** `hermes_contract_validate` re-run → `SATISFIED`.

**Design rules:**

- self-review is visibly rejected (`reviewer ≠ assignee`);
- evidence is referenced, never copied; no raw prompts/transcripts;
- the flow is presented as a linear spec (1 → 4) so the operator understands
  the cost of each step before confirming;
- retention (30d proposed) noted as legal-open.

### Flow 4 — Understand and control least-privilege authority

**Goal:** the operator can see exactly what they may do and how each gate
behaves, and change posture only through the existing gated config/env tools.

**Trigger:** rail entry, or the posture card on Overview.

**Steps:**

1. **Current posture card.** Level, apply mode, owner mode, audit status,
   mutation gate rule.
2. **Level ladder.** read_only → cron → skills → skills_config → workspace →
   owner; current level marked; owner marked break-glass with its
   requirements (`HERMES_GPT_OWNER_ACTIVE` + owner ack, secret-path
   protections not bypassed).
3. **Surface gates.** Every new v0.7 surface with its authority class
   (`review_accept → owner`, `events_* → read_only`, `oauth_status →
   read_only`, `oauth_revoke → owner*`, `swarm_reconcile → ws/owner`).
4. **Allowlist semantics** rendered exactly: unset = all, list = only
   listed, empty = none — with the env names.
5. **Control is explicit.** Posture changes land through config/env tools at
   their level gates; the Deck surfaces state and never bypasses.

**Design rule:** the Deck shows the authority model; it does not implement a
parallel one (NG6).

## 6. Visual direction

### 6.1 Theme

**Control-plane dark theme** — consistent with the architecture's
"control-plane" language (D2-A) and the fleet's existing dark diagrams style.
The Deck reads as instrumentation, not as marketing.

### 6.2 Tokens

| Token | Value | Use |
|---|---|---|
| `bg/base` | `#0B1020` | page background |
| `bg/panel` | `#131A2E` | cards/panels |
| `bg/inset` | `#0F1730` | nested rows, inputs |
| `bg/code` | `#0A0F20` | JSON/code blocks |
| `border/default` | `#2A3550` | panel borders |
| `grid/line` | `#1B2440` | background grid (40px) |
| `text/primary` | `#E6EDF7` | headings, values |
| `text/muted` | `#8B98B8` | secondary text |
| `text/dim` | `#5B6A8F` | meta, footers |
| `accent/flight` | `#22D3EE` | active, current, links |
| `status/ok` | `#34D399` | healthy, done, satisfied |
| `status/warn` | `#FBBF24` | dry-run, blocked, warning |
| `status/deny` | `#FB7185` | denied, error, owner-critical |
| `status/review` | `#A78BFA` | review/authority pending |
| `status/muted` | `#64748B` | neutral pending |

### 6.3 Typography

- **Primary**: monospace (`JetBrains Mono`, fallback `IBM Plex Mono`,
  `ui-monospace`). Instrument feel; aligns with existing diagram style.
- **Sizes**: 17px identity; 13–14px section headings; 11–12px body; 10px
  meta. No sizes below 10px in rendered views.
- **Letter-spacing**: 2px on the `FLIGHT DECK` identity only.

### 6.4 Layout

- 1200×780 wireframe canvas; left rail 180px; content 972px.
- Cards: 6px radius; 1px border; 12px internal padding.
- Persistent chrome: top bar 56px, footer 40px.
- Status chips: 22–24px height, colored tint background (opacity 0.15–0.2)
  + colored text.
- Stage ladder: 44px stage cards, chevron connectors.

### 6.5 States and motion

- **Loading**: value rows render as muted placeholder dashes (`···`) — never
  blank; refresh affordance visible.
- **Stale**: cache TTL noted under the panel title (e.g. `TTL 5s`).
- **Denied**: `AUTHZ_DENIED` envelope rendered verbatim with
  `suggested_action`; panel border tints deny-red.
- **Dry-run**: amber chip `DRY-RUN · NO-OP`; no confirm color until confirm
  is genuinely available.
- **Confirm**: emerald chip; only rendered when the tool call would pass
  level + owner ack.
- Motion, if implemented: minimal — fade/slide on view change only. No
  decorative animation. Status changes never animate silently; a change
  writes an event and the event is visible (P5/P6).

## 7. Interaction specs (by component)

### 7.1 Posture bar (persistent)

- Always shows level + apply mode (P7).
- Clicking level opens Authority view.
- Source: `operator_policy` status via Mission Control overview / config
  surface; refresh on view load.

### 7.2 Task row

- Renders subject_id, kind, stage/status, elapsed, reason when blocked.
- Row click → Task Monitor for that subject.
- Source: `hermes_swarm_workflow_list`, `hermes_mission_codex`,
  `hermes_mission_cron`.

### 7.3 Event row

- Renders ts, source chip, kind, actor, subject, summary (redacted),
  refs, trace_id.
- Subject link when it is a workflow/contract.
- Source: `hermes_events_query` / `hermes_events_tail`.

### 7.4 Gated action button

Three states, always in this order:

1. **Idle**: label + level tag (e.g. `owner`).
2. **Dry-run**: click runs the tool with `dry_run=true`; result plan shown;
   chip flips amber `DRY-RUN · NO-OP`.
3. **Confirm**: second click runs with `confirm=true`; success shows the
   returned id/record; failure shows the envelope.

Never a single-click mutation.

### 7.5 Review acceptance form

- Fields: reviewer, verdict, evidence refs (required), approval reference
  (optional).
- Constraint text: `reviewer ≠ assignee enforced`.
- Buttons: `DRY-RUN first` → `CONFIRM` (owner-gated).

### 7.6 Filter bar (event history)

- Controls map 1:1 to query args; Apply/RESET; retention + allowlist note
  under the bar.

## 9. Conflicts and flags against the architecture contract

| # | Flag | Resolution / note |
|---|---|---|
| F1 | D2-A keeps the MCP surface as the only interface; a rendered "dashboard" is explicitly **not** in v0.7 scope (open question 6). The wireframes are a **presentation contract** — the reference implementation is a thin read-only consumer, not a new interactive product. | Design aligns; S7 optional consumer test only if media/Tony approve dashboard scope. |
| F2 | No UI-only mutation: every "action" in the wireframes is a call to the gated `hermes_*` tool. Any S7 consumer must not shortcut this — a mutation button that bypasses tools would violate NG6/R6. | Hard constraint, restated in §3 P2. |
| F3 | Event redaction means some views will look sparse (bodies absent). This is intended, not a bug. The design renders `[REDACTED]` markers so operators can distinguish "absent" from "redacted". | Behavior mandated by §6.3 invariants. |
| F4 | Allowlist semantics: unset = all is not "deny by default". The Deck must render the effective semantics (including "all") and must not claim deny-by-default. | Architecture §9.1 explicit warning; mirrored in wireframe caption. |
| F5 | `hermes_oauth_revoke` and retention windows are legal-pending; the Authority view and Evidence Review note the `*`/open-question status rather than asserting them as shipped. | Kept truthful to gates. |
| F6 | Timeline is a read-model over existing stores; there is no write path. The design must never imply the UI can edit history. | P1/P8; wireframe shows `APPLY` filters only. |
| F7 | Owner mode is break-glass and does not bypass secret-path protections; the Authority view states this literally. | Mirrors v0.6 invariant. |
